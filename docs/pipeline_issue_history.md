# RAG 파이프라인 이슈 정리

현재 파이프라인(`src/pipeline.py`)에서 확인된 여섯 가지 문제 — 응답 지연(Reranking), 출처 URL 오출력,
[NO_SOURCE] 마커 신뢰성, 하위 답변 출처 소실, 마커 내용 오표기, 분해 프롬프트 부스러기 유입 —
의 원인과 해결 방안을 정리한다.

## 이슈 1. Reranking 단계 CPU 병목으로 인한 응답 지연

### 목적

전체 답변 시간이 오래 걸리는 원인을 확인하기 위해 `rag_answer()`의 단계별 실행 시간을 측정한다.

### 측정 방식

- 기존 `rag_answer(query)`는 문자열을 반환하는 구조를 유지한다.
- 내부에 `_rag_answer_traced(query)` 함수를 추가한다.
- `_rag_answer_traced()`에서 단계별 시간과 최종 답변을 함께 반환한다.
- 성능 측정 스크립트에서만 `_rag_answer_traced()`를 사용한다.

측정 단계:

- 질문 분류
- 검색
- Reranking
- 출처 및 민원 데이터 구성
- 프롬프트 생성
- HyperCLOVA X 호출
- 전체 실행 시간

### 대표 질문 선정

`testset_all.jsonl`에서 실제 라벨이 확인된 질문을 유형별로 1개씩 선택한다.

- 정보성 질문
- 민원성 질문
- 표 조회 질문
- 근거 부족 또는 범위 밖 질문

새로운 질문을 임의로 만들지 않고 기존 테스트셋의 질문을 사용한다.

### Cold와 Warm

- **Cold 실행**: 프로그램 실행 후 첫 질문으로, 모델과 인덱스 로딩 시간이 포함된다.
- **Warm 실행**: 첫 실행 이후 모델과 데이터가 메모리에 올라온 상태에서 질문을 처리한다.
- 실제 질문 처리 성능은 Warm 실행 시간을 기준으로 비교한다.

첫 질문을 웜업용으로 한 번 실행한 뒤, 대표 질문 4개를 다시 실행하여 측정한다.

### 측정 결과

단계별 실행 시간을 측정한 결과, 전체 응답 시간의 대부분이 **Reranking 단계**에서 발생하였다.

| 질문 유형 | Reranking | LLM 호출 | 전체 시간 |
| --- | --- | --- | --- |
| 정보성 | 99.47초 | 2.17초 | 101.90초 |
| 민원성 | 105.42초 | 2.18초 | 107.78초 |
| 표 조회 | 131.72초 | 0.98초 | 132.83초 |
| 근거 부족 | 160.78초 | 4.93초 | 166.39초 |

- 질문 분류: 약 0.01~0.6초
- 검색: 약 0.01~0.26초
- 근거 조립: 0초에 가까움
- 프롬프트 조립: 0초에 가까움
- LLM 호출: 약 0.98~4.93초
- Reranking: 약 99~161초

전체 실행 시간의 **97% 이상을 Reranking이 차지**하고 있어, 현재 응답 지연의 원인은 거의 전부 재정렬 단계로 확인되었다.

### Cold/Warm 실행 결과

웜업 실행의 전체 시간은 176.69초였다.

이 실행에는 임베딩 모델의 최초 로딩 시간이 포함되어 있어 일반 질문 처리 시간과 직접 비교하지 않는다. 문서에는 Cold 실행 또는 웜업 결과로 별도 표시하였다.

대표 질문 4개의 성능 비교에는 모델 로딩이 끝난 이후의 Warm 실행 결과를 사용하였다.

### 원인 확인

Reranking 관련 코드 구조(`src/reranker.py`)를 확인한 결과는 다음과 같다.

- Reranker 모델은 싱글턴으로 관리되어 요청마다 다시 로딩되지 않는다.
- `device="cpu"`로 설정되어 CPU에서 실행된다.
- 질문과 후보 청크를 `model.predict(pairs)`에 전달하여 배치로 처리한다.
- 초기 후보는 20개다(`pipeline.py`의 `K_CANDIDATES=20`).
- 일부 청크는 최대 약 5,502토큰으로 매우 길다.
- Reranker의 `max_length`는 8,192로 설정되어 있다.

따라서 현재 지연은 모델 재로딩이나 반복 호출 문제가 아니라, **긴 청크 20개를 대형 Cross-Encoder가 CPU에서 처리하면서 발생하는 순수 연산 시간**으로 판단된다.

Cross-Encoder는 질문과 청크 전체를 함께 입력해 Attention을 계산하므로, 입력 길이가 길어질수록 연산량이 크게 증가한다. 특히 긴 청크가 포함된 질문에서 Reranking 시간이 100초 이상으로 증가하였다.

### 현재 결론

- 검색이나 HyperCLOVA X 호출은 주요 병목이 아니다.
- 전체 지연의 핵심 원인은 CPU 기반 Cross-Encoder Reranking이다.
- 모델 반복 로딩 문제는 확인되지 않았다.
- 배치 처리도 이미 적용되어 있다.
- 긴 청크, 높은 `max_length`, 후보 20개, CPU 실행의 조합이 주요 원인으로 보인다.

### 추가 실험 — 리랭커 도입 여부 검증 (결론: Off)

리랭킹 단계가 답변 속도를 크게 늦추는 것을 확인한 뒤(질문 1개당 약 30초, 긴 청크가 걸리면 그 이상), 속도를 튜닝하기 전에 근본 질문부터 확인하기로 했다: **리랭커가 그 시간을 쓸 만큼 검색 품질을 실제로 올리는가?**

**측정 방법**

현행 파이프라인 설정을 그대로 사용했다 — 리랭커는 `BAAI/bge-reranker-v2-m3`(cross-encoder), 1차 검색 상위 20개 후보를 재정렬해 상위 5개를 남기는 방식, `max_length=8192`, CPU 실행. 동일한 1차 후보(top-20)에 대해 "리랭크 없이 상위 5개"와 "리랭크 후 상위 5개"를 비교해, 정답 페이지가 상위 5개에 들어오는지(Recall@5)와 그 순위(MRR@5)를 페이지 단위로 측정했다. 표본은 쉬운 질문 3개 + 새로 만든 모호(구어체) 질문 3개, 총 6개.

**결과**

| 구분 | Recall@5 (Off→On) | MRR@5 (Off→On) |
| --- | --- | --- |
| 전체 6문항 | 0.83 → 0.83 | 0.71 → 0.64 |
| 쉬운 3문항 | 1.00 → 1.00 | 0.75 → 0.61 |
| 모호 3문항 | 0.67 → 0.67 | 0.67 → 0.67 |

리랭커가 새로 건져낸 정답은 하나도 없었고(Recall 개선 0), 순위는 오히려 소폭 나빠졌다.

**질문별 원인**

- 한 쉬운 질문: 리랭크 없이 정답이 이미 1위였는데, 리랭커가 2위로 강등시킴(순위점수 1.00→0.50).
- 한 모호 질문: 순위 변화 없음. 그런데도 긴 청크 때문에 리랭킹에만 210초(3.5분) 소요.
- 다른 모호 질문: 정답 페이지가 애초에 1차 검색 top-20 안에 없어 리랭커가 손을 쓸 수 없었음.
- 나머지: 변화 없음.

**해석**

임베딩(bge-m3-ko) 기반 1차 검색이 이미 충분히 강해서 리랭커가 더 얹을 여지가 거의 없고, 오히려 이미 맞게 배열된 순위를 흔드는 부작용이 관찰된다. 여기에 리랭커는 후보마다 모델을 다시 돌려야 하는 cross-encoder라 CPU에서 극단적으로 느리다(격리 측정에서 후보 20개에 약 27초, 긴 청크가 섞이면 질문 하나에 수 분까지 증가). 종합하면 현행 설정(k=20, max_length=8192, CPU)의 리랭커는 **이득은 없거나 마이너스인데 비용(시간)은 매우 크다.**

**한계**

표본이 6개로 매우 작다. 특히 MRR 하락은 사실상 한 질문(정답 강등 사례)이 주도한 것이라 통계적으로 확정할 수준은 아니다. 큰 표본으로 확인하는 게 이상적이지만, CPU·max_length=8192·k=20 설정에서는 40문항에 한 시간이 넘어 현실적으로 대규모 측정이 불가능했다. 대규모 재확인은 GPU(예: Colab)나 더 가벼운 리랭커 설정에서 별도로 진행해야 한다.

### 최종 결정: 리랭커 기본 Off

위 실험 결과를 근거로 팀 협의를 거쳐 **리랭커를 기본 Off로 결정했다.** 현 시점에서 리랭커는 검색 품질을 올리지 못하면서 응답 속도만 크게 악화시키기 때문이다.

향후 재도입을 검토한다면:

1. GPU 환경에서 더 큰 표본으로 리랭커 이득을 재측정한다.
2. `max_length`·후보 수를 줄인 경량 설정에서 품질(Recall@5·MRR@5)이 유지되는지 확인한 뒤 재도입 여부를 다시 판단한다.

### 구현 반영

위 결정을 실제 코드에 반영했다.

- **`reranker.py` → `candidate_ranking.py` 파일명 변경**
  리랭킹이 꺼진 상태에서 이 파일이 실제로 하는 일은 "1차 검색 후보를 상위 k로 좁히는 것"(`top_k_cut`)이고, cross-encoder 재정렬(`rerank`)은 있지만 안 쓰는 선택 단계다. 파일명이 여전히 `reranker.py`면 "리랭커인데 왜 안 쓰지?"라는 의문을 코드만 보고는 풀 수 없어서, 실제 역할에 맞게 이름을 바꿨다.

- **`pipeline.py`에 `USE_RERANKER = False` 플래그 추가**
  `rerank()` 함수 코드 자체는 `candidate_ranking.py`에 그대로 남겨두고, `pipeline.py`에서 이 플래그로만 호출 여부를 가른다(`rerank(query, candidates) if USE_RERANKER else candidates`). 재도입은 이 값을 `True`로 바꾸는 한 줄로 끝나며, 이 파일에 재도입 전 GPU/경량 설정 재검증이 필요하다는 근거도 주석으로 같이 남겨뒀다.

- **docstring에 결정 근거를 self-contained로 기록**
  `candidate_ranking.py` 상단에 비활성 상태·측정 결과·재도입 조건을 그대로 적어뒀다. gitignore된 별도 결정 문서(`project_context.md` 등) 없이도 이 파일만 보고 "왜 꺼져 있는지"를 알 수 있게 하기 위함이다.

- **참조 정리**: `pipeline.py`의 import(`from candidate_ranking import rerank, top_k_cut`)와 `prompt_builder.py`·`retrieval.py`의 관련 주석을 새 파일명·역할에 맞게 갱신했다.

**효과**: 질문당 27~210초 걸리던 리랭킹 단계가 사라져 응답 속도가 대폭 빨라졌고, Off 상태에서 측정했던 "무리랭크" 경로(Recall@5 0.83)와 동일한 품질을 유지한다.

**참고 — Off 결정 이전에 검토했던 속도 최적화 옵션**

리랭커를 계속 쓴다는 전제로 정리했던 대안들이다. 지금은 채택하지 않지만, 향후 재도입을 검토할 때 참고용으로 남겨둔다.

1. **`K_CANDIDATES` 축소** (`pipeline.py`, 현재 20)
   후보 수를 줄이면 Reranking 호출 횟수가 그만큼 줄어 선형적으로 빨라진다. 다만 20이라는 값은 `route_eval.py`로 실측한 Recall@20(99%+) 근거로 정해진 값이라, 줄이기 전에 더 작은 k(예: 10)에서의 Recall을 같은 방식으로 측정해 정답률 손실이 감내할 수준인지 먼저 확인해야 한다.

2. **`max_length` 축소** (`candidate_ranking.py`, 현재 8192)
   8192는 코퍼스 전체 최대 토큰(5,502)을 커버하기 위한 값이지만, 대부분의 청크는 이보다 훨씬 짧다. 청크 길이 분포를 실측해 상위 몇 %가 실제로 8192에 가까운 길이를 쓰는지 확인하고, 대다수를 커버하는 더 작은 값(예: 2048~3072)으로 낮추면 긴 꼬리 청크 일부만 잘리는 대가로 평균 연산 시간을 크게 줄일 수 있다.

3. **더 가벼운 reranker 모델로 교체**
   `bge-reranker-v2-m3` 대신 `bge-reranker-base` 등 더 작은 cross-encoder로 바꾸면 속도는 오르지만 재정렬 정확도가 떨어질 수 있다. 임베딩 모델 비교 때와 동일하게, 후보 모델들의 AnswerRecall@5를 같은 테스트셋으로 비교해 손실 폭을 확인한 뒤 결정한다.

4. **GPU 사용** (`device="cpu"` → `device="cuda"`)
   가장 근본적인 해결책이지만 코드 변경(`candidate_ranking.py`, 그리고 동일하게 CPU로 고정된 `retrieval.py`의 Dense 임베딩 모델도 함께)과 GPU 서빙 인프라가 모두 필요하다. 배포 환경에 상시 GPU를 확보할 수 있는지가 선행 조건이다.

5. **조건부 Reranking**
   1차 검색(BM25/Dense/Hybrid) 점수 격차가 이미 충분히 크면(상위 후보가 압도적으로 높은 점수) Reranking을 생략하고, 격차가 애매한 경우에만 Reranking을 적용하는 방식. 구현 난이도가 있어 우선순위는 낮지만, 평균 응답 시간을 줄이는 데는 효과적일 수 있다.

위 실험에서 리랭커가 품질 이득을 보이지 못했기 때문에, 지금은 이 옵션들을 적용하기보다 리랭커 자체를 Off 상태로 두는 것이 우선이다. 재도입을 검토하게 되면 그때 이 목록부터 순서대로(1→5) 시도한다.

## 이슈 2. 답변 출처 URL 오출력

### 문제

`rag_answer()`가 생성한 답변 끝에 붙는 출처 표시에서 URL이 누락되거나 실제 검색된 페이지와 다른 출처가 출력되는 문제가 발견되었다.

### 원인

`src/citation.py`는 문제가 없다 — `format_all_citations()`가 `data/corpus.jsonl`에서 실제 `source_url`·`page_title`을 정확히 조회해 `prompt_builder.py`에 넘긴다.

문제는 `src/prompt_builder.py`의 `FEW_SHOT_EXAMPLES`에 있다:

```python
"answer": "주민등록증·운전면허증·여권 등 공공기관 발행 신분증과 본인의 도장(서명 가능)만 있으면 됩니다.\n\n(출처: 신청시 구비서류 안내)",
```

세 개 few-shot 예시 전부 답변 끝을 `(출처: <제목>)` 형식으로 마무리하는데, **URL이 전혀 포함되어 있지 않다.** 반면 `SYSTEM_INSTRUCTION`에는 "답변 끝에 참고한 출처(페이지 제목과 링크)를 안내하세요"라고 되어 있어, **지시문과 few-shot 예시의 요구 포맷이 서로 다르다.**

실제 프롬프트 구조를 보면, 진짜 검색 결과의 제목·URL은 `참고 출처:` 섹션에 별도로 주어지는데(`build_informational_prompt()`의 `sources` 변수), 모델이 이 섹션을 참고해 답변을 구성하기보다 **few-shot 예시의 답변 종료 패턴(제목만 있는 짧은 문구)을 그대로 흉내 내면서** URL을 빠뜨리거나, 심한 경우 예시에 나온 고정 문구("신청시 구비서류 안내")를 실제 질문과 무관하게 재사용하는 것으로 보인다. LLM은 일반적으로 추상적인 지시문보다 few-shot 예시의 출력 형식을 더 강하게 따라가는 경향이 있어, 이런 불일치가 있으면 예시 쪽이 우선하는 경우가 많다.

### 해결 방안

1. **`FEW_SHOT_EXAMPLES`의 답변 형식을 실제 원하는 출력 형식으로 수정** (가장 중요)
   세 예시 모두 답변 종료 문구를 `(출처: 제목)`이 아니라 `(출처: 제목 - URL)` 또는 팀이 최종적으로 원하는 형식(예: 마크다운 링크)으로 바꿔서, 모델이 URL 포함 형식을 그대로 학습하도록 한다. 이때 예시에 쓰는 URL도 실제 `data/corpus.jsonl`에 있는 값을 그대로 가져와야 한다(지어내면 안 됨 — 기존에도 `reference_answer`를 그대로 가져다 쓴 원칙과 동일).

2. **`SYSTEM_INSTRUCTION`과 few-shot 예시 포맷 일치**
   지시문 3번("페이지 제목과 링크를 안내하세요")과 예시가 항상 같은 형식을 보여주도록 맞춘다. 포맷이 하나로 통일되면 모델이 헷갈릴 여지가 줄어든다.

3. **"참고 출처" 섹션을 그대로 인용하라는 지시 강화**
   `build_civil_petition_prompt()`에는 이미 "위 URL은 새로 만들지 말고 그대로 인용하세요"라는 문구가 있다. `build_informational_prompt()`에도 동일한 취지의 문구를 추가해, 모델이 `참고 출처:` 섹션의 실제 URL을 답변에 그대로 반영하도록 명시적으로 강조한다.

**1번(few-shot 예시 수정)만으로도 대부분 해결될 가능성이 높고, 2·3번은 재발 방지를 위한 보강책이다.**

## 이슈 2 후속 — 실제 적용한 해결책 (2026-07-23)

위에서 제안한 방법(few-shot 형식 수정 등)을 실제로 시도해봤지만, 재현 테스트에서 충분히 해결되지 않았다. 그래서 방향을 바꿔 더 구조적인 방식으로 해결했다.

### 시도했지만 부족했던 것들

다음 세 가지를 순서대로 적용해봤다.

1. `SYSTEM_INSTRUCTION`에 "few-shot은 형식만 참고하고, 근거에 없는 내용은 가져오지 말 것"이라는 원칙 추가
2. 절차 → 서류 → 페이지 순서 규칙에 "근거 없는 단계는 생략" 예외 추가
3. 서류·링크 근거가 비어있으면 그 섹션 자체를 프롬프트에서 삭제(빈 칸 자체를 안 줌)

문제였던 실제 질문("나의 미수령금", "나 돈 잘못보냈는디 어캄쇼" 같이 짧고 모호한 질문)으로 다시 테스트해보니, 세 가지를 다 적용해도 여전히:

- 근거에 없는 서류명이나 전화번호를 지어내고
- 심지어 우리가 준 적도 없는 URL(`https://www.kdic.or.kr/vaup/...`)을 새로 만들어냈다.

질문이 짧고 few-shot 예시와 주제가 비슷할수록 이 현상이 심했다. 프롬프트 지시문을 아무리 강하게 써도 LLM이 지시문보다 few-shot의 "내용"을 더 강하게 따라가는 경향이 남아있어서, **프롬프트 문구만으로는 근본적으로 막기 어렵다**고 결론 내렸다.

### 실제 해결책: URL을 LLM에게 아예 안 보여준다

"LLM이 URL을 안 틀리고 잘 쓰게 만들기"가 아니라, **"LLM이 URL을 아예 쓸 일이 없게 만들기"**로 접근했다.

- `build_informational_prompt()` / `build_civil_petition_prompt()`: 프롬프트에서 서류·링크·출처 URL을 완전히 뺐다. LLM은 이제 "절차 설명"이나 "근거 기반 답변 본문" 텍스트만 쓴다.
- `SYSTEM_INSTRUCTION`에 "URL·웹사이트 주소·전화번호를 답변에 직접 쓰지 마세요. 그 부분은 시스템이 별도로 붙여줍니다"라는 원칙을 추가했다.
- `assemble_informational_answer()` / `assemble_civil_petition_answer()` (신규 함수): LLM이 쓴 답변 텍스트 뒤에, `citation.py`/`civil_petition.py`가 검색 결과에서 이미 조회해둔 **진짜** documents/links/citations를 그대로 붙인다. 이 부분은 LLM이 전혀 관여하지 않는 100% 결정론적 코드라서, 애초에 지어낼 수 있는 여지가 없다.
- `pipeline.py`: LLM 호출 직후 위 assemble 함수로 최종 답변을 조립하도록 흐름을 바꿨다.

### 곁들여 고친 것 — 다운로드 URL 자체가 깨져있던 문제

서류 URL을 들여다보다가 별개의 문제도 발견했다. `civil_petition.py`가 넘겨주던 다운로드 링크(`resolved_url`)가 애초에 작동하지 않는 링크였다. 코퍼스 전체 103개 서식 다운로드 항목을 확인해보니 `resolved_url`이 딱 3개의 URL로만 겹쳤다 — 이건 실제 파일 링크가 아니라 자바스크립트 다운로드 버튼이 공통으로 쓰는 POST 전용 서블릿 주소였다. 실제 파일 구분은 암호화된 파라미터를 POST 본문으로 같이 보내야만 되는데 우리는 그 값을 안 보내고 있어서, 클릭해도 다운로드가 안 되는 깨진 링크를 안내하고 있었던 것이다. `resolved_url` 대신 다운로드 버튼이 실제로 있는 페이지 주소(`page_url`)를 안내하도록 수정했다.

### 검증 결과

문제였던 질문 2개와 정상 케이스 2개, 총 4개 질문으로 재확인했다. 4개 전부 URL 관련 할루시네이션이 완전히 사라졌고, 백엔드가 붙인 링크는 항상 실제 검색 결과와 정확히 일치했다.

| 질문 | 결과 |
| --- | --- |
| 나의 미수령금 | URL을 지어내던 문제 해결 - 신청 페이지 5건이 실제 링크로 정확히 표시됨 |
| 나 돈 잘못보냈는디 어캄쇼 | 깨끗한 절차 설명 + 정확한 링크 5건 |
| 위임장 양식 (회귀 확인) | 서류 12건 + 링크 2건 정확히 붙음, 이상 없음 |
| 예금보호한도 (회귀 확인) | 출처 2건 정확히 붙음, 이상 없음 |

### 남은 사소한 여지

LLM이 절차 설명 안에서 가끔 "신분증과 도장" 같은 일반적인 표현을 근거에 정확히 없어도 관습적으로 언급하는 경우가 있었다(예: 미수령금 답변). 다만 이건 URL이나 구체적인 서류명을 지어내는 것보다는 훨씬 가벼운 문제라, 지금은 별도 이슈로 남겨두고 범위 밖으로 둔다.

## 이슈 3. [NO_SOURCE] 마커 신뢰성 — 복합 질문(Multi-Query) 작업 중 발견, 그 작업이 원인은 아님

### 배경

`src/query_decomposer.py`(복합 질문을 하위 질문으로 분해) + `pipeline.py`의 멀티쿼리 연결(2026-07-30,
`_answer_one()`/`USE_QUERY_DECOMPOSITION`) 작업 도중, 실사용자가 실제 앱에서 다음과 같은 뒤섞인
질문을 테스트했다:

> "예금에 대해서 잘몰라 그리고 내가 친구한테 돈을 갚으려고 송금을 했는데 잘못 송금했는데 이거에
> 대해 방법이 있어? 그리고 돈을 안보내게되면 고소를 당한다는 말이 있던데 진짜야?"

분해기가 이걸 "잘못 송금한 돈 돌려받는 방법"(착오송금, KDIC 업무 맞음)과 "친구에게 돈을 갚지
않으면 고소를 당하나요?"(개인 간 채무불이행 — KDIC 업무 범위 완전히 밖) 두 개로 정확히 쪼갰다.
첫 번째는 정상 답변됐지만, 두 번째(스코프 밖) 하위 질문에서 **LLM이 완전히 지어낸 법률 상식
답변("형사상 사기죄 인정되기 어렵다" 등 — 코퍼스 어디에도 없는 내용)을 내놓았고, 거기에 무관한
KDIC 출처 3~4건이 마치 근거인 것처럼 그대로 붙어 나왔다.**

### 최초 우려와 실제 검증

멀티쿼리 분해가 이 환각을 유발한 것처럼 보였다 — 원래 한 덩어리 질문 속에 묻혀 있던 곁가지
질문을 분해기가 독립된 질문으로 꺼내면서 새로 노출된 문제처럼 보였기 때문이다. 하지만 실제로
원인을 특정하기 위해 **같은 질문 문장을 `USE_QUERY_DECOMPOSITION=True`/`False` 두 조건에서 각각
3회씩 반복 실행**해 비교했다(질문: "친구에게 돈을 갚지 않으면 고소를 당하나요?" 단독).

| 조건 | 반복 | 결과 |
| --- | --- | --- |
| 디컴포지션 On | 3회 | 3/3 정상 거절("알 수 없습니다") |
| 디컴포지션 Off | 3회 | 3/3 정상 거절("알 수 없습니다") |

처음 봤던 완전한 내용 환각은 6회 추가 실행 중 단 한 번도 재현되지 않았다 — `temperature=0.2`
(`llm_client.py`)에 따른 낮은 확률의 우연으로 판단된다. **디컴포지션 On/Off 두 조건의 결과가
동일했으므로, 멀티쿼리 작업이 이 환각의 원인이라는 근거는 없다.**

### 실제로 발견된 것 — 다른, 더 확실한 버그 (6/6 재현, 디컴포지션과 무관)

위 6회 실행 전부에서 **답변 본문은 매번 올바르게 거절**했지만("친구에게 돈을 갚지 않았을 때의
법적 결과에 대해서는 알 수 없습니다... 답변을 제공할 수 없습니다"), **그 아래에 무관한 KDIC
출처 4건이 매번 그대로 붙었다.** 두 조건(On/Off) 모두 100% 동일하게 재현됐다.

원인은 `prompt_builder.py`의 `NO_SOURCE_MARKER` 방식에 있다: `assemble_informational_answer()`는
LLM 응답이 정확히 `[NO_SOURCE]` 토큰으로 시작할 때만 출처 첨부를 생략한다(`_strip_no_source_marker()`).
그런데 LLM은 **내용상으로는 올바르게 거절문을 쓰면서도, 정해진 마커 토큰은 안 붙이는 경우가
있다** — 이번 6회 실행이 그 경우였다. 마커가 없으니 시스템은 "근거를 실제로 썼다"고 오판해
무관한 출처를 그대로 붙였다.

### 결론 — 멀티쿼리 작업의 버그가 아니다

- 이 마커 실패는 `prompt_builder.py`(파이프라인의 모든 답변 생성이 공유하는 코드)에 있는
  **기존 문제**이며, `USE_QUERY_DECOMPOSITION` On/Off와 무관하게 동일하게 재현된다.
- 멀티쿼리 분해 자체는 이 버그를 만들지 않았다. 다만 한 사용자 턴이 하위 질문 개수만큼
  독립된 검색·답변 시도로 늘어나므로, 이 기존 취약점(그리고 낮은 확률의 내용 환각)에
  **노출되는 횟수 자체는 늘어난다** — 뒤섞인 질문 속 곁가지 스코프 밖 질문을 분해기가 성실하게
  독립 질문으로 꺼내 그 자체의 검색·답변 시도를 부여하기 때문이다.

### 해결 (2026-07-30)

`prompt_builder.py`의 마커 방식을 **조건부 지시("근거 미사용일 때만 [NO_SOURCE]를 붙여라")에서
강제 이지선다("항상 [SOURCE_USED] 또는 [NO_SOURCE] 둘 중 하나로 시작하라")로 바꿨다.** 조건부
지시는 LLM이 마커 자체를 빼먹을 여지가 있었지만, 둘 중 하나를 반드시 고르게 하면 누락 여지가
줄어든다는 가설이었다. ("알 수 없습니다"류 표현을 휴리스틱으로 잡는 방식은 이 프로젝트가 이미
"표현이 다양해 계속 샌다"고 폐기한 접근(이슈 2 후속 참고)이라 다시 쓰지 않았다.)

**1차 수정에서 새 버그 발견 → 즉시 재수정**: 이지선다로 바꾼 뒤 검증하다가, LLM이 지시한 정확한
밑줄 표기 `[SOURCE_USED]` 대신 **띄어쓰기로 `[SOURCE USED]`**라고 쓰는 사례를 발견했다. 완전
일치 문자열 비교(`text.startswith(...)`)로는 이 변형을 못 잡아 (a) 마커 텍스트가 그대로 답변에
노출되고 (b) 근거_사용_여부까지 `False`로 잘못 떨어져 **정상 답변인데도 출처가 통째로 안 붙는
회귀**가 났다. `_strip_no_source_marker()`를 정규식(`_MARKER_RE`, 밑줄/띄어쓰기·대소문자 허용)
기반으로 다시 고쳐 해결했다 — 여전히 고정된 두 토큰만 인식하는 결정론적 매칭이고, 자유 문구를
추측하는 방식이 아니다.

**검증**: 원래 실패했던 스코프 밖 질문 3회 재실행 — 마커 노출 없이 깔끔하게 거절, 무관한 출처
없음(정상). 정상 informational·civil_petition 질문도 각각 재실행해 회귀 없음(출처/서류·신청
페이지 섹션 정상 첨부) 확인.

## 이슈 4. 하위 답변 출처 소실 — "중복 출처 제거" 누적 집합 버그 (2026-07-30 해결)

### 배경

멀티쿼리 분해(`USE_QUERY_DECOMPOSITION`)로 복합 질문을 하위 질문 2~3개로 나눠 답할 때,
"같은 문서가 여러 하위 답변에 반복해서 인용되면 지저분하니 두 번째부터는 출처를 붙이지
말자"는 중복 제거 로직이 `_answer_one()`에 있었다 — 하위 답변끼리 `seen_pages`(출처 페이지)·
`seen_urls`(서류/신청 페이지 링크) 누적 집합을 공유하며, 앞 하위 답변에 나온 페이지/링크를
뒤 하위 답변의 목록에서 걸러내는 방식이었다.

### 문제

이 누적 집합에 도장을 찍는 기준이 **"출처를 실제로 답변에 붙였는가"가 아니라 "검색됐는가"**였다.
`seen_pages.update()`가 `[NO_SOURCE]`/`[SOURCE_USED]` 마커 판정과 무관하게, 검색으로 딸려온
페이지 전부에 무조건 찍혔다.

검색은 관련도 임계값 없이 항상 top-k를 반환하므로(이슈 3 참고), 업무 밖 하위 질문에도 무관한
페이지 5개가 항상 검색된다. 그래서 다음 순서로 출처가 소실됐다:

1. 하위 질문 ①이 업무 밖("돈 안 갚으면 고소당하나요?") → LLM이 `[NO_SOURCE]`로 올바르게 거절
   → 출처 미부착(여기까지 정상) → **그런데 검색됐던 페이지 5개에 '이미 인용됨' 도장이 찍힘**
2. 하위 질문 ②("잘못 보낸 돈 어떻게 돌려받나요?")가 그중 한 페이지를 **진짜 근거로 답변**
   → "①에서 이미 인용했다"고 오판해 출처 목록에서 제거 → **문서로 답했는데 출처 0건인
   답변이 출고**

이 프로젝트가 가장 피하려는 "근거 표시 없는 답변"(민원 리스크)이 정확히 재현되는 버그다.
업무 밖 하위 질문이 앞 순서일 때뿐 아니라, 업무 내 질문이라도 검색이 빗나가 `[NO_SOURCE]`
거절이 나온 뒤 다음 하위 답변이 같은 페이지를 쓰는 경우에도 동일하게 터진다.

### 원인 분석 — 세 겹

1. **직접 원인**: 도장을 검색 결과에 찍었다. "검색됨"과 "인용됨"은 이 파이프라인에서 서로
   다른 개념인데(임계값 없는 검색은 공짜로 항상 발생, 인용은 마커 판정 후 결정), 그 구분을
   무시했다.
2. **구조적 원인**: 하위 답변들이 누적 집합을 공유하면서 서로 의존하게 됐다 — ②의 출처가
   "①이 뭘 먼저 인용했나"에 따라 달라져, 하위 질문 순서만 바뀌어도 결과가 바뀐다.
3. **유래의 문제**: 이 규칙의 근거로 코드 주석이 `log/0729.md 3항`을 인용했는데, log는 AI
   생성 스탠드업 기록이라 요구사항의 원천이 아니다. 팀이 실제로 합의한
   요구인지 확인되지 않은 규칙이 코드에 들어와 있었다.

멀티쿼리 분해기(`query_decomposer.py`) 자체는 원인이 아니다 — 재현 시나리오에서 분해는
정확했고(서로 다른 두 요구를 옳게 쪼갬), 분해가 완벽해도 이 버그는 그대로 터진다. intent
분류도 무관하다(informational/civil_petition 이지선다라 업무 밖 라벨 자체가 없고, 도장은
양쪽 분기 모두에서 마커 판정을 무시하고 찍혔다).

### 해결 — 중복 제거 로직 자체를 삭제

도장을 "제대로 찍게" 고치는 대신(마커 판정 결과를 도장 코드까지 전달 — 코드가 늘고 순서
의존성은 남음), **누적 집합 로직을 통째로 제거**했다. `_answer_one()`의 시그니처에서
`seen_pages`/`seen_urls` 파라미터, 걸러내는 필터 2곳, 도장 찍는 `update()` 3줄, 집합 생성과
호출부 전달을 모두 삭제 — 각 하위 답변이 자기 검색 결과에서만 출처를 만든다.

삭제를 택한 근거:

- 이 규칙이 지키려던 가치("같은 링크 두 번 보이면 지저분")가 지킬 만한 것이 아니다. 같은
  문서가 하위 답변 ①·②의 근거라면 각각에 보이는 것이 사실 그대로이고, 사용자에게 오히려
  "이 답의 근거는 이것"이 명확해진다.
- 하위 답변 간 상태 공유라는 구조 자체가 사라져, 순서 의존성 계열 버그의 재발 경로가 닫힌다.
- 규칙의 유래가 팀 합의가 아니었다(위 3번).

### 사이드이펙트 검토 — 의도한 변화 하나뿐

- **단일 질문 경로는 출력 불변**: 누적 집합은 요청마다 새로 만들어졌고 단일 경로에서는 항상
  빈 채로 통과했다(안 거르던 필터 삭제 = 동작 동일).
- **LLM 답변 본문 불변**: 출처는 LLM 호출 뒤 결정론적으로 붙이는 것이고 LLM은 URL을 아예
  보지 않으므로(이슈 2 후속), 이 로직은 LLM 입력에 관여한 적이 없다.
- **한 답변 안의 페이지 중복 제거는 유지**: 같은 페이지의 청크 여러 개가 검색됐을 때 출처
  1줄로 합치는 로직은 `citation.format_all_citations()`에 있고 건드리지 않았다.
- **외부 호출자 영향 없음**: 파이프라인 밖에서 쓰는 것은 `app.py`의 `_rag_answer_traced(query)`
  뿐이고 시그니처 불변. 시그니처가 바뀐 `_answer_one()`은 `pipeline.py` 내부 전용.
- **유일한 가시적 변화**: 복합 질문에서 같은 문서를 두 하위 답변이 모두 근거로 쓰면 링크가
  양쪽에 표시된다 — 이것이 수리 목표다.

### 검증

AI 호출 없이 협력자(분해기·분류기·검색·LLM)를 가짜로 대체하고 조립 로직만 실행해 확인:

| 시나리오 | 결과 |
| --- | --- |
| 업무 밖 하위 질문(①, `[NO_SOURCE]`) 선행 + 업무 내(②, `[SOURCE_USED]`)가 같은 페이지 검색 | ① 출처 미부착(정상), ② 출처 정상 부착 — **소실 없음** |
| 단일 질문 경로(`[SOURCE_USED]`) | 출처 정상 부착, 회귀 없음 |

`_answer_one()` docstring에 "하위 답변 간 출처 중복 제거를 다시 도입하지 말 것"과 이 문서
참조를 남겨, 같은 로직이 재도입되는 것을 막았다.

### 남은 것 (별도 논의)

- 하위 답변 출처 소실과 마커 사고(이슈 3)를 자동으로 잡을 빠른 검사(AI 없이 초 단위 실행)가
  아직 없다 — 지금까지 전부 앱을 눈으로 확인해 발견했다.
- 범위 밖 질문의 방어선이 파이프라인 맨 끝의 마커 하나뿐인 구조(임계값 없는 검색 + 업무 밖
  라벨 없는 intent 분류)는 별도의 설계 논의 대상이다.

## 이슈 5. 마커 내용 오표기 → 자기보고 폐기, source_verifier 도입 (2026-07-30 해결)

### 문제

이슈 3에서 마커의 **형식** 문제(누락·띄어쓰기 변형)는 잡았지만, **내용**이 틀리는 문제가
남아 있었다: LLM이 착오송금 근거 청크로 절차를 상세히 답해놓고 첫 줄에 `[NO_SOURCE]`를
표기 — 검색은 정확했고(top-5 전부 착오송금 페이지) 답변 내용도 청크에 그대로 있는데,
자기보고만 틀려서 출처가 통째로 생략됐다.

근거 청크를 고정하고 프롬프트 가설 7종을 각 5회 반복(총 35회 HCX 호출)으로 통제 검증했지만
**전부 실패**했다:

| 가설 | 실험 | NO_SOURCE 오표기 |
| --- | --- | --- |
| '친구에게' 개인사 프레이밍 탓 | 중립 표현("착오송금한 돈을…")으로 교체 | 5/5 |
| few-shot 마지막 거절 예시 탓 | 그 예시 제거 | 5/5 |
| few-shot이 예금보험금 일색 탓 | 착오송금 `[SOURCE_USED]` 예시 추가(testset 기반) | 5/5 |
| 마커 규칙의 이중 기준(질문 관련성+사용 여부) 탓 | "답변에 썼는가" 단일 기준으로 교체 | 5/5 |
| 질문 직전 리마인더 부재 탓 | informational에도 civil_petition식 리마인더 추가 | 4/5 |
| 청크의 UI 잔해("열기·퀵메뉴") 탓 | 깨끗한 절차 청크 1개만 제공 | 5/5 |
| (기준선) | 분해기가 만든 원래 질문 그대로 | 5/5 |

같은 프롬프트로 예금보험금 주제는 마커가 안정적으로 맞았다 — 오표기는 주제 의존적이고
원인은 불투명해, 자기보고의 정확성은 프롬프트로 통제 불가능하다는 게 실측 결론이다.

학습용 라벨 데이터 107건 실측에서 마커는 **근거를 실제로 쓴 답변 61건 중 33건(54%)에서
출처를 잘못 생략**하고 있었다 — 간헐 사고가 아니라 상시 대량 손실이었다. 라벨 수집 중
`[ SOURCE USED ]`(괄호 안 공백)라는 새 형식 변형도 또 관측됐다.

### 원인 — 자기보고 방식 자체의 한계

"근거를 썼는지"를 LLM에게 묻는 구조는 형식을 아무리 강제해도 판단의 정확성을 보장할 수
없다(주제 의존적으로 틀리며 원인 불투명). 업계 프로덕션(AWS Bedrock 가드레일, Google
Vertex Check Grounding, Azure Groundedness)은 전부 생성 모델의 자기보고를 쓰지 않고
**생성 후 별도 판정(작은 모델/규칙) + 임계값** 구조를 쓴다. 학계 표준(ALCE/AIS)도 동일
— "생성자를 믿지 말고 사후 검증하라".

### 해결 — 생성 후 결정론적 판정 (`source_verifier.py`)

마커를 프롬프트·파싱에서 완전히 제거하고, 답변이 도착한 뒤 코드가 판정한다:

- **특징 3종**: 답변 형태소 TF-IDF(거절·인사 문체는 정형적 — 고정 문구 매칭이 아니라
  학습 가중치라 표현 변형에 견딤) + 내용어 근거 겹침률 + bge-m3-ko(`retrieval.py`의
  `DEFAULT_DENSE_MODEL` 재사용) 코사인. 모두 파이프라인이
  이미 로딩한 자원(Kiwi, bge-m3)만 사용 — 새 의존성·추가 API 호출 0.
- **모델 저장은 sklearn pickle이 아니라 JSON**(가중치+임계값): sklearn 버전이 다르면
  pickle 로드가 깨지는 문제가 intent 분류기에서 실제 발생("idf vector is not fitted",
  아나콘다 1.4.2 vs 학습 1.6.1). TF-IDF 변환을 수식으로 재구현했고,
  `train_source_verifier.py`가 학습 때마다 sklearn 확률과의 일치를 assert로 검증한다.
- **임계값 정책**: '근거 쓴 답변의 출처 누락 0' 우선(무관한 출처 부착보다 출처 누락이
  더 나쁨 — 출처 표시 필수 원칙). 안전 마진 0.7~1.0 스윕 결과 누락은 전 구간 동일해
  차단율이 더 좋은 0.9 채택.
- **학습 데이터**: `data/source_verifier/labels.jsonl` 107건(테스트셋 층화 샘플 + 스코프
  밖 전수 + 인사말, 실제 파이프라인 실행 답변을 사람이 라벨링). 재학습:
  `python3 src/train_source_verifier.py`.

### 결과 (같은 라벨 107건 기준)

| | 근거사용 답변의 출처 누락 (위험 축) | 미사용(거절·인사) 차단 (미관 축) |
| --- | --- | --- |
| 마커(기존) | **33/61 (54%)** | 46/46 |
| source_verifier (5-fold CV) | **1/61 (2%)** | 28/46 (61%) |

위험 축 실패를 54%→2%로 줄이는 대신 미관 축(거절문에 무관한 출처가 붙는 것)을 일부
양보하는 교환이다. E2E: 오표기되던 착오송금 질문에 출처 5건 정상 부착, 인사말엔 미부착.

### 알려진 한계와 다음 단계

- 경계 거절문 일부("제공된 자료에서는 예금보험금 정보만 있어 알 수 없습니다"처럼 도메인
  명사가 많고 긴 거절)는 여전히 통과해 무관한 출처가 붙는다 — 문체·겹침 특징의 한계 지점.
  개선 경로는 **문장별 NLI 검증**(학계 표준 ALCE 패턴): 답변을 문장 단위로 쪼개 각 문장이
  근거 청크에 함의(entailment)되는지 소형 NLI 모델로 판정한다. 후보 모델은
  `MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7`(279M — 한국어는 이 `-2mil7`
  변형만 학습 데이터에 포함, 무인 `-xnli` 변형은 한국어 미지원) 또는
  `klue/roberta-small`(68M)+KorNLI(94만 쌍) 파인튜닝이며, CPU에서는 ONNX INT8
  양자화(리랭커 재도입 리서치 때 정리한 속도 스택)로 수백 ms 수준을 기대할 수 있다.
  실패 사례는 labels.jsonl에 추가하고 재학습하면 반영된다(프롬프트를 고치는 게 아니라
  데이터를 늘리는 구조).
- 회귀 방지: `python3 tests/test_source_pipeline.py` (AI 호출 없이 수 초) — 판정 4픽스처
  + 출처 조립 + 이슈 4 하위 답변 독립성. **파이프라인 코드를 고치면 커밋 전에 돌릴 것.**
  (2026-08-03 롤백으로 구성이 바뀌었다 — 아래 "이슈 5 후속" 참고.)

| 파일 | 변경 |
| --- | --- |
| `prompt_builder.py` | `SYSTEM_INSTRUCTION` 규칙 7(마커 강제 이지선다) 부활, few-shot 5개 답변에 마커 재삽입, `_MARKER_RE`·`_strip_no_source_marker()` 복원, `assemble_*()` 3인자 → 2인자 |
| `pipeline.py` | `source_verifier` import·`source_verification` 타이밍 단계 제거, 2인자 조립 호출 |

`query_classifier.py`(intent 분류)와 검색·분해기 쪽은 건드리지 않았다 — 이번 롤백은
멀티쿼리 답변 조립 경로 한정이다. 이슈 4(하위 답변 출처 소실)의 수정은 **그대로 유지**한다.
즉 `seen_pages`/`seen_urls` 누적 집합은 되살리지 않았고, 하위 답변끼리 출처는 여전히 독립이다.

### 삭제한 것

- `src/source_verifier.py`, `src/train_source_verifier.py`
- `data/source_verifier/labels.jsonl`(라벨 107건), `data/source_verifier/model.json`

마커가 판정을 도로 가져가면서 호출부가 하나도 남지 않았다. 리랭커(`USE_RERANKER`)처럼
플래그로 껐다 켜는 구조가 아니라 파이프라인 배선 자체가 사라지는 것이라, 코드를 남겨두지
않고 지웠다. 되살릴 필요가 생기면 이 커밋 이전 이력이나 태그 `semi_document-freeze`에서
복원하면 된다.

### 다시 떠안게 된 알려진 위험

이슈 5에서 실측한 마커의 실패는 그대로 되살아난다. 감수하고 내린 결정이며, 이 문서를
읽는 사람이 "몰랐다"가 되지 않도록 수치를 다시 적어둔다:

| | 근거사용 답변의 출처 누락 (위험 축) | 미사용(거절·인사) 차단 (미관 축) |
| --- | --- | --- |
| **마커 (되돌아간 방식)** | **33/61 (54%)** | 46/46 |
| source_verifier (삭제됨) | 1/61 (2%) | 28/46 (61%) |

- 근거를 실제로 쓴 답변의 **절반 이상에서 출처가 통째로 빠질 수 있다**. 이는 '출처 표시
  필수' 원칙과 정면으로 충돌하는 축이다.
- 프롬프트로는 못 고친다는 게 이슈 5의 통제 실험 결론이다(가설 7종 × 5회 = 35회 HCX 호출,
  전부 실패). 오표기는 주제 의존적이고(예금보험금은 안정, 착오송금은 5/5 오표기) 원인이
  불투명하다. **같은 프롬프트 튜닝을 다시 시도하는 건 이미 한 번 실패한 경로다.**
- 마커 형식 변형(`[SOURCE USED]` 띄어쓰기, `[ SOURCE USED ]` 괄호 안 공백, 소문자)은
  `_MARKER_RE`가 밑줄/띄어쓰기·대소문자까지만 흡수한다. 그 밖의 변형이 오면 마커가 없는
  것으로 보고 **안전한 쪽(출처 미첨부)** 으로 처리한다.
- 멀티쿼리는 하위 질문마다 답변을 따로 생성하므로, 한 턴에 이 실패율이 하위 질문 수만큼
  독립적으로 노출된다.

### 회귀 방지 스크립트 변경

`tests/test_source_pipeline.py`가 3종으로 바뀌었다(기존 4종에서 `test_verifier()` 제거 —
대상 모듈이 사라졌다). 남은 검사는 다음과 같고, source_verifier가 빠지면서 bge-m3 로딩이
없어져 수 초 이내로 끝난다.

1. `test_marker_parsing()` — 정상 마커 2종 + 재현됐던 띄어쓰기 변형 + 소문자 변형
   + 마커 없음(안전 폴백). 마커 텍스트가 본문에 노출되지 않는지까지 확인.
2. `test_assemble()` — 마커에 따른 출처 부착/미부착.
3. `test_subanswer_independence()` — 이슈 4 회귀. `used_source` 패치 대신 마커가 붙은
   답변을 주입하도록 바꿨다.

부수적으로, 완료 메시지의 em-dash가 Windows cp949 콘솔에서 `UnicodeEncodeError`를 내
**검사가 다 통과하고도 비정상 종료(exit 1)** 하던 문제를 고쳤다.

### 남은 것 — intent 문제가 아니라 이 롤백이 남긴 잔재

`query_classifier.py`의 `tokenize_intent()`(Kiwi 형태소 토크나이저)가 고아가 됐다. **intent
분류 동작과는 무관하다** — 이름 때문에 헷갈리지만 현재 `classify_intent()`(OpenAI structured
output)는 이 함수를 쓰지 않는다. 원래 옛 intent 분류기(TF-IDF)의 전처리였고, intent가
OpenAI로 교체된 뒤에도 남아 있던 이유는 `source_verifier`·`train_source_verifier`가
재사용했기 때문인데(해당 주석에 명시), 이번 롤백으로 그 둘을 지우면서 호출부가 0이 됐다.

지우지 않고 둔다. 기능상 차이가 없는 죽은 함수 십수 줄인 반면, `query_classifier.py`는
intent 작업이 진행 중인 파일이라 건드리면 머지 충돌만 생긴다. `kiwipiepy` 의존성도
`retrieval.py`(BM25 토큰화)가 계속 쓰므로 제거해도 줄지 않는다. intent 쪽에서 이 파일을
다음에 손볼 때 같이 정리하면 된다.

## 이슈 5 후속 2 — 롤백이 남긴 출처 누락 실제로 수리 (2026-08-03)

위 롤백에서 "감수한다"고 적어둔 출처 누락을, 마커 방식(판정은 LLM이 한다)을 유지한 채
수리했다. 두 가지를 고쳤는데 **원인이 서로 다르고, 그중 하나는 이 문서가 지금까지
기록해온 설명과 달랐다.**

### (1) 정규식이 관측된 변형을 못 잡고 있었다

롤백이 되돌린 `_MARKER_RE`는 `^\[(SOURCE[_ ]USED|NO[_ ]SOURCE)\]` 였다. `[` 바로 뒤에
단어가 오는 형태만 매치하므로 **대괄호 안쪽 공백(`[ SOURCE USED ]`)을 못 먹는다.**
그런데 이 변형은 이슈 5 라벨 수집 중 실제로 관측돼 이 문서에 적혀 있던 것이다 —
관측해 놓고 대응이 안 들어간 채로 롤백된 셈이다.

미매치는 `(원문, False)`를 반환하므로 증상이 두 겹이었다: 출처가 통째로 빠지고,
`[ SOURCE USED ]` 문자열이 사용자 화면에 그대로 노출된다(2026-07-30에 한 번 고쳤던
증상과 동일). 실측:

| 입력 | 수정 전 | 수정 후 |
| --- | --- | --- |
| `[SOURCE_USED]` / `[NO_SOURCE]` / `[SOURCE USED]` / 소문자 | 정상 | 정상 |
| `[ SOURCE USED ]` | **False + 마커 노출** | True, 본문 깨끗 |
| `[ NO_SOURCE ]` | False + **마커 노출** | False, 본문 깨끗 |
| `**[SOURCE_USED]**` | **False + 마커 노출** | True, 본문 깨끗 |
| `[SOURCE_USED]:` | True, 본문이 `:`로 시작 | True, 본문 깨끗 |

인식 대상은 여전히 **고정된 두 토큰뿐**이다. 표기 흔들림(괄호 안 공백·볼드·콜론)만
흡수했을 뿐, "여러 표현을 추측해 거른다"는 폐기된 접근으로 넘어가지 않았다.
회귀 검사에 `[ SOURCE USED ]` 케이스가 빠져 있어서 이 결함이 3종 통과를 통과했다 —
누락 변형들을 `tests/test_source_pipeline.py`에 추가했다.

### (2) 착오송금 실패의 진짜 원인은 오표기가 아니라 마커 '누락'이었다

이 문서는 착오송금 실패를 **`[NO_SOURCE]` 오표기**(근거를 써놓고 안 썼다고 잘못
표기)로 기록해왔다. 2026-08-03 실제 파이프라인 응답을 그대로 찍어보니 **아니었다.**

```
'착오송금을 하셨다면 다음의 절차를 따라 예금보험공사에 착오송금 반환 지원을 …'
SOURCE_USED 포함? False | NO_SOURCE 포함? False
```

응답 **어디에도 마커가 없다.** 답변 내용은 코퍼스 그대로다(반환지원 제도, 1년 이내,
5만원~1억원). 즉 LLM은 근거를 정확히 쓰고도 마커 자체를 통째로 빠뜨렸고, 미매치
폴백(`False`)이 출처를 지운 것이다.

**이슈 3에서 "조건부 지시 → 강제 이지선다"로 마커 누락을 잡았다고 판단했는데, 그
누락이 착오송금 주제에서는 그대로 살아 있다.** 이슈 5의 "주제 의존적으로 틀린다"는
관찰은 맞았지만, 틀리는 방식이 오표기가 아니라 누락이었다. 이 문서를 읽고 오표기를
전제로 대책을 세우면 헛다리를 짚게 되므로 여기 바로잡아 둔다.

### 수리 — 틀리는 방향에만 두 번째 의견을 붙인다 (`source_check.py`)

프롬프트를 다시 손대는 길은 이슈 5가 35회 통제 실험으로 이미 막았다. 그래서 프롬프트가
아니라 **판정 시점을 생성과 분리**했다: 답변이 다 나온 뒤, 별도 호출로 "이 답변이 이
자료를 썼는가"만 묻는다(YES/NO 한 단어). 생성 부담이 없는 순수 텍스트 대조라 자기평가와
성격이 다르고, 판정 주체는 여전히 LLM이다(2026-08-03 팀 결정).

**근거 사용으로 판정된 답변은 절대 재확인하지 않는다.** 라벨 107건에서 마커의 실패가
한 방향뿐이었기 때문이다:

| 마커가 말한 것 | 건수 | 오판 |
| --- | --- | --- |
| `[SOURCE_USED]` | 28 | **0건** |
| `[NO_SOURCE]`(또는 마커 없음) | 79 | **33건 (42%)** |

맞고 있는 축(거절·인사에 무관한 출처가 안 붙는 것, 46/46)을 건드리면 그 축이 무너진다.
그래서 `_resolve_used_source()`는 판정이 `False`일 때만 콜백을 부른다. 호출 실패·파싱
실패는 전부 `False`로 떨어져 **이 기능이 죽어도 켜기 전과 동작이 정확히 같다.**

### 검증 (착오송금, 분해기 Off, 각 3회)

| 조건 | 출처 부착 | recheck 호출 |
| --- | --- | --- |
| `USE_SOURCE_RECHECK=False` | **0/3** | 0 |
| `USE_SOURCE_RECHECK=True` | **3/3** | 3 (전부 '썼다') |

지연: recheck 호출 자체는 **0.80초**(warm). 같은 실행에서 생성 호출이 3.4초였으니
답변 하나당 20% 남짓 늘어난다 — 한 토큰만 뱉는 판정이라 생성보다 훨씬 싸다.

**한계**: 3회 반복 1주제라 표본이 매우 작다. 특히 "마커 누락"이 착오송금 외 어느
주제에서 얼마나 흔한지 아직 안 쟀다 — 이번 3회에서는 recheck가 100% 발동했으므로,
"추가 호출은 `[NO_SOURCE]` 답변에만 발생한다"는 비용 추정이 주제에 따라 낙관적일 수
있다. 라벨 107건 규모의 재측정은 별도 과제로 남는다.

### 폴백 방향에 대한 미해결 논점

`_strip_no_source_marker()` 독스트링은 "없는 출처를 안 보여주는 게, 무관한 출처를
잘못 붙이는 것보다 낫다"고 적고 있고, 이슈 5의 임계값 정책은 정반대로 "무관한 출처
부착보다 출처 누락이 더 나쁨(출처 표시 필수 원칙)"이라고 적고 있다. 둘 다 현재 트리에
살아 있고 코드는 앞쪽을 따른다. 이번 수리는 recheck로 누락을 구제해 충돌의 실질적
피해를 줄였을 뿐, **어느 쪽이 팀의 현재 원칙인지는 정리되지 않았다.** 마커도 없고
recheck도 실패했을 때 어디로 떨어질지가 이 판단에 걸려 있다.

## 이슈 6. 분해 프롬프트의 형식 부스러기가 하위 질문으로 유입 (2026-08-04 해결)

### 문제

복합 질문 분해가 만든 하위 질문 목록에 `출력:` 같은 무의미한 줄이 섞여 들어가, 최종 답변에
"제공해주신 자료에 정보가 없어 답변 못 드립니다"류 거절 문단이 함께 붙어 나오는 것이 실사용
중 발견됐다. 사용자가 묻지도 않은 질문에 대한 거절이 답변 안에 끼어 있는 모양이 된다.

### 원인 — 프롬프트 형식과 파싱 규칙이 맞물린 자리

`_build_prompt()`(`query_decomposer.py:87-93`)가 few-shot을 `질문: …` / `출력: …` 형식으로
넘긴다. 드물게 LLM이 실제 하위 질문 대신 **이 틀 자체**(`질문:` · `출력:` 한 줄)를 그대로 따라
써서 응답에 섞어 보낸다.

`decompose_query()`는 JSON을 쓰지 않고 **줄바꿈만 보고 나눈다**. 이건 실수가 아니라 설계다 —
출력에서 번호·불릿·따옴표·설명문구를 금지하는 대신 파싱을 줄바꿈 하나로 고정했다
(`docs/multiquery_decomposition.md` 3절 규칙 5). 그래서 부스러기 줄이 그대로 하위 질문 하나로
취급돼 `pipeline.py`로 넘어가고, `_answer_one()`이 `출력:`을 진짜 질문처럼 검색·생성에 태운다.
근거가 나올 리 없으니 거절 답변이 만들어지고, 그것이 정상 하위 답변들과 함께 결정론적으로
이어붙여져(`"\n\n".join(...)`) 사용자에게 나간다.

즉 **분해기의 판단 품질 문제가 아니라 출력 형식과 파싱 계약이 어긋난 문제**다. 프롬프트를
고쳐 "틀을 따라 쓰지 마라"고 지시하는 길은 이 저장소가 이미 여러 번 실패한 접근이므로
(이슈 2 후속·이슈 5 참고) 택하지 않았다.

### 해결 — 파싱 단계에서 걸러낸다

`query_decomposer.py`에 정규식 하나를 두고, 줄 분리 직후 필터에서 뺀다.

```python
_PROMPT_ARTIFACT_RE = re.compile(r"^(질문|출력)\s*[:：]")

sub_queries = [line.strip() for line in response.strip().splitlines()
               if line.strip() and not _PROMPT_ARTIFACT_RE.match(line.strip())]
return sub_queries if sub_queries else [query]
```

- 인식 대상은 **`질문:`·`출력:` 두 어휘로 시작하는 줄뿐**이다. 전각 콜론(`：`)까지만 흡수하고,
  "거절문처럼 보이는 표현을 추측해 거른다"는 폐기된 접근으로 넘어가지 않았다.
- 필터 결과가 비면 기존 폴백대로 **원본 질문 1개짜리 리스트**로 떨어진다 — 부스러기만 온
  최악의 경우에도 분해 실패가 검색을 막지 않는다.

### 검증

시뮬레이션한 오염 응답으로 필터 동작을 확인하고, 정상 응답(2개로 깨끗이 분해)이 그대로
유지되는 것도 재확인했다(커밋 `78274f1`).

### 한계

- **재현율이 낮아 실제 발생 빈도를 재지 못했다.** 실사용에서 한 번 관측됐고, 직접 재현을
  시도한 5회는 전부 정상이었다. 방어 코드 자체엔 비용이 없어 빈도 측정 없이 넣었다.
- 정상 하위 질문이 우연히 `질문:`·`출력:`으로 시작하면 같이 걸린다. 분해기가 만드는 하위
  질문은 "…무엇인가요?"류 완성 문장이라 실제 위험은 낮다고 판단했지만, 걸러진 사실이 로그에
  남지 않으므로 조용히 사라진다.
- 같은 계열의 다른 부스러기(예: `---` 구분선, 번호 매김)가 나오면 이 정규식은 못 잡는다.
  그때는 어휘를 늘리기보다 프롬프트 형식 자체를 바꾸는 쪽을 먼저 검토할 것.
