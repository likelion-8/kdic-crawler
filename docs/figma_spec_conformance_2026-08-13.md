## 2. 결함 — 심각도순

### 🔴 F-1. 마스킹이 스텁인데 필드 이름은 `*_masked`

- `api/masking.py:31` — `mask_text()`가 입력을 **그대로 반환**한다.
- `admin_logs.py:271,408` — `question_masked` · `answer_masked_preview` · `answer_masked_full`이
  전부 원문이다.
- 기획서 요구: PRD-01 3장 "질문·답변은 마스킹 후 저장(90일)", CM-DF-004 08절.

모듈 주석에 "이번 주 마스킹은 구현하지 않기로 팀에서 정했다"고 적혀 있어 **의도된 미구현**이지만,
필드 이름이 마스킹을 약속하고 있어 AD-005를 보는 관리자는 마스킹된 값이라 믿는다. 저장본도
마스킹돼 있지 않다(`api/rag/conversation.py:25-27` — 저장은 원문, 마스킹은 읽는 쪽 책임으로 이관).

### 🔴 F-2. AD-009에서 저장한 요청 제한이 실제 제한이 아니다

- 화면이 저장하는 값: `ops_policy` 테이블 (`admin_ops.py:177-220`, 기본값 `:77-84` = ip 10/분,
  300/일, burst 3/10초, 세션 30/30분 — **기획서 수치와 정확히 일치**).
- 실제로 걸리는 제한: `api/middleware.py:113` — `settings.rate_limit_per_minute`
  (`api/config.py:64` = **30/분 고정**).
- `ops_policy`를 읽는 코드는 `admin_ops.py`(CRUD) 밖에 **한 곳도 없다**.

즉 관리자가 IP 제한을 10회로 낮춰도 서버는 계속 30회로 돈다. 추가로 일일 300회·burst·세션 단위
제한은 아예 없고, "10분 내 위반 3회 → 10분 임시 차단"도 없다 — `rate_limit_blocks`에
행을 만드는 코드가 없어(`src/schema_admin.py:222`만 존재) 차단 목록은 항상 비어 있다.

### 🔴 F-3. 가드레일(금칙어·마스킹 규칙)이 챗봇 경로에 적용되지 않는다

- `guardrail_rules` 테이블의 `kind='blocklist'`를 읽는 곳은 **추천 질문 저장 검증 한 곳뿐**

- AD-008에서 금칙어를 등록해도 사용자 질문·답변에는 아무 영향이 없다.

## C-1. 🔴 AD-007 [운영 반영]에 **구조적으로 도달할 수 없다**

3단계 흐름 ①초안 편집 → ②초안 평가 → ③반영 중 **③이 영원히 열리지 않는다.**

최종 근거 수를 5→6으로 바꾸고 [초안 평가]를 실행했다. 서버는 정상 처리했다.

- `POST /api/admin/rag-params/evaluate` → **200**, `evaluation_runs` 0→1, `rag_param_versions` 0→1
- 게이트 결과 : `passed: true` · 검색 정확도@5 **0.949**(≥0.92) · MRR **0.805**(≥0.80) ·
  홀드아웃 75/79 · `recommendation: "→ B(초안) 반영 가능"`

그런데 화면은 **"초안이 바뀌어 평가가 무효화되었습니다"**를 띄우고 [운영 반영]을 계속 잠근다.

| | `draft_signature` 값 |
|---|---|
| 백엔드 (`admin_rag_params.py:156`) | `sha256(정규화 JSON)[:16]` → `"48622ae5ee96dd2c"` |
| 프론트 (`RagParams.tsx:116`) | `gate.draft_signature !== JSON.stringify(draft)` 로 비교 |
| **MSW 목** (`mocks/handlers/extra/ad-eval-rag.ts:523`) | `draft_signature: JSON.stringify(body.draft)` |

**목이 프론트의 잘못된 가정에 맞춰져 있다.** 해시와 JSON 문자열은 절대 같아질 수 없으므로
`stale`이 항상 참이고 게이트는 영구히 닫힌다. 목으로 개발하면 완벽히 동작하고 실백엔드에
붙는 순간에만 깨지는, **AD-009 `click_count`와 완전히 같은 패턴**이다(CLAUDE.md 불변식
"목이 곧 계약" 위반 2건째).

부수 관측 : A(현행)와 B(초안)의 지표가 소수점까지 동일했다(0.9494 / 0.8046). 이 평가는 검색 축만
재므로 **최종 근거 수처럼 생성에만 영향을 주는 파라미터는 판별하지 못한다.** 그런데도
`improved 0 · regressed 0` 상태로 "반영 가능"을 준다.

## C-2. 🔴 재적재 모달의 안내와 실제 동작이 다르다 (F-9 실행 확증)

[재적재]를 실제로 완주시켰다. 결과는 **SUCCESS**이고 6단계가 진짜로 돌았다.

| 단계 | 상태 | 건수 | 소요 |
|---|---|---|---|
| 수집 | SKIPPED | — | — |
| 변환 | SUCCESS | 58 | 8ms |
| 청킹 | SUCCESS | 494 | 9ms |
| 검증 | SUCCESS | 0 | 8ms |
| 색인 | SUCCESS | 494 | 12,494ms |
| 반영 | SUCCESS | 1 | 180ms |

데이터는 무손실이다(58문서 · 494청크 · 임베딩 누락 0). 그러나 모달이 약속한 것과 다르다.

- 모달 안내 : "재청킹 → 재임베딩 → **임시 색인 → 홀드아웃 평가 → 통과 시 교체**·캐시 무효화
  (미달 시 자동 중단·기존 유지)" · **예상 소요 약 3분 + 홀드아웃 평가**
- 실제 : 색인 UPSERT → 버전 기록으로 끝. **`evaluation_runs`가 0 그대로** — 홀드아웃 평가가
  실행되지 않았다. 캐시 무효화도 없다. 총 **13초**.

같은 모달이 "무중단 교체 미구현"이라고 스스로 밝히기도 한다. 즉 **화면이 없는 안전장치를
있는 것처럼 설명한다** — 관리자가 "미달 시 자동 중단"을 믿고 누르게 된다.

## C-3. 🟠 QUEUED 를 "실행 중"으로 표기한다

워커를 내린 상태에서 [전체 재수집]을 트리거했다. DB는 `status = QUEUED`인데 화면은 **"실행 중"**
이라고 표시했다(CM-DF-002 : QUEUED=대기 · RUNNING=진행 중). 워커가 죽어 아무것도 돌지 않는
상황에서도 관리자는 크롤링이 진행 중이라고 읽는다.

[취소]는 정상이었다 — 사유 필수 모달 → 취소 성공 → 이력에 '취소' 기록 → 트리거 버튼 재활성화.
실제 크롤링은 한 번도 일어나지 않았다.

## C-4. 🟠 전체 재수집 예상 소요가 비현실적이다

모달은 **"약 6분"**이라 안내한다. PRD-03의 전체 재수집 타임아웃은 **120분**이고, 실제 수집은
58페이지 × 0.5초 간격 + 판본 검증 재시도 + 동적 표 서브프로세스다. 백엔드 주석도
`_SECONDS_PER_TARGET`이 "실측이 아니다"라고 적어 두었다.
