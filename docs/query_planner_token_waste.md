# 현행 멀티쿼리 방식 토큰 낭비 실측 리포트

현재 RAG 파이프라인의 멀티쿼리(복합 질문 분해) 로직을 **실제 테스트셋에 그대로 돌려서**,
HyperCLOVA가 실제로 소비한 토큰을 호출마다 측정하고 어디서 얼마나 낭비되는지 정리한 문서다.
이 문서의 모든 토큰 수치는 **추정이 아니라 실측**이다.

> **한 줄 요약**
> 100문항을 현행 로직으로 1회 통과시키면 HyperCLOVA 토큰 **약 103만 개**가 나간다.
> 이 중 **오분류(안 쪼개도 될 질문을 쪼갬)로 인한 낭비가 약 50,600토큰(4.9%)**,
> **단일 질문인데도 매번 치르는 분해 판단 오버헤드가 약 33,900토큰(3.3%)**이다.
> 별개로, 눈에 안 띄던 **출처 재확인 호출이 전체의 29%**를 먹고 있다.

---

## 1. 측정 방법 (어떻게 쟀나)

- **운영 코드는 한 줄도 안 고쳤다.** 각 모듈의 `call_hyperclova` 참조만, 응답의 토큰 수를
  기록하는 래퍼로 임시 교체(monkeypatch)했다. 래퍼는 실제 응답
  (`AIMessage.usage_metadata` → `{input_tokens, output_tokens, total_tokens}`)을 그대로
  읽어 기록만 하고 원래 값을 반환한다.
- **별도 trace 도구(Langfuse)나 대시보드가 필요 없다.** CLOVA는 호출할 때마다 응답에 이번
  호출의 토큰 수를 같이 돌려준다. 현행 코드는 이 값을 그냥 버리고 있어서, 읽어서 쌓기만 했다.
- **테스트셋**: `data/testset/testset_query_decomposition.jsonl` — 이번에 40 → **100문항**으로
  확장(6개 도메인 고루 분포, easy 46 / hard 54, 단일 42 / 복합 58). 라벨:
  `should_split`, `expected_items`(정답 하위질문 개수), `difficulty`, `case_type`.
- **실행**: 현행 `pipeline` 로직 그대로 — 질문마다 `decompose_query`(분해) → 하위질문마다
  `_answer_one`(분류·검색·답변생성·조건부 재확인). 100문항 1회 통과.
- **측정한 3개 HyperCLOVA 단계**:
  - `decompose` — 복합 여부 판단·분해 (질문당 1회 고정)
  - `answer` — 답변 생성 (하위질문당 1회)
  - `recheck` — `[NO_SOURCE]` 답변의 출처 재확인 (조건부)
  - (intent 분류는 OpenAI라 이 HyperCLOVA 집계에는 미포함)

> 실측 단가(참고): 분해 **816 tok/호출**, 답변 생성 **3,914 tok/호출**(최소 1,564 ~ 최대 9,908),
> 재확인 **3,187 tok/호출**. 기존 문서의 참고값(분해 819 / 답변 4,445)이 실측으로 확인됐다.

## 2. 토큰이 어디에 쓰이는가 (100문항 1회 통과)

| 단계 | 토큰(실측) | 비중 | 호출 수 | 평균/호출 |
|---|---:|---:|---:|---:|
| 답변 생성 (answer) | 649,733 | **63.0%** | 166 | 3,914 |
| **출처 재확인 (recheck)** | 299,544 | **29.1%** | 94 | 3,187 |
| 멀티쿼리 분해 (decompose) | 81,625 | **7.9%** | 100 | 816 |
| **합계** | **1,030,902** | 100% | 360 | — |

- 질문당 평균 **10,309토큰**.
- 대부분(63%)은 실제 답변 생성이라 필수 작업이다.
- **눈여겨볼 점 두 가지**: (a) 재확인이 무려 29%를 먹는다(7절). (b) 분해 판단은 7.9%인데,
  이 중 상당수가 "안 쪼갤 걸 판단하는" 순수 오버헤드다(5절).

## 3. 낭비 ① 오분류(false split)로 인한 낭비 — 실측 50,594토큰 (4.9%)

**false split** = 안 쪼개도 될 단일 질문을 복합으로 잘못 판단해 쪼갠 것. 쪼개면 하위질문마다
답변 생성이 추가로 일어나고(+재확인까지), 그만큼 토큰이 낭비된다.

이번 1회 통과에서 **단일 질문 42개 중 6개**가 false split 됐고, 그로 인한 **초과 생성의 실제
토큰**은 다음과 같다.

| 문항 | 유형 | 분해 | 초과 답변 | 초과 재확인 | 낭비(실측) |
|---|---|---|---:|---:|---:|
| dq_004 | single_procedure | 1→3 | 6,215 | 2,717 | 8,932 |
| dq_022 | single_synonym_trap | 1→2 | 8,984 | 0 | 8,984 |
| dq_040 | single_urgency_clause | 1→2 | 1,704 | 0 | 1,704 |
| dq_048 | single_synonym_trap | 1→2 | 8,760 | 0 | 8,760 |
| dq_053 | single_informal_typo | 1→3 | 10,255 | 1,550 | 11,805 |
| dq_064 | single_synonym_trap | 1→2 | 5,495 | 4,914 | 10,409 |
| **합계** | | **초과생성 8회** | **41,413** | **9,181** | **50,594** |

- **낭비 총합 50,594토큰 = 전체의 4.91%.** 질문당 평균으로 환산하면 506토큰/질문.
- 낭비의 정체는 "동의어 함정"(방법/절차, 자격/요건/조건)과 절차형·오타·급함 문장이다 —
  실제로는 요구가 하나인데 접속어를 보고 두세 개로 쪼갠다.
- 초과로 만들어진 답변은 각각 **재확인 호출까지 유발**하므로, 낭비에 재확인분(9,181)도 포함된다.

> ⚠️ **이 6건은 1회 통과 기준이다.** 분해기는 `temperature=0.2`라 실행마다 흔들려서, false
> split 되는 문항 집합은 재실행 시 조금씩 바뀐다(4절 안정성 참고). 낭비의 **크기**(초과 1건당
> 약 5,000~12,000토큰)는 안정적이지만, **건수**는 확률적으로 변동한다.

## 4. false split 안정성 (분해 판단 3회 반복)

분해 판단만 저비용으로 3회 반복해 분해율을 안정화한 결과(답변 생성 없이 측정, 분해 호출
평균 816 tok로 확인):

| 지표 | 값 (3회 반복, run 단위) |
|---|---:|
| false split rate | **11.1%** (14/126 runs; 단일 42 × 3회) |
| under split rate | **9.2%** (16/174 runs; 복합 58 × 3회) |
| count match rate | **90.0%** |
| 초과 생성 | 평균 **5.7회 / 100문항 통과** |

- 3회 중 한 번이라도 false split 된 단일 질문: **5개** — dq_022·dq_048·dq_064(동의어 함정),
  dq_053(오타), dq_040(급함 절). 전부 hard.
- **오분류되는 문항 집합은 실행마다 바뀐다(비결정성).** 2절 full-pass(1회)에서는 dq_004도
  false split 됐지만 이 3회 반복에서는 한 번도 안 났고, 반대로 여기선 dq_073·dq_085·dq_086이
  under split로 새로 잡혔다. 다만 오분류 **건수**는 통과당 대략 5~8건으로 비슷하고, 낭비
  **크기**(초과 1건당 5,000~12,000토큰)는 안정적이다.
- 참고: 낡은 40문항 challenge set의 3회-**다수결** false split은 5.9%였다. 100문항으로 넓히고
  run 단위(다수결 없이)로 보면 11.1%로 올라간다 — 동의어 함정형 단일 질문이 더 들어왔고,
  실사용은 다수결이 아니라 매 질문 1회 판단이기 때문이다.

## 5. 낭비 ② 단일 질문인데도 매번 치르는 분해 판단 — 실측 33,854토큰 (3.3%)

현행 구조는 게이트 없이 **모든 질문에 분해 호출 1회**를 무조건 한다. 단일 질문(안 쪼갤 질문)
이어도 "쪼갤지 말지"를 판단하려면 이 호출이 필요하다.

| 대상 | 토큰(실측) | 비중 |
|---|---:|---:|
| 전체 분해 호출(100문항) | 81,625 | 7.9% |
| 그중 **단일 질문 42개**의 분해(순수 오버헤드) | **33,854** | **3.3%** |

- 단일 질문 42개는 결국 "안 쪼갠다"는 결론만 얻으려고 33,854토큰을 쓴다.
- 이건 오분류(실수)가 아니라 **구조(게이트 없는 always-LLM)** 때문이라 프롬프트 튜닝으로는
  절대 못 줄인다. 줄이는 유일한 길은 **분해 판단을 어차피 하는 다른 호출(intent 분류)과 한
  번의 호출로 합치는 것**이다(→ 다음 단계 "쿼리 플래너" joint-call).

---

## 6. under split은 왜 여기 없나 — 낭비가 아니라 품질 문제

**under split** = 쪼개야 할 복합 질문을 안 쪼갠 것. 이번 통과에서 복합 질문 58개 중 4개
(dq_031, dq_039, dq_087, dq_098)가 안 쪼개졌다.

- under split은 답변을 **덜** 만든다 → 토큰은 오히려 **적게** 쓴다. 그래서 "토큰 낭비"에는
  안 잡힌다.
- 대신 요구사항이 검색·답변에서 누락된다 → **답변이 불완전**해지는 품질 손실이다.
- 즉 **false split = 비용 문제 / under split = 품질 문제**로 성격이 완전히 다르다. 이 문서는
  비용(토큰)을 다루므로 under split은 건수만 기록하고, 품질 평가는 별도 과제로 둔다.

---

## 7. 숨은 대형 비용 — 출처 재확인(recheck)이 전체의 29%

측정하면서 드러난, 멀티쿼리와 별개의 큰 토큰 사용처다.

- 재확인은 답변이 `[NO_SOURCE]`로 판정될 때만 근거를 다시 넣어 "이 답변이 자료를 실제로
  썼는가"를 LLM에 되묻는 호출이다(`source_check.py`).
- 이번 통과에서 **166개 답변 중 94개(57%)가 재확인을 유발**했고, 재확인 하나가 근거 청크를
  통째로 다시 넣어 평균 3,187토큰을 쓴다. 합계 **299,544토큰 = 전체의 29.1%.**
- 멀티쿼리와의 연결점: **복합 질문은 하위 답변마다 재확인이 따로 발동**하므로, 분해가 답변
  수를 N배로 늘리면 이 29% 비용도 같이 N배로 커진다. false split이 만든 초과 답변도 각자
  재확인을 유발한다(3절 표의 "초과 재확인" 열).
- 이건 멀티쿼리의 "낭비"로 분류하진 않았지만(출처 정확도를 위한 구조적 비용), **토큰을 크게
  줄이고 싶다면 재확인 발동 조건·비용이 가장 큰 후보**라는 사실은 기록해 둔다.

## 9. 그래서 얼마나 심각한가

**100문항 1회 통과 = 1,030,902토큰** 기준으로 정리하면:

| 구분 | 토큰 | 비중 | 성격 |
|---|---:|---:|---|
| 답변 생성 | 649,733 | 63.0% | 필수 작업 |
| 출처 재확인 | 299,544 | 29.1% | 구조적 비용(멀티쿼리가 N배 증폭) |
| 분해 판단(전체) | 81,625 | 7.9% | 고정 오버헤드 |
| └ 낭비 ② 단일질문 분해 오버헤드 | 33,854 | 3.3% | joint-call로 제거 가능 |
| 낭비 ① 오분류 초과 생성 | 50,594 | 4.9% | 프롬프트·분해기 개선 대상 |

- **멀티쿼리 방식이 직접 유발한/관련된 낭비 ≈ 낭비① 50,594 + 낭비② 33,854 = 84,448토큰 (약 8.2%).**
- 이 중 **낭비②(3.3%)는 분해 호출을 intent 분류와 합치면(joint-call) 통째로 사라진다** —
  분해 버킷 7.9% 전체가 HyperCLOVA에서 빠지고, 어차피 하던 intent 호출에 얹힌다.
- **낭비①(4.9%)은 분해기 프롬프트·라벨 개선(동의어 함정 방어)으로 줄일 대상**이다. 단
  `temperature=0.2` 비결정성 때문에 완전히 0으로 만들긴 어렵다. (이 4.9%는 초과 생성 8건이
  난 full-pass 실측이고, 분해 3회 반복 평균은 통과당 초과 5.7건이라 **기대 낭비율은 대략
  3.5~4.9% 범위**로 보는 게 안전하다.)
- 참고로, 앞서 40문항 challenge set을 3회 반복 **다수결**로 봤을 때는 오분류 낭비가 ~1.4%로
  작아 보였는데, **실사용처럼 1회 통과(다수결 없음)로 100문항을 실측하니 4.9%로 더 크게**
  나왔다. 운영 환경은 질문 한 건당 분해를 딱 1번 하므로, 1회 통과 수치가 실제에 더 가깝다.

## 10. 한계와 다음 단계

**한계**
1. **1회 통과 실측이다.** 낭비의 크기(초과 1건당 토큰)는 안정적이나, false split 되는 문항
   집합은 `temperature=0.2` 때문에 재실행 시 변동한다(4절). 정밀한 기대 낭비율은 여러 번
   통과 평균이 필요하다.
2. **challenge 성격의 테스트셋이다.** 복합 질문(58%)·hard(54%)가 실사용보다 많이 섞여 있어,
   이 절대 낭비율(8.2%)을 실제 운영 평균으로 그대로 보면 안 된다. 실사용 분포로 재측정 필요.
3. **비용(원화)은 계산하지 않았다.** 토큰만 실측했다 — 요금 환산은 CLOVA 요금표 적용 필요.

**다음 단계**
1. **쿼리 플래너(joint-call) 모델 선정** — 분해 판단 + intent 분류를 한 호출로 합쳐 낭비②를
   제거하는 방식. Structured Output을 쓸 모델(HCX-007 / gpt-5.4-mini / gpt-5.6-luna)을 비교해
   정한다(별도 문서).
2. **분해기 동의어 함정 방어** — 낭비①의 주범(방법/절차, 자격/요건/조건)을 프롬프트·라벨로
   줄인다.
3. **재확인 비용 최적화 검토** — 전체의 29%를 먹는 만큼, 발동 조건·근거 재전송 방식의 경량화
   여지 확인.

### 부록 — 재현 방법

- 측정 하네스: 각 모듈의 `call_hyperclova`를 `usage_metadata` 캡처 래퍼로 교체 후, 현행
  `decompose_query` + `pipeline._answer_one`를 100문항에 실행(임시 스크립트, 저장소 미커밋).
- 원자료: 호출별 `{stage, test_id, subq, input, output, total}` 기록 → 단계별 합계·오분류
  귀속으로 위 표 산출.
- 테스트셋: `data/testset/testset_query_decomposition.jsonl`(100문항).
