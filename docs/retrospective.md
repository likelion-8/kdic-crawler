# 프로젝트 회고 — 실전프로젝트 1~2 종합 정리

종합 프로젝트를 시작하기 전에, 지금까지 실험하고 선택했던 것들과 그 이유를 한 곳에
모은다. 논문 형식이 아니라 "무엇을 시도했고, 무엇을 근거로 채택/폐기했는가"를 추적하는
데 초점을 둔다. 각 절 끝에 원본 근거 문서를 링크해뒀으니, 수치 재현이나 더 깊은 맥락이
필요하면 그쪽을 보면 된다.

**더 세밀한 시행착오(일자별 작업 기록)는 `log/0713.md`~`log/0730.md`에 있다. 이 문서는
그중 최종적으로 코드/결정에 반영된 것만 추린 요약이다.**

## 0. 프로젝트가 풀려는 문제

예금보험공사(KDIC)의 기존 챗봇 '예솜24'를 RAG로 다시 만드는 프로젝트. 예금자보호제도,
예금보험금 안내, 고객 미수령금 신청, 착오송금 반환 신청, 채무조정 안내, 은닉재산 신고
6개 업무의 공식 웹페이지를 근거로 질문에 답한다.

왜 검색 품질이 이 프로젝트의 핵심인가 — **틀린 답이 바로 금전 피해로 이어진다.** 보호한도가
실제로 시점에 따라 5천만원/1억원으로 갈리는(2025.9.1 경과규정) 사례처럼, 어느 페이지를
근거로 잡느냐가 답의 사실성을 좌우한다. 그래서 "그럴듯한 답변을 생성하는 모델"보다
"맞는 근거를 정확히 찾고, 없으면 정직하게 모른다고 말하는 파이프라인"을 우선순위로 뒀다.

(전체 배경·문헌조사는 [README.md](../README.md) 1~2장 참고)

## 1. 데이터 파이프라인

### 수집 범위 확정

사람이 손으로 정리한 후보 49건을 커버리지 검사기(`coverage_check.py`)로 사이트 메뉴와
대조하니 미수집 23페이지가 더 나왔다(지급대행점 조회, 착오송금 지원현황 등). 전부 추가해
**58페이지**로 확정 — "사람이 훑은 목록"과 "실제 사이트 구조"가 다를 수 있다는 걸 자동
대조로 잡은 사례.

### 수집(크롤링) — 사이트가 실제로 던진 문제들

팀원 3명이 각자 크롤러를 짰다(`crawler_hw.py`/`crawler_dy.py`/`crawler_yj.py`, 담당
페이지 분담). 난이도가 올라갈수록 사이트가 던지는 문제도 늘었다:

- **판본 혼재 페이지**: fins.kdic.or.kr 쪽은 `<body>` 태그가 2개(첫 번째는 빈 태그)라,
  파싱 실패 시 `<body>` 전체로 폴백하는 흔한 안전장치를 여기선 오히려 금지해야 했다
  (`crawler_dy.py`). 더 나아가 `crawler_yj.py`의 `render_stable()`은 같은 URL을 새
  세션으로 두 번 가져와 내용을 diff한다 — 서버가 같은 페이지를 여러 판본으로 서빙하는
  걸 실측으로 확인했기 때문이며, 자동으로 못 좁히면 관측된 판본을 전부
  `data/variants/`에 남겨 사람이 판단하게 했다.
- **soft 404**: 없는 페이지에 HTTP 404가 아니라 200 + "오류" 제목을 주는 사이트라, 상태
  코드만 보는 흔한 방식으로는 깨진 링크를 못 잡는다 — 별도 감지 로직 필요.
- **JS 뒤에 숨은 다운로드·이동 링크**: 서류 다운로드 버튼이 `href`가 아니라
  `gfn_downloadFile(암호화경로, 암호화파일명)` 같은 onclick 함수 호출이고, 신청·조회
  버튼도 `gfn_openUrl` onclick 안에 실제 URL이 있다. 인자가 암호화돼 있지만 HTML에
  정적으로 박혀 있고 세션과 무관하게 유효함을 실측 확인해(`crawl_mistaken_remittance_
  jh.py`, 2026-07-14, hwp 다운로드 성공 확인) 이 함수 호출을 정규식으로 역해석하는
  방식을 택했다 — 실제 브라우저 자동화(Selenium 등) 없이도 안정적으로 받을 수 있었다.
- **동적 검색 화면의 페이지네이션**: "보호대상 금융회사 검색" 같은 화면은 페이지네이션도
  JS(`chgPagingNo`)로 처리돼 있어, 이 함수가 쓰는 hidden 필드(`curPage`/`pageSize`)를
  그대로 흉내 내 POST하는 방식으로 전체 행을 받았다(`fetch_dyntable.py`). 페이지 상한을
  처음엔 낮게 뒀다가 "보호대상 금융회사는 실제로 289행인데 20페이지(200행)에서 잘린다"는
  걸 발견하고 `MAX_PAGES=300`으로 올렸다 — 상한을 못 믿을 근거 없이 임의로 잡으면 안
  된다는 사례.
- **화면 템플릿 치환 토큰 오염**: 위 검색 화면의 표 셀 값이 실제 데이터가 아니라
  `#PRSNCONM`, `#COADDR` 같은 클라이언트 렌더링용 치환 토큰으로 나오는 경우가 있었다
  ("이걸 그대로 청크로 만들면 챗봇이 '은행명: #PRSNCONM'이라고 답한다"). 그대로 색인하면
  안 되는 걸 걸러내는 필터를 별도로 뒀다.
- **게시판형 페이지의 첨부파일**: "안내자료 다운로드" 같은 게시판은 목록 페이지에 첨부파일
  URL이 없고 게시글 상세 페이지에만 있어서, 목록만 크롤링하면 파일 링크를 통째로 놓친다
  (`fetch_extra.py`) — 목록에서 `detailView(bbsId)` 패턴으로 상세 URL을 뽑아 별도로
  다시 수집해야 했다.
- **표 파서의 함정**: 계산기 UI처럼 셀 값이 전부 `0`/`-`인 빈 표 뼈대는 데이터가 아니므로
  걸러야 하지만, `colspan`으로 병합된 진짜 행이나 실제 값이 0인 셀은 남겨야 한다 —
  이 구분을 `crawler_yj.py`의 표 변환 함수에 자체 검증(selftest)으로 박아뒀다.
- **인벤토리 병합 중 발견한 라벨 오류**: 5명이 각자 관리하던 수집 대상 목록을
  `inventory.py` 하나로 합치는 과정에서, 한 팀원의 채무조정 페이지 URL 2건이 실제로는
  다른 페이지를 가리키고 있었다는 게 다른 팀원의 독립 수집본과 대조하다 드러나 정정했다.

### 전처리 원칙: HTML→텍스트에 LLM을 안 쓴다

원문 보존이 최우선이라 규칙 기반으로만 변환한다. 실제로 JS가 채우는 빈 검색 결과표를
안 걸러내면 챗봇이 "포상금 0원"이라고 답하는 문제를 겪은 뒤, 페이지 크롬 제거를 정확일치
방식으로만 하도록 다잡았다.

**콘텐츠 해시(`content_sha256`)도 원본 HTML이 아니라 정규화된 본문 텍스트를 기준으로
잡는다** — 같은 페이지가 판본 혼재로 서빙되고 세션 토큰·공백이 매 요청 달라지는 사이트라
HTML을 그대로 해시하면 내용이 안 바뀌어도 값이 계속 튄다(`hashing.py`). 이 정규화도
처음부터 완벽하진 않았다 — 한 페이지(`dp_protlmts`)를 재수집했더니 글자는 한 자도 안
바뀌었는데 빈 줄 하나가 사라져 해시가 달라진 걸 발견하고서야 빈 줄 제거를 정규화 단계에
추가했다.

### 청킹: 고정 길이 대신 구조 인식 청킹 (채택)

원래 계획은 "500자 고정 분할 + 헤딩 프리픽스 유지"였다. 실측 결과 이게 아니라 **구조
인식 청킹**으로 바꿨다:

- FAQ 페이지 → 질문 마커 기준 QA쌍 단위
- 표 페이지 → 3행씩 헤더 반복 묶음
- 그 외 → 페이지 통짜 1개 유닛

판별 자체도 하드코딩된 페이지 ID가 아니라 텍스트 패턴이다(`project1_src/chunking.py`) —
`is_faq()`는 본문에 "질문"·"답변" 마커가 각 2회 이상 나오면 FAQ로, `is_table()`은 행
구분자 `" | "`가 20회 이상 나오면 표로 판정한다. 재수집으로 새 FAQ·표 페이지가 추가돼도
페이지 ID를 새로 등록할 필요 없이 자동으로 같은 방식으로 처리된다는 게 이 방식을 고른
이유다.

**왜 3행인가** — 청크 크기 스윕 실험(꼬리 프로브 AnswerRecall@5 기준):

| 행/청크 | 유닛 수 | 꼬리 AnswerRecall@5 |
|---|---|---|
| 40 | 81 | 0.250 |
| 10 | 163 | 0.250 |
| **3** | 417 | **1.000** |
| 1 | 1148 | 1.000 |

3행이 "품질 1.000 달성 + 유닛 폭증 억제"의 sweet spot이라 채택. 1행까지 가도 품질은
같은데 유닛 수만 3배 가까이 늘어나 비효율적이었다.

**FAQ 청킹 효과**: faq 유형 문서찾기 MRR이 page 0.696 → faq_atomic **0.926~0.928**로
급등(580문항 재검증 기준). **표 청킹의 진짜 가치는 MRR이 아니라 AnswerRecall에 있다** —
통짜 baseline은 8192토큰 경계 뒤에 잘린 표 꼬리 질문에 답을 하나도 못 냈다(0.000).
3행 청킹으로 1.000. 문서찾기 지표(MRR)는 페이지 단위라 정답 페이지만 맞히면 만점을 줘서
이 잘림 피해를 못 본다 — **"어느 지표로 보느냐"에 따라 정반대 결론이 나오는 경우**였다.

### 평가셋 구축과 검증 — "정답이 실제로 맞는가"를 스크립트로 전수 검사

평가셋(`testset_all.jsonl`, 853건)이 틀리면 그 위의 모든 실험 수치가 무의미해진다는
전제로, 두 단계 검증 스크립트를 뒀다.

- `validate_testset.py`(구조 검증): 필드 집합·순서가 스키마와 정확히 일치하는지,
  `test_id` 중복이 없는지, `question_type`·`intent`가 정의된 값 안에 있는지,
  `expected_sources`의 모든 page_id가 실제 `corpus.jsonl`에 존재하는지, 그 페이지의
  `business_function` 라벨이 문항 라벨과 일치하는지, `out_of_scope` 유형이면
  `expected_sources`가 정확히 비어있는지를 검사한다.
- `validate_golden_labels.py`(내용 검증): `must_include` 키워드가 실제로 정답 페이지의
  본문·제목·링크·첨부·서식·영상 어딘가에 있는지 문자열 대조로 확인한다. **처음엔 본문
  (`text`)과 `source_url`만 검사해서 `ha_center_q3`처럼 실제로는 맞는 문항을 오탐으로
  잘못 걸렀다** — 정답 근거가 링크나 첨부파일 텍스트에 있었기 때문이다. 검사 대상을
  본문+제목+링크+첨부+서식+영상 전체로 넓혀 이 문제를 고쳤다(2026-07-23). 날짜 표기
  (`2025.9.1` vs `2025-09-01`)나 구분자(`/` vs `-`) 차이로 생기는 거짓 불일치도 문자열
  정규화 단계에서 흡수한다.

두 스크립트 다 사람이 853건을 눈으로 다시 읽는 대신, "이 라벨이 원문에 실재하는가"를
기계적으로 반복 검증할 수 있게 만들었다는 게 핵심이다 — 853/853 통과라는 숫자 자체보다,
그 숫자를 재현 가능하게 만든 절차가 더 중요하다.

## 2. 검색(Retrieval) — 무엇을 시도했고 무엇을 버렸나

### 2.1 임베딩 모델 비교 → BGE-m3-ko 채택

BGE-M3 · BGE-M3-ko · Qwen3-Embedding-8B · Nemotron-3-Embed-8B 4종을 비교했다.
Nemotron이 지표는 더 높았지만(MRR 0.846) 8B급이라 오프라인 CPU 배포 제약으로 제외하고
**BGE-m3-ko**(MRR 0.770) 채택 — 성능과 배포 현실성의 트레이드오프.

### 2.2 BM25 vs Dense vs Hybrid → 기본 Dense, 유형별 라우팅

169문항 baseline과 580문항 확장 재검증 둘 다 같은 결론:

| 검색기 | page | faq_atomic | table_row | all |
|---|---|---|---|---|
| BM25 | 0.570 | 0.711 | 0.624 | 0.685 |
| **Dense** | 0.718 | 0.719 | 0.723 | **0.724** |
| Hybrid(RRF) | 0.682 | 0.730 | 0.695 | 0.720 |

**순진한 균등 RRF Hybrid는 항상 Dense보다 낮다** — 약한 BM25가 강한 Dense를 끌어내리는
현상. 그래서 "무조건 Hybrid"가 아니라 **질문 유형별 라우팅**으로 방향을 바꿨다.

유형별 재검증(bf_score_fusion_eval.py, 821문항):

| 유형 | Dense | Hybrid |
|---|---|---|
| fact | 0.745 | 0.739 |
| faq | 0.819 | 0.788 |
| table_lookup | 0.866 | 0.626 ← BM25가 약해 Hybrid가 확실히 손해 |
| **link_guide** | 0.650 | **0.708** ← 유일하게 Hybrid가 나음 |
| file_download | 0.931 | 0.925 |

`link_guide`(페이지명·메뉴 키워드 질문)만 BM25가 강해서 Hybrid가 이긴다. 그래서
**"기본 Dense, link_guide만 Hybrid"**로 확정(`retrieval.py`의 `RoutedRetriever`).

결합 방식도 RRF보다 **Linear fusion(α=0.4)**이 나음이 확인돼(link_guide 융합 스윕,
59문항 부트스트랩) 그쪽으로 교체했다(Linear 0.744 > RRF 0.725 > Dense 단독 0.650).

**이 라우팅 결론도 한 번 뒤집혔던 결론이다.** `retrieval.py` 주석에 남아있는 기록에
따르면, 2026-07-21에 더 작은/구버전 테스트셋으로 `route_eval.py`를 처음 돌렸을 때는
**정반대 결론**이 나왔었다. 이후 테스트셋이 169건→821건으로 커지면서 재측정한 위 표
수치로 그 결론을 대체했다 — 옛 테스트셋 자체가 지금 저장소엔 남아있지 않아 "무엇이
왜 반대였는지" 세부까지는 재구성할 수 없지만, "작은 표본 결론을 그대로 프로덕션에
박아넣지 않고 표본이 커질 때마다 재검증한다"는 원칙이 실제로 결론을 바꿔놓은 사례로
남겨둔다. 같은 스크립트는 정직한 평가와 낙관적 평가를 구분해서 낸다 — `evaluate_routed()`
는 정답 유형 라벨을 그대로 써서 라우팅 자체의 상한을 재고, `evaluate_routed_with_
predicted_types()`는 분류기가 실제로 예측한 유형으로 재서 "실서비스에서 실제로 겪을
성능"을 별도로 측정한다.

- [retrieval_eval.md](retrieval_eval.md)

### 2.3 업무(business_function) 계층 필터 → 폐기

**당초 계획의 핵심 아이디어였는데 실측으로 뒤집힌 대표 사례.** 오답 원인이 "타 업무 청크
혼입 25.4%"로 특정돼 있어 검색 공간을 업무별로 좁히면 해결될 거라 예상했고, 초기 측정도
그렇게 보였다(Recall@3 63.5%→75.1%).

**그런데 이 초기 측정에 형제 질문 편향이 섞여 있었다.** 같은 페이지에서 나온 질문들이
학습/평가에 같이 들어가 있어 낙관적으로 나온 것. **Leave-page-out**(같은 페이지의 형제
질문을 평가에서 통째로 제외)으로 정직하게 재검증하니:

- 필터를 켜면 분류기 오분류로 정답 업무가 통째로 빠지는 all-or-nothing 실패가 821문항 중
  63건(7.7%) 발생
- MRR 0.775(무필터) → 0.759(필터)로 오히려 하락
- 업무 정보를 점수에 약하게 섞는 절충안도 시도했지만(`bf_score_fusion_eval.py`), 분류기의
  진짜 일반화 정확도가 55~80%에 그쳐 어떤 융합 방식을 쓰든 손해였다. 실제로 시도한 건
  세 가지다: **(1)** dense 점수와 business_function 점수를 그냥 가중합(둘 다 코사인
  유사도라 스케일이 같다는 근거로 순위 대신 점수를 직접 더함), **(2)** BM25+Dense를
  RRF로 먼저 합친 뒤 업무 일치 보너스를 곱으로 얹음(`rrf_score · (1 + λ·bf_score)`),
  **(3)** 팀원 제안으로 유형별 기본 검색기(table_lookup=Dense, 나머지=Hybrid)에 "예측
  1순위 업무와 문서 업무가 일치할 때만" 하드 보너스를 주는 top-1 매칭. λ를 0.1~1.0
  네 값으로 스윕했지만 leave-page-out 기준 세 방식 다 무필터보다 나은 조합을 못 찾았다.
- 분류기 정확도(55~80%)의 "55%"가 유독 낮게 나온 이유도 형태소 intent 분류와 같은
  패턴이었다 — 같은 페이지 형제 질문은 business_function이 100% 같으므로, leave-one-out
  만으로는 형제가 정답을 새어나가게 하고, 형제까지 통째로 제외하는 leave-page-out으로
  재야 분류기의 진짜 일반화 성능이 드러났다(3절의 intent 분류 사례와 완전히 같은 함정을
  독립적으로 다시 만난 셈).

**결론**: 검색 공간을 좁히는 방향 자체는 맞았지만, 좁히는 축이 "업무"가 아니라 "질문
유형"이어야 했다(2.2절). 지금은 `RoutedRetriever`에 `bf_classifier`를 안 넘겨서 필터가
꺼져 있는 상태 — 재도입 여지는 코드에 남겨뒀지만, 하드 필터가 아니라 소프트(부스팅/top-2/
확신 게이팅)로 가야 한다는 방향까지만 정리해뒀다.

### 2.4 리랭커(cross-encoder) → 기본 Off (품질 판정은 보류)

## 3. 질문 분류 (Intent / Question Type)

### question_type 분류 (link_guide 여부 등, 검색 라우팅용)

라벨링된 질문 579개와의 **코사인 1-NN**으로 분류. table_lookup 여부가 코퍼스(본문)가
아니라 질문 자체의 형태(엔티티+조회 의도)에서 나온다는 게 확인돼, 코퍼스 대신 질문
예시로 분류하는 방식을 채택했다(`query_classifier.QuestionTypeClassifier`).

### intent 분류 — 4가지 방법을 실측 비교하고 골랐다

라벨 자체도 사람이 823건을 전부 손으로 본 게 아니라 **규칙 기반 1차 라벨링**이다
(`project1_src/label_intent.py`): `question_type`이 file_download·link_guide면 무조건
civil_petition, 그 외엔 "신청·접수·제출·구비서류·위임장·철회·취소·이의제기·지급명령·청구"
같은 절차 실행 표현이 있으면 civil_petition, 없으면 informational
(`label_intent.PROCEDURE_MARKERS`). 이 라벨을 기준으로 네 가지 분류 방법을 비교했다
(`src/eval_intent_*.py`, 실행 결과는 `data/intent_*_result.json`에 커밋돼 있음):

| 방법 | 평가 방식 | 정확도 | 비고 |
|---|---|---|---|
| 규칙 기반(정규식) | leave-page-out | **91.5%** | ⚠ 라벨 자체가 비슷한 절차표현 규칙으로 만들어져 순환 검증 우려 |
| 코사인 1-NN(운영 초기 방식 그대로 측정) | self-match | 100% | 자기 자신이 항상 최근접으로 잡혀 완전 누수, 무의미 |
| 코사인 1-NN | leave-one-out | 88.8% | 자기 자신만 제외 — 그래도 형제질문 누수 남음(아래) |
| 코사인 1-NN | **leave-page-out** | **81.5%** | 같은 페이지 형제질문 전부 제외 — 가장 정직한 값 |
| 코사인 centroid(클래스 평균벡터) | 8:2 stratified split | 73.8% | 1-NN 대신 centroid로 바꿔도 하락 |
| **형태소 TF-IDF + LogisticRegression(최종 채택)** | leave-page-out | **89.6%** | 페이지 단위 분리, `class_weight="balanced"` |

**운영 방식(코사인 1-NN)의 실제 정확도를 처음엔 잘못 재고 있었다는 게 이 비교의 핵심
발견이다.** `query_classifier.py`가 쓰는 방식 그대로("in-scope 질문 821건 전체를 참조
벡터로 쓰고, 정확도도 그 같은 데이터로 잼") 재면 자기 자신이 항상 1등으로 뽑혀 100%가
나온다 — 완전한 데이터 누수(`eval_intent_cosine.py`의 STEP 1 진단). leave-one-out(자기
자신만 제외)으로 다시 재면 88.8%로 떨어지는데, **`eval_intent_sibling.py`로 한 번 더
파보니 이 88.8%도 여전히 부풀려져 있었다**: 최근접 이웃의 67.1%가 "같은 페이지에서 나온
형제 질문"이고, 형제 질문은 표현이 비슷해 더 잘 맞는다(형제일 때 정확도 90.0% vs 비형제일
때 86.3%). 같은 페이지 형제를 통째로 평가에서 빼는 leave-page-out으로 다시 재면 **81.5%**
까지 떨어진다 — 이게 "진짜 낯선 질문"에 대한 코사인 1-NN의 정직한 성능이다.

**형태소 TF-IDF+LogReg(89.6%, 역시 leave-page-out)가 코사인 방식의 정직한 성능(81.5%)보다
뚜렷하게 낫다.** 규칙 기반(91.5%)이 수치는 더 높지만, 라벨 자체가 유사한 절차 표현 규칙
으로 만들어졌다는 순환성 때문에 신뢰하지 않기로 하고 **형태소 방식을 최종 채택**했다
(`query_classifier.classify_intent`가 `data/intent_classifier/*.pkl`을 로드,
`train_intent_morpheme.py`가 학습 산출물을 생성). question_type은 코사인 방식을 그대로
유지하고 intent만 형태소로 바꾼 것도 이 실측 차이 때문 — 같은 파이프라인 안에서도 "무엇을
분류하느냐"에 따라 최적 방법이 다를 수 있다는 사례다.

**부가 확인**: LogReg 계수로 어떤 형태소가 civil_petition 쪽으로 미는지 봤더니(`eval_intent_
morpheme.py`) 어미·연결어미(Kiwi 태그 EF/EC) 토큰이 상위에 잡혔다 — "~하려면", "~해야
하나요" 같은 절차 실행형 어미가 실제로 민원성 의도의 신호가 된다는 걸 형태소 분석이
포착한 것으로, 형태소 방식이 이 도메인에서 코사인 임베딩보다 더 잘 맞는 이유를 부분적으로
설명해준다.

## 4. 복합 질문 분해 (Multi-Query Decomposition)

"신청 방법과 필요한 서류, 처리 기간을 알려주세요"처럼 한 질문에 여러 정보 요구가 섞이면,
단일 임베딩으로는 검색 벡터가 여러 주제 사이에서 뭉개져 일부 요구가 밀려난다. 이 문제를
**두 단계**로 풀었다.

### 1차 시도 — 규칙(정규식)+Kiwi 형태소 게이트 (폐기)

접속사·물음표·명사+접속조사 등을 규칙으로 누적하며 튜닝. 최종 버전(Recall 0.743, 오탐
0.150)까지 갔지만 목표 성능에 못 미쳤고, "~하고"처럼 원리적으로 못 잡는 패턴이 남았다.
이 단계에서 **always-LLM(게이트 없이 항상 LLM 호출)도 대안으로 테스트했지만, 단일 질문을
강제로 분해기에 태우면 없는 하위 항목("서류는?", "기간은?")을 지어내며 오분할하는 문제가
3/3 재현돼 당시엔 기각했다.**

> 1차 시도의 코드는 현재 저장소에 없다(별도 환경 작업, 커밋 없이 유실). 수치는 당시 기록
> 재구성이며 이 저장소에서 재검증한 게 아니라는 점은 한계로 남겨둔다.

### 2차 시도 — 항상-LLM 방식 (최종 채택)

**1차 시도가 기각했던 바로 그 실패(단일 질문 강제 분해 시 지어내기)를 2차 시도 초기 버전도
독립적으로 재현했다.** 차이는 그다음 대응이다 — 1차는 이 실패를 이유로 방식 자체를 버렸지만,
2차는 **이 정확한 실패 사례를 few-shot 예시로 박아넣는 프롬프트 보강**으로 문제를 상당 부분
해결했다. 즉 "always-LLM은 안 된다"는 결론이 아니라 "프롬프트 보강 없는 always-LLM은
안 된다"는 결론으로 정정된 셈.

최종 결과(38문항×3회 반복):

| 방식 | Recall(복합→복합) | 오탐(단일→복합) |
|---|---|---|
| 1차 최종(규칙+Kiwi) | 0.743 | 0.150 |
| **2차 최종(항상-LLM)** | **0.955** | **0.000** |

검색 품질 개선도 별도 검증(cq01~15, 27건 라벨셋):

| 조건 | Recall@5 | MRR@20 |
|---|---|---|
| BEFORE — 원 복합질문 통째로 검색 | 0.556 | 0.334 |
| AFTER-GOLD — 손라벨 하위질문(이론적 상한) | 0.815 | 0.576 |
| **AFTER-REAL — 실제 `decompose_query()` 출력** | **0.815** | 0.50~0.53 |

AFTER-REAL이 AFTER-GOLD와 Recall@5가 정확히 같다는 게 핵심 — 실제 배포된 분해기가
이론적 상한만큼의 검색 개선을 실현한다는 뜻이다. (초기엔 0.778로 측정했다가, 중복 페이지
쌍(`kmrs_proc`/`mtrs_gvbk_proc`)을 하나로 잘못 채점했던 라벨 오류를 발견해 0.815로
정정한 이력이 있다 — 검색·분해기의 실패가 아니라 평가셋 라벨 문제였음을 확인 후 수정.)

**솔직한 한계**: `llm_client.py`의 `temperature=0.2`(전체 파이프라인 공유) 탓에 어떤
케이스든 **10~20%대 확률적 흔들림이 잔존**한다. 3회 반복에서 100%/95.5%로 나왔던
케이스가 이후 스팟체크에서 다시 실패하는 걸 관찰했다 — 이 수치를 절대 신뢰하지 말고
운영 시 잔여 오류율로 감안해야 한다. "~인지와 ~에 대해 알고 싶습니다" 같은 정중한 복합
서술 패턴도 미해결로 남아 있다(few-shot을 더 늘리면 동의어 함정 케이스가 회귀해 되돌림).

- [multiquery_decomposition.md](multiquery_decomposition.md)

## 5. 답변 생성 (Prompt Engineering)

### 5.1 URL 할루시네이션 — "안 틀리게" 대신 "아예 안 보여주기"

초기엔 LLM에게 근거 청크와 함께 출처 URL도 프롬프트에 넣고 답변에 포함시키도록 했다.
반복적으로 재현된 문제: 근거가 없거나 애매한 질문("나의 미수령금")에서 few-shot 예시
내용을 그대로 베끼거나, 준 적 없는 URL을 새로 지어냄. system 지시문 보강, 섹션 생략
규칙 추가, 빈 섹션 자체 삭제까지 순서대로 시도했지만 여전히 재현됐다.

**최종 해결책은 "LLM이 URL을 안 틀리게" 만드는 게 아니라 "LLM이 URL을 아예 쓸 일이
없게" 만드는 구조 전환이었다** — LLM은 절차 설명/답변 본문 텍스트만 쓰고, 실제 서류·
페이지·출처 URL은 `citation.py`/`civil_petition.py`가 검색 결과에서 조회한 값을
`assemble_*_answer()`가 LLM 응답 뒤에 결정론적으로 붙인다. LLM이 URL을 아예 안 보므로
지어낼 소스 자체가 없어졌다.

곁들여 발견한 별개 문제: 서식 다운로드 URL(`resolved_url`) 자체가 103건 중 3개 URL로만
겹치는 깨진 링크였다(JS 다운로드 버튼의 공통 서블릿 주소, 실제 파일 식별엔 암호화 파라미터
필요). 클릭해도 다운로드 안 되는 링크 대신 다운로드 버튼이 실제로 있는 페이지 주소
(`page_url`)를 안내하도록 변경.

### 5.2 `[NO_SOURCE]` 마커 — 근거 미사용 판정의 신뢰성

BM25 점수 임계값으로 범위 밖 질문을 거르는 건 안 된다는 걸 먼저 확인했다(범위 안/밖
점수 분포가 겹침). 대신 **LLM이 근거를 실제로 썼는지를 고정 마커로 직접 표시**하게 하고,
그 마커로 출처 첨부 여부를 결정론적으로 가르는 방식을 택했다.

- 1차: "근거 미사용일 때만 `[NO_SOURCE]`를 붙여라"는 조건부 지시 → LLM이 내용상으로는
  올바르게 거절하면서도 마커 자체를 빼먹는 경우가 재현(6/6, 복합질문 실사용 테스트 중
  발견). 무관한 출처가 거절 답변에 그대로 붙는 결과로 이어짐.
- 2차: "항상 `[SOURCE_USED]`/`[NO_SOURCE]` 둘 중 하나로 시작하라"는 강제 이지선다로 교체.
- 2차 적용 직후 새 버그 발견: LLM이 `[SOURCE_USED]` 대신 띄어쓰기로 `[SOURCE USED]`라고
  쓰는 변형이 나와 완전 일치 비교로 못 잡음 → 정규식(`_MARKER_RE`, 밑줄/띄어쓰기·대소문자
  허용) 기반으로 재수정.

이 과정에서 배운 것: **"거절 문구를 휴리스틱으로 잡는" 접근(표현 패턴 매칭)은 표현이
다양해 계속 샌다는 게 이 프로젝트에서 두 번 확인됐다**(URL 문제 때도, 마커 문제 때도).
그래서 둘 다 "LLM 자유 출력을 패턴으로 추측"하는 대신 "고정된 토큰/구조로 결정론적으로
분기"하는 방향으로 수렴했다.

멀티쿼리 분해(4장)와 무관함은 A/B 검증(디컴포지션 On/Off 각 3회, 6/6 동일 재현)으로
따로 확인 — 겉보기엔 새 기능이 원인처럼 보였지만 실제로는 기존 코드의 독립적인 결함이었다.

- [pipeline_issue_history.md](pipeline_issue_history.md) 이슈 2·3

### 5.3 no-source에 대한 정중한 톤

시스템 프롬프트에 "근거 없으면 지어내지 말고 정직하게 모른다고 답하되, 친절하고 정중한
어투를 쓰라"는 원칙을 명시하고, few-shot 예시로 정체성 질문·인사말·범위 밖 질문 각각에
대한 정중한 응대 문구를 박아뒀다(`prompt_builder.py`). 하드코딩된 고정 거절 문구는 없고,
전부 LLM이 이 지시·예시를 따라 직접 쓰는 구조다.

**측정 방법론의 한계도 명시해둔다.** `measure_baseline.py`는 스스로를 "일회성 진단
스크립트(반복·통계 집계는 하지 않음 — 병목이 애매하면 그때 추가)"라고 규정한다. 즉 위

부족하다. 정식 성능 튜닝 단계(종합 프로젝트)에서는 반복 측정이 필요하다.

## 7. 종합 프로젝트로 넘기는 것 (미해결·범위 밖)

실측으로 확인은 했지만 이번 범위에서 못 끝낸 것들 — README 5~6장에 이미 정리돼 있지만,
"왜 남았는지" 관점에서 다시 정리한다.

1. **역할 라우팅 미구현** (2.5절) — 문제는 실측으로 확인(41개 역할 축), 로직 미착수.
2. **E2E 정량 평가 스크립트 부재** — `evaluate_pipeline.py`가 한 차례 구현·운용됐다가
   "파라미터 튜닝은 아직 이르다"는 팀 판단으로 롤백됨. 정답성/출처 정확도/환각률/거절
   품질 네 지표를 채점하는 스크립트는 재도입이 필요. 테스트셋 라벨 품질 자체는 이미
   검증돼 있음(`validate_testset.py`, `validate_golden_labels.py`).
3. **분해기·마커의 잔여 확률적 흔들림** (4·5.2절) — `temperature=0.2` 고정에서 오는
   구조적 한계. 프롬프트만으로 0으로 못 없앤다는 게 실측으로 확인됨.
4. **"~인지와 ~에 대해" 복합 서술 패턴** — few-shot을 늘리면 다른 케이스가 회귀하는
   딜레마, 후처리 검증 등 다른 접근 필요.
5. **리랭커·GPU 미검증** — CPU·현 설정에서는 손해로 결론 났지만, GPU/경량 설정 재검증은
   안 함(2.4절 재도입 조건 참고).
6. **웹 서비스 확장** (React+FastAPI+PostgreSQL+Qdrant 서버 모드) — `pipeline.py`의
   `rag_answer()`를 백엔드-AI 경계 인터페이스로 삼는 설계까지만 확정, 구현은 종합
   프로젝트 범위. 현재 `index_qdrant.py`는 컬렉션명이 `kdic_chunks_all` 고정 상수다 —
   README가 계획한 "코퍼스 해시를 컬렉션명에 넣어 코퍼스가 바뀌면 자동으로 새 컬렉션을
   쓰는" 방식(`kdic_chunks_a18f02c3` 등)은 아직 코드로 구현되지 않은 순수 계획 단계다.
   다만 인덱싱 전에 모든 청크의 `business_function`이 `inventory.BUSINESSES`에 정의된
   값과 정확히 일치하는지 하드 검증하는 가드(`validate_business_functions()`)는 이미
   있다 — Qdrant의 payload 필터가 완전 일치 문자열 매칭이라, 라벨이 하나라도 어긋나면
   그 문서가 필터링 검색에서 조용히 빠지는 사고를 막기 위함.

## 8. 이 회고에서 반복적으로 드러난 패턴

각 절이 개별 실험이지만, 몇 가지 방법론적 교훈이 여러 번 겹쳐 나왔다는 점은 따로 적어둘
가치가 있다.

- **초기 측정을 곧이곧대로 믿지 말 것.** 업무 필터(2.3절)와 사이트 커버리지(1절) 둘 다
  "낙관적으로 보이는 초기 수치"가 더 엄격한 재검증(leave-page-out, 자동 커버리지 대조)
  에서 뒤집혔다. intent 분류(3절)는 더 극단적인 사례다 — 운영 방식 그대로 측정하면
  100%(자기참조 누수), 자기 자신만 빼도 88.8%(형제질문 누수)로, "제대로 측정한 것처럼
  보이는" 두 단계를 더 거치고 나서야 정직한 수치(81.5%)가 나왔다. 데이터 누수는 한 번
  걷어냈다고 끝난 게 아니라 "또 다른 형태로 남아있지 않은지" 한 번 더 의심해야 한다는
  사례.
- **지표 하나만 보면 반대 결론이 나올 수 있다.** 표 청킹(1절)에서 MRR과 AnswerRecall이
  정반대 결론을 냈다 — 어떤 실패는 특정 지표 구조상 원리적으로 안 보인다.
- **LLM 자유 출력을 문자열 패턴으로 거르는 접근은 반복적으로 샜다.** URL 문제(5.1절)와
  마커 문제(5.2절) 둘 다 "표현을 추측해서 거르기"가 아니라 "LLM이 애초에 그걸 못 쓰게
  구조를 바꾸기" 또는 "고정 토큰으로 결정론적으로 분기하기"로 가서야 해결됐다.
- **같은 실패가 독립적으로 재현되면 그건 우연이 아니라 방식의 구조적 약점이다.** 복합
  질문 분해(4절)에서 1차 시도가 기각했던 실패를 2차 시도가 다시 만났을 때, 그게 우연이
  아니라 always-LLM 방식 자체의 특성임을 확인하고 나서야 올바른 대응(few-shot 보강)을
  찾을 수 있었다.
- **"형제 질문 누수"는 이 코퍼스의 구조 자체에서 나오는 문제라 한 번으로 안 끝났다.**
  같은 페이지에서 나온 질문끼리는 표현도 라벨(intent·business_function)도 비슷하다는
  성질이, intent 분류(3절)와 업무 분류(2.3절) **두 개의 서로 다른 실험에서 독립적으로**
  같은 방식(leave-one-out만으로는 부족, leave-page-out까지 가야 진짜 성능)으로 발견됐다.
  같은 원인이 여러 실험에 반복해서 스며든다는 걸 알고 나면, 다음에 새 분류기를 만들 때는
  leave-page-out을 처음부터 기본 평가 방식으로 깔아야 한다는 결론이 자연스럽게 나온다 —
  이번엔 매번 뒤늦게 발견했지만, 다음엔 미리 알고 시작할 수 있다.
- **수집(크롤링) 단계의 문제도 같은 결을 띤다 — "상한/기본값을 근거 없이 잡지 않는다."**
  표 청크 크기(1절, 3행), 동적 표 페이지 상한(1절, MAX_PAGES 20→300, 실제 289행 확인
  후 조정) 둘 다 "일단 적당한 값"을 넣었다가 실측(꼬리 프로브, 실제 행 수 대조)으로
  못이 박혔다. 값을 정하는 근거가 실측이어야 한다는 원칙이 데이터 계층과 알고리즘 계층
  양쪽에서 똑같이 적용됐다.
