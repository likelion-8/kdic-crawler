# 8월 28일 스탠드업 미팅

## 전일 진행 사항

### 1. 최종 발표자료 수정 및 발표 흐름 정리

기존에 작성한 발표자료 초안을 기준으로 전체 내용을 다시 확인하고, 발표 시간 안에 핵심 내용이 전달될 수 있도록 슬라이드 구성을 정리했다.

프로젝트에서 진행한 모든 실험과 기능을 나열하기보다는 **최종 RAG 구조를 결정하는 데 영향을 준 문제와 실험을 중심으로 발표 흐름을 정리**했다.

특히 발표 내용이 다음과 같은 흐름으로 자연스럽게 이어질 수 있도록 확인했다.

```text
문제 발견
→ 개선 방향 설정
→ 실험
→ 결과 비교
→ 최종 선택
→ 최종 파이프라인
```

중복되거나 발표에서 설명하기 어려운 내용은 줄이고, 각 슬라이드에서 전달해야 할 핵심 메시지가 명확하게 보이도록 수정했다.

---

### 2. 발표 스크립트 작성 및 내용 점검

수정한 발표자료를 기준으로 실제 발표에서 사용할 스크립트를 작성하고 전체 흐름을 점검했다.

슬라이드 내용을 그대로 읽기보다,

```text
왜 이 문제가 발생했는지
→ 어떤 방법을 시도했는지
→ 결과가 어떻게 나왔는지
→ 그래서 어떤 구조를 선택했는지
```

순서로 설명할 수 있도록 구성했다.

또한 실험 수치를 모두 설명하기보다 최종 판단에 직접 영향을 준 결과를 중심으로 설명하고, 최종 RAG 파이프라인과 관리자 페이지 및 서비스 시연까지 자연스럽게 이어지도록 발표 순서를 확인했다.

---

### 3. 발표자료와 실제 구현 내용 일치 여부 확인

발표자료에서 설명하는 기능과 현재 구현된 RAG 파이프라인이 서로 다르게 보이지 않도록 내용을 다시 확인했다.

Guardrail, OOS, Clarification, Rewriter, Retrieval, Reranking, Validation 등 주요 단계의 역할과 실행 순서를 기준으로 발표 내용과 실제 구조를 맞추고, 파이프라인 다이어그램에서도 핵심 흐름이 드러날 수 있도록 정리했다.

---

## 금일 진행할 사항

오늘은 **최종 발표자료를 한 번 더 다듬고, GitHub 정리와 아키텍처 작성까지 마무리하는 것**을 중심으로 진행한다.

### 1. 발표 PPT 최종 수정

현재 발표자료를 기준으로 실제 발표에 필요한 부분을 다시 확인하고 최종 수정한다.

주요 확인 내용:

* 슬라이드별 핵심 메시지 명확하게 정리
* 불필요하거나 중복되는 내용 제거
* 실험 결과 및 수치 최종 확인
* 발표 스크립트와 PPT 내용 일치 여부 확인
* 표와 그래프에서 필요한 결과가 잘 보이는지 확인
* 최종 파이프라인 설명 보완
* 관리자 페이지 및 서비스 시연 흐름 정리
* 발표 시간에 맞게 슬라이드별 설명 분량 조정

특히 앞부분의 실험 설명이 길어져 최종 파이프라인이나 서비스 시연 시간이 부족해지지 않도록 전체 분량을 조절할 예정이다.

---

### 2. GitHub 내용 수정 및 프로젝트 정리

최종 프로젝트 상태를 기준으로 GitHub에 정리된 내용을 확인하고 필요한 부분을 수정한다.

발표자료와 실제 프로젝트 설명이 서로 다르지 않도록 현재 구현된 기능과 최종 구조를 기준으로 내용을 맞출 예정이다.

주요 작업:

* 프로젝트 설명 및 README 내용 확인
* 현재 구현된 기능 기준으로 내용 수정
* 실행 방법 및 주요 기능 설명 확인
* 기존 내용 중 변경된 구조가 남아 있는지 확인
* 최종 RAG 파이프라인 설명 반영
* 발표자료와 GitHub 설명 간 내용 차이 확인
* 불필요한 내용이나 오래된 설명 정리

최종적으로 프로젝트를 처음 보는 사람도 **어떤 문제를 해결하기 위한 서비스인지, 어떤 구조로 구현되어 있는지** 이해할 수 있도록 정리하는 것이 목표다.

---

### 3. 최종 시스템 아키텍처 작성

현재 구현된 서비스 전체 구조를 한눈에 확인할 수 있도록 최종 아키텍처를 작성한다.

RAG 파이프라인 내부 흐름뿐 아니라 사용자 화면, 백엔드, 데이터 저장소, 검색 시스템, 관리자 기능 등이 실제 서비스에서 어떻게 연결되는지를 기준으로 정리할 예정이다.

아키텍처에서는 너무 세부적인 구현까지 모두 표현하기보다 발표와 프로젝트 설명에 필요한 수준에서 주요 구성요소와 데이터 흐름을 보여주는 것을 목표로 한다.

예상 흐름은 다음과 같이 정리한다.

```text
사용자 / 관리자
→ Frontend
→ Backend API
→ RAG Pipeline
→ Retrieval / Vector DB
→ LLM
→ Validation
→ Response

Backend
→ Database
→ 로그 / 피드백 / 관리자 기능
```

작성 이후 실제 코드 구조와 비교해 빠진 부분이나 잘못 표현된 부분이 없는지 확인한다.

---

### 4. 추가 고도화 사항 확인 및 개선

발표자료, GitHub, 아키텍처 정리가 끝난 이후 시간이 가능한 범위에서 현재 서비스에서 추가로 개선할 수 있는 부분을 확인한다.

새로운 기능을 크게 추가하기보다는 **현재 구현된 기능 중 실제 서비스 안정성이나 완성도를 높일 수 있는 부분**을 우선적으로 살펴볼 예정이다.

주요 확인 대상:

* RAG 파이프라인에서 남아 있는 예외 케이스
* 답변 품질이 불안정한 질문 확인
* OOS / Clarification / Validation 동작 확인
* 검색 및 리랭킹 결과 확인
* 반복 질문이나 캐시 처리 상태 확인
* 관리자 기능에서 남아 있는 작은 오류 확인
* 사용자 화면에서 개선이 필요한 부분 확인
* 발표 시연 과정에서 문제가 발생할 수 있는 부분 점검

추가 개선이 필요한 부분이 확인되면 발표와 서비스 안정성에 영향을 주는 항목부터 우선적으로 수정할 예정이다.

## Blocker / 논의 필요 사항

* 발표자료에 포함할 내용이 많기 때문에 최종 수정 과정에서도 핵심 내용 중심으로 분량을 유지할 필요가 있음
* GitHub에는 개발 과정의 이전 구조가 남아 있을 수 있어 현재 최종 구현 기준으로 설명을 다시 확인할 필요가 있음
* 아키텍처에 RAG 내부의 모든 Gate와 분기를 표현하면 복잡해질 수 있으므로 발표용 아키텍처에서는 주요 흐름 중심으로 표현 수준을 조정할 필요가 있음
* 추가 고도화는 새로운 기능을 무리하게 추가하기보다 현재 구현된 기능의 안정성과 완성도를 높이는 방향으로 우선순위를 정할 필요가 있음
* 최종 발표 직전 수정으로 기존 정상 동작에 영향을 주지 않도록 기능 변경 범위를 조절할 필요가 있음
