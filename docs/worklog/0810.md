# 8월 10일 스탠드업 미팅

## 전일 진행 사항

* 프로젝트 내 MD 문서의 파일명과 내용을 전반적으로 점검하고, 중복되거나 오래된 내용을 정리하여 현재 코드 및 파이프라인 상태와 일치하도록 수정
* 현재 RAG 파이프라인의 단계별 토큰 사용량을 측정하고, 불필요한 토큰 사용을 줄이기 위한 최적화 방향 검토
* 답변 생성 외 출처 재확인 및 멀티쿼리 과정에서 발생하는 토큰 사용 비중 확인
* 리랭킹 적용 결과를 기존 검색 결과와 비교하여 현재 파이프라인에서의 적용 가능성과 성능 영향 검토
* 관리자 기능의 2·3주차 구현 범위와 작업 순서 재정리
* 관리자 인증·문서 관리·재적재 기능 중 AI/RAG 프로젝트에 필요한 핵심 기능과 후순위 운영 기능 구분
* 신규 문서 반영 시 기존 검색 데이터를 바로 덮어쓰지 않고 별도 검색 버전을 생성한 뒤 평가 후 활성화하는 방향 검토
* 관리자 문서 관리 기능과 재적재 파이프라인 간 의존성 확인

## 금일 진행할 사항

### 1. No-source 처리 방식 결정

현재 RAG 답변에서 검색 근거가 부족하거나 실제 답변에 활용할 수 있는 출처가 없는 경우의 처리 방식을 확정한다.

논의 내용:

* 검색 결과가 없을 때 답변 처리 방식
* 검색 결과는 있지만 답변 근거로 사용하기 어려운 경우의 처리 방식
* 출처 표시 여부와 답변 생성 여부 기준
* 기존 Source Verifier 구조와의 연결 방식
* No-source 판정 시 로그에 저장할 정보

결정 후 현재 RAG 파이프라인의 답변·출처 처리 흐름에 반영할 수 있도록 정리한다.

---

### 2. 이번 주 작업 범위 및 역할 분담 확정

관리자 기능 구현에 앞서 이번 주 완료 범위를 팀 단위로 확정한다.

우선 구현 대상:

```text
관리자 로그인·세션·권한
→ 관리자 활동 로그 최소 구현
→ 검색 데이터 버전 구조 확정
→ pipeline_jobs 기반 구현
→ 기존 문서·청크 조회
→ 검색·필터
→ 문서 상세·연결 청크 조회
```

후순위 작업:

```text
Redis·ARQ Worker
재적재
Smoke 평가
검색 버전 활성화
Rollback
대시보드
```

복잡한 멱등키·재인증·개인정보 마스킹 등 운영 보안 기능은 현재 프로젝트의 AI/RAG 구현 우선순위를 고려하여 후순위로 둔다.

---

### 3. 관리자 로그인·세션·권한 구현

관리자 화면 접근을 위한 최소 인증 구조를 구현한다.

대상 API:

```text
POST /api/admin/login
POST /api/admin/logout
GET  /api/admin/session
```

구현 범위:

* 관리자 계정 정보 확인
* 비밀번호 검증
* 로그인 성공 시 관리자 세션 생성
* HttpOnly 쿠키를 이용한 세션 유지
* 현재 로그인 관리자 조회
* 로그아웃 시 세션 제거
* 로그인하지 않은 사용자의 관리자 API 접근 차단
* 관리자 API에서 공통으로 사용할 인증 의존성 구현

이번 단계에서는 복잡한 세션 만료 정책이나 재인증 기능보다 관리자 화면과 API를 실제로 연결할 수 있는 최소 인증 흐름 완성을 우선한다.

---

### 4. 관리자 활동 로그 최소 구현

관리자가 주요 기능을 실행했을 때 누가 어떤 작업을 수행했는지 확인할 수 있도록 기본 활동 로그를 구현한다.

예시:

```text
LOGIN
LOGOUT
KNOWLEDGE_LIST_VIEW
DOCUMENT_PREVIEW
DOCUMENT_APPROVE
DOCUMENT_REJECT
DOCUMENT_DELETE_REQUEST
PIPELINE_JOB_CREATE
```

최소 저장 항목:

* 관리자 ID
* 작업 종류
* 작업 대상
* 성공 여부
* 발생 시간

세부 저장 범위는 팀 회의를 통해 확정한다.

---

### 5. 검색 데이터 버전 관리 방식 확정

신규·삭제 문서를 검색 시스템에 반영할 때 기존 운영 데이터를 바로 덮어쓰지 않도록 검색 버전 관리 구조를 결정한다.

논의 및 확정 항목:

```text
index_version
active_version
Rollback 방식
평가 실패 시 기존 버전 유지 방식
```

기본 방향:

```text
현재 운영 버전
        ↓
새 검색 버전 생성
        ↓
정합성 및 Smoke 평가
      ↙       ↘
   통과        실패
    ↓           ↓
새 버전 활성화   기존 버전 유지
```

3주차 재적재 Worker 구현 전에 DB 구조와 검색 코드에서 버전을 어떤 방식으로 구분할지 확정한다.

---

### 6. `pipeline_jobs` 테이블 및 Jobs API 스텁 구현

향후 재적재 작업과 관리자 화면의 작업 상태 조회에 사용할 Job 관리 기반을 구현한다.

대상 기능:

```text
Job 생성
Job 목록 조회
Job 상세 조회
Job 상태 저장
```

대상 API 예시:

```text
POST /api/admin/jobs
GET  /api/admin/jobs
GET  /api/admin/jobs/{job_id}
```

이번 단계에서는 실제 Redis·ARQ Worker를 실행하지 않고 DB에 Job을 생성하고 조회할 수 있는 API 계약과 기본 구조만 구현한다.

---

### 7. 기존 문서·청크 조회 API 구현

Supabase에 저장된 기존 운영 문서와 청크를 관리자 화면에서 조회할 수 있도록 읽기 API를 구현한다.

대상 데이터:

```text
documents
document_chunks
```

구현 범위:

* 기존 문서 목록 조회
* 기존 청크 목록 조회
* 페이지네이션
* 활성 문서 기준 조회
* 관리자 인증 적용
* 프론트 API 계약에 맞는 응답 구조 반환

---

### 8. 문서 검색·필터 및 상세 조회 구현

관리자가 기존 문서를 쉽게 확인할 수 있도록 검색과 필터 기능을 추가한다.

검색 및 필터:

```text
문서 제목
URL
업무 분류
```

상세 조회:

```text
문서 기본 정보
→ 해당 문서와 연결된 document_chunks 조회
```

최종적으로 다음 흐름이 가능하도록 구현한다.

```text
관리자 로그인
→ 문서 목록 조회
→ 제목·URL 검색
→ 업무 분류 필터
→ 문서 선택
→ 문서 상세 조회
→ 연결된 청크 확인
```
