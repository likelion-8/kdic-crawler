## 금일 진행할 사항

오늘은 개별 기능 구현보다 **팀 전체가 현재 백엔드와 AI 파이프라인을 함께 검토하고, 남은 개선 사항의 적용 여부와 우선순위를 결정**한다.

### 1. 관리자 백엔드 전체 구현 검증

현재까지 구현된 관리자 백엔드 기능을 실제 코드와 API 흐름 기준으로 함께 확인한다.

주요 확인 항목:

* 관리자 인증·세션·권한 처리
* 문서·청크 조회
* 신규 URL 검증 및 Preview
* 변경 요청 생성·승인·반려
* 관리자 활동 로그
* 대화 로그·피드백 조회
* 개인정보 마스킹
* API 예외 처리 및 Response 구조

단순히 동작 여부만 확인하는 것이 아니라, **팀원 모두가 전체 백엔드 흐름을 이해할 수 있도록 주요 로직을 함께 살펴본다.**

---

### 2. 현재 RAG 파이프라인 구조 재점검

현재 실제 코드가 어떤 순서로 동작하고 있는지 다시 정리하고, 멘토링에서 논의한 개선 구조와 비교한다.

현재 구조와 아래 개선 방향을 비교한다.

`사용자 질문`

→ `Out-of-Scope 판단`

→ `Query Planning / Multi-Query`

→ `Retrieval`

→ `Reference Validation`

→ `Answer Generation`

각 단계가 현재 코드에서 어떤 역할을 담당하고 있는지 확인하고, 중복되거나 역할이 섞여 있는 부분을 정리한다.

---

### 3. `NO_SOURCE` / Out-of-Scope 구조 결정

현재 `SOURCE / NO_SOURCE` 판단 로직을 다시 확인하고 역할을 구분한다.

논의할 내용:

* Out-of-Scope를 어느 단계에서 판단할지
* 단순 인사·서비스 범위 외 질문 처리 방식
* `NO_SOURCE`라는 상태를 계속 사용할지
* Reference가 없는 경우와 Reference가 부적절한 경우를 어떻게 구분할지
* 답변 생성 전 Reference Validation으로 변경할지
* Validation 실패 시 재검색 여부 및 최대 횟수

최종적으로 **질문 범위 판단과 검색 결과 검증의 책임을 명확하게 분리하는 것**을 목표로 한다.

---

### 4. Reranking 적용 여부 재검토

기존 실험에서는 Reranker의 성능 대비 CPU Latency 문제로 적용하지 않았지만, 현재 Pipeline 개선 과정에서 다시 필요성을 검토한다.

확인할 내용:

* 현재 Dense / Hybrid 검색 결과만으로 충분한지
* Reference Validation 이전에 Reranking이 필요한지
* Reranker를 추가했을 때 실제 품질 개선 폭
* Latency 증가 대비 얻는 효과
* 현재 프로젝트 규모에서 적용할 가치가 있는지

필요성이 낮다면 기존처럼 사용하지 않고, **적용하지 않은 이유와 실험 근거를 명확하게 정리**한다.

---

### 5. Supervisor / Validator 구조 검토

복합 질문이나 검색 결과 검증 과정에서 Supervisor 역할이 필요한지 검토한다.

검토 구조:

`원 질문`

→ `분해 Query`

→ `검색 결과`

→ `Validator / Supervisor`

→ `충분하면 답변 생성`

→ `부족하면 재검색 또는 종료`

ReAct와 같은 Agent 구조를 그대로 적용하기보다는,

* 검색 결과가 원 질문을 충분히 커버하는지
* Multi-Query 분해가 적절했는지
* 재검색이 필요한지

를 판단하는 **가벼운 Validator 역할만 현재 프로젝트에 적용할 수 있는지** 검토한다.

---

### 6. Validation용 Context Summary 검토

Reference Validation 과정에서 원문 Chunk 전체를 LLM에 다시 전달하는 현재 방식의 Token 사용량을 줄일 수 있는지 논의한다.

검토할 구조:

`원문 Chunk`

→ `Validation용 Summary / Metadata`

→ `Reference Validation`

→ `적합한 경우 원문 Chunk로 Answer Generation`

논의할 내용:

* Summary에 어떤 정보를 포함할지
* 문서 제목·업무 분류·Chunk 주제 등 Metadata 활용 여부
* Summary를 적재 시 미리 생성할지
* 런타임에서 생성할지
* 원문 대비 Validation 정확도가 유지되는지
* 실제 Token 절감 효과를 어떻게 측정할지

적용 여부는 추측으로 결정하지 않고 **기존 방식과 비교 실험 후 판단**한다.

---

### 7. Langfuse 적용 범위 결정

현재 RAG Pipeline에서 어떤 단계를 Langfuse로 Trace할지 정리한다.

우선 확인할 단계:

* Query Planning
* Intent / Question Type
* Multi-Query
* Retrieval
* Reference Validation
* Answer Generation

확인할 주요 지표:

* 단계별 Latency
* Prompt / Model
* Input / Output Token
* 전체 Token 사용량
* LLM 호출 횟수
* 검색 결과 및 Reference
* 오류 발생 단계

관리자 Dashboard와 역할을 분리하고, Langfuse는 **개발자용 RAG Debugging·Evaluation·Trace 도구**로 활용한다.
