### 1. Supabase PostgreSQL 및 pgvector 구현 방식 확정

* 기존 Qdrant 기반 벡터 검색 구조를 Supabase PostgreSQL과 pgvector 기반 구조로 전환함
* Supabase 접근 방식을 다음과 같이 확정함

```text
DB 접근: SQLAlchemy + psycopg3
접속 방식: Supabase Transaction Pooler
벡터 검색: Exact Search
거리 계산: Cosine Distance
벡터 인덱스: 미적용
```

* 현재 검색 대상이 494개 Chunk로 규모가 작아 HNSW와 IVFFlat을 적용하지 않고 전체 벡터를 비교하는 Exact Search를 사용함
* 기존 Qdrant의 `Distance.COSINE` 방식과 동일하게 pgvector의 코사인 거리 연산자를 사용함
* 기존 검색·필터링·라우팅 로직을 유지하기 위해 Supabase 전용 VectorStore 대신 SQLAlchemy 기반 직접 접근 방식을 적용함

### 2. Supabase 정식 테이블 구조 구축

* 초기 pgvector 검증용 임시 테이블을 제거하고 실제 프로젝트에서 사용할 정식 스키마를 구축함
* 다음 6개 테이블을 생성함

| 테이블                     | 용도                        |
| ----------------------- | ------------------------- |
| `documents`             | KDIC 페이지 원문과 문서 메타데이터 저장  |
| `document_chunks`       | 검색용 Chunk와 1024차원 임베딩 저장  |
| `golden_set`            | 질문 유형 분류와 내부 검증용 기준 질문 저장 |
| `test_set`              | 최종 평가용 질문 저장              |
| `rag_runs`              | 질문·답변 실행 기록 저장            |
| `rag_retrieval_results` | 검색 후보와 최종 선택 결과 저장        |

* 기존 `page_id`, `chunk_id`를 유지해 평가 데이터 및 기존 코드와의 연결 관계를 보존함
* `documents`와 `document_chunks`를 1:N 관계로 구성함
* `documents.is_active` 변경 시 연결된 `document_chunks.is_active`도 변경되도록 동기화 구조를 추가함
* 비활성화된 문서의 Chunk가 검색 결과에 포함되지 않도록 처리함

```text
→ 하위 질문 분해
→ 하위 질문별 Supabase 검색

```

```text

out_of_scope = true
sources = []
attachments = []
```

#### 오류 발생

```text
status = ERROR
answer = 사용자용 오류 안내
error.code = 오류 코드
error.retryable = 재시도 가능 여부
```

* 기존 문자열 답변 결과와 구조화 답변의 `answer` 본문이 일치하는지 확인
