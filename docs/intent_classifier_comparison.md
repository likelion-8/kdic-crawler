# Intent 분류 최종 보고서 — 4자 비교 (TF-IDF vs HyperCLOVA X vs OpenAI gpt-4o-mini/gpt-5.4-mini)

정보성(informational) vs 민원성(civil_petition) intent 분류 방식을 결정하기 위한 전체 실험·비교
정리다. 사고 과정(왜 이 방식들을 시도했는지), 각 실험의 가설과 실제 결과, 3자 비교 수치, 종합
결론(채택 제안)을 담는다. **실제 운영 코드(query_classifier.py) 교체는 이 문서에서 "제안"만
하고, 코드 반영은 다음 작업으로 분리한다.** (작성일: 2026-08-02)

---

## 1. 전체 사고 과정 (시간순)

### ① Dense 1-NN → 형태소 TF-IDF (80.5% → 89.6%)
처음엔 testset_all 질문을 임베딩해 사용자 질문과 가장 유사한 1개의 라벨을 쓰는 **코사인 1-NN**
방식이었다(Leave-Page-Out 80.5%). intent 신호가 도메인 명사가 아니라 **어미·문장구조**에 있다는
판단에서, Kiwi 형태소 + TF-IDF + LogisticRegression으로 교체해 **89.6%(Leave-Page-Out 개발셋)**
까지 올렸다.

### ② held-out 재검증에서 하락 발견 (89.6% → 77.2%)
멀티쿼리 처리 로직을 붙이며 튜닝에 쓰지 않은 held-out(testset_pipeline)으로 재검증하니
**77.2%**로 떨어졌다. 개발셋(89.6%)과의 격차는 held-out에 **구어체·오타·비정형 표현**이 섞여
있기 때문. 멘토 피드백("가벼운 방법부터 순서대로 검증")에 따라 baseline 최적화부터 시도했다.

### ③ Kiwi 설정 조사 (docs/kiwi_config_investigation.md)
도메인 복합명사(착오송금 등)가 형태소로 쪼개지고 있었으나(착오/NNG + 송금/NNG), intent를 가르는
진짜 신호는 **절차어휘(신청·접수·방문) + 어미**였다. 구어체("어케해"가 어/IC로 오분석)가 정확도
하락의 더 직접적 원인으로 추정됐다. (Kiwi 인스턴스 3곳 모두 옵션 없는 기본값·사용자 사전 없음.)

### ④ N-gram 실험 — 가설 기각 (docs/intent_baseline_optimization.md)
"절차어휘+어미 조합을 n-gram으로 잡으면 개선된다"는 가설을 세웠으나 **결과는 반대**:
unigram 89.6% > bigram 86.0% > trigram 83.5%. 조합 특징 자체는 상위에 잡혔지만
(예: "신청/NNG 하/XSV"), **특징 수가 756→2275→3567로 폭증하는데 학습 데이터가 655건뿐이라
과적합 손해가 조합의 이득보다 컸다.** → n-gram 미채택.

### ⑤ 사용자 사전 실험 — intent엔 미미 (+0.6%p)
도메인 복합명사 통짜 등록은 +0.6%p(노이즈 범위)로 intent엔 유의미하지 않았다. **BM25 검색 쪽엔
유의미할 수 있으나, 검색 알고리즘(Dense/Hybrid 라우팅, α=0.4 등)은 이미 별도 실험으로
확정·검증이 끝난 영역이라 이번 범위에서 제외**하고, 검색용 사용자 사전 적용은 향후 별도 과제로
백로그에 남긴다.

### ⑥ baseline 확정
**intent 공식 baseline = Kiwi(기본, unigram)+TF-IDF+LogReg, 89.6%(개발) / 77.2%(held-out)**.
현재 운영 코드가 이미 이 설정이라 baseline 코드 변경은 없다. 이 값이 아래 3자 비교의 기준선이다.

## 2. N-gram이 성능을 떨어뜨린 이유 (상세)

n-gram의 조합 특징 자체는 **유효했다** — bigram 상위 특징에 `신청/NNG 하/XSV`(-3.1),
`방문/NNG 접수/NNG`(-0.99), `주/VX 어/EF`(동사+어미 조합) 등이 실제로 잡혔다. 문제는 **과적합**이다:
- 특징 수: unigram 756 → bigram 2275 → trigram 3567
- 학습 데이터: 655건뿐
- 데이터 대비 특징이 폭증하면 희소한 n-gram에 모델이 과적합해, unigram이 개별 토큰
  (`신청/NNG`, `어/EF`)만으로 이미 확보한 신호를 넘어서지 못하고 오히려 일반화가 나빠진다.

즉 "조합이 무의미해서"가 아니라 "데이터가 그 많은 조합 특징을 감당할 만큼 크지 않아서" 손해였다.

## 3. 사용자 사전을 이번 범위에서 제외한 이유

1. **intent엔 효과 미미** — +0.6%p는 eval 수십 건 기준 1건 수준으로 노이즈 범위. intent 신호가
   도메인 명사가 아니라 절차어휘+어미에 있다는 조사 결과와도 일치(명사 통짜화의 이득이 작음).
2. **검색은 이미 확정된 영역** — 사용자 사전이 도움 될 만한 곳은 BM25 검색인데, 검색
   알고리즘·파라미터는 별도 실험으로 확정·검증이 끝났다. 지금은 intent 고도화에 집중하기로 결정.
3. → 검색용 사용자 사전은 **향후 별도 과제(백로그)**로 남김.

## 4. Structured Output 개념 (LLM 방식의 전제)

- **이진분류 기능이 아니라 '출력 형식을 제약'하는 기능**이다. 실제 의도 판단은 LLM의 언어이해가
  수행하고, structured output은 그 출력이 반드시 정해진 스키마(여기선 두 라벨 중 하나)가 되도록
  강제할 뿐이다.
- **확률론적**이다 — 같은 입력도 100% 동일 출력을 보장하지 않는다(TF-IDF+LogReg의 결정론적
  특성과 다름). 본 실험에선 temperature=0으로 최대한 결정적으로 두고, 일관성을 별도 측정했다.
- 기존 **LogReg의 '학습된 가중치' 역할을, 사람이 작성한 시스템 프롬프트(intent 정의 + 혼동 예시)**
  가 대신한다(few-shot 기법의 응용). 본 실험은 HCX·OpenAI가 **완전히 동일한 시스템 프롬프트·스키마**
  (`src/intent_llm_common.py`)를 쓰도록 해 공정 비교했다.
- **파이프라인상 위치**: 최종 답변 생성(HyperCLOVA X 호출)과 별개인, 더 앞선 질의 전처리 단계.
  도입 시 질문 1건당 API 호출이 1회 → 2회(intent 분류 + 답변 생성)로 늘어난다.

### ⚠️ 중요 제약: HCX는 native structured output을 쓰지 못했다
- langchain-naver 0.1.1의 `with_structured_output()`이 CLOVA API가 받지 않는 파라미터
  (`parallel_tool_calls`·`response_format`·`reasoning`)를 보내 **모든 method가 400 에러**
  (모델 무관 — HCX-DASH-002·HCX-007 둘 다 실패). **모델 한계가 아니라 langchain 래퍼 호환성 문제.**
- 그래서 HCX는 **프롬프트-JSON 방식**(langchain으로 호출하되 프롬프트로 JSON 형식을 지시하고
  응답을 파싱)으로 대체했다. HCX-007은 이 지시를 안정적으로 따랐다.
- **결과적으로 OpenAI(native SO, API가 스키마 강제) vs HCX(프롬프트-JSON, 모델이 형식을 따라줌)
  라는 비대칭이 있다.** 진짜 native 비교가 필요하면 CLOVA API 직접 호출(OpenAI 호환 엔드포인트)
  또는 langchain-naver 업그레이드가 필요하며, 이는 운영 도입 판단 시 별도 고려사항이다.

## 5. 최종 비교 결과 (held-out testset_pipeline, 89문항)

- 데이터: intent 라벨 있는 89행 (informational 66 / civil_petition 23), 오타 서브셋 30, 구어체·모호 서브셋 16
- baseline = 운영 분류기(query_classifier.classify_intent), 나머지는 API 호출
- **2회에 걸쳐 실험**: 처음엔 3자(baseline/HCX/gpt-4o-mini), 이후 **gpt-5.4-mini를 추가해 4자로 확장**
  (기존 gpt-4o-mini 결과 유지). 아래 표는 **최종(4자) 재실행 값**이다.

| 지표 | ① TF-IDF (baseline) | ② HCX-007 (프롬프트-JSON) | ③ gpt-4o-mini (native SO) | ④ **gpt-5.4-mini (native SO)** |
|---|---|---|---|---|
| **전체 정확도** | 78.6% | 91.0% | 87.6% | **92.1%** |
| 오타 서브셋(30) | 76.7% | **96.7%** | 93.3% | 93.3% |
| 구어체·모호(16) | 68.8% | 75.0% | 68.8% | **93.8%** |
| civil_petition F1 | 0.642 | 0.818 | 0.776 | **0.857** |
| 주 오분류 | info→civil 13 / civil→info 6 | info→civil 3 / civil→info 5 | info→civil 7 / civil→info 4 | **info→civil 5 / civil→info 2** |
| **응답시간(평균/중앙/최대)** | 로컬(즉시) | 5.56 / 4.75 / **62.2초** | **0.68 / 0.64 / 1.66초** | 0.85 / 0.83 / 1.38초 |
| 일관성(3회 반복) | 결정론적 | 100% | 100% | 100% |
| 비용(89문항, 추정) | $0 (로컬) | CLOVA 요금 확인 필요(DASH보다 비쌈) | **~$0.006** | 확인 필요(4o-mini보다 높을 수 있음) |
| 오류 | 0 | 0 | 0 | 0 |

### 핵심 관찰
- **모든 LLM 방식이 baseline(78.6%)을 크게 앞선다** — 특히 baseline이 약했던 오타(76.7%)·구어체(68.8%)에서.
  "가벼운 방법으로 안 잡히던 구어체를 LLM이 잡는다"는 기대가 수치로 확인됐다.
- **gpt-5.4-mini가 종합 1위.** 전체 정확도 92.1%(HCX와 동급 최고)이면서 **구어체 93.8%로 압도적 1위**,
  civil_petition F1도 0.857로 최고. 게다가 **응답시간 0.85초로 HCX(5.56초)의 약 6.5배 빠르고**, HCX의
  최대 지연 62초 같은 리스크가 없다(최대 1.38초).
- **gpt-4o-mini(87.6%)**는 가장 빠르고(0.68초) 저렴하지만 구어체(68.8%)는 baseline 수준 — 구어체가
  중요하면 부족.
- **HCX-007**은 정확도는 높지만(91.0%) **느리고(평균 5.56·최대 62.2초) native SO 미지원(프롬프트-JSON
  우회)**이라 운영 지연·구현 제약이 크다.
- 일관성 전부 100%(temperature=0), 오류 0.

### LLM 확률론적 특성 관찰 (문서화 포인트)
HCX-007은 1차 실험 92.1%/구어체 81.3% → 2차(4자) 재실행 91.0%/구어체 75.0%로 값이 흔들렸다.
같은 입력·temperature=0에도 출력이 100% 고정되지 않는 **LLM의 확률론적 특성** 때문이며(특히 구어체
16건 같은 소표본에선 1~2건 차이로 %가 크게 움직임), 결정론적 TF-IDF와의 본질적 차이다. 단일 질문
반복(일관성 테스트)은 100%였으나, 셋 전체 재실행 시엔 소폭 변동이 있음에 유의.

## 6. 종합 결론 및 채택 제안

**gpt-5.4-mini가 정확도·구어체·속도를 동시에 만족하는 명확한 최선**으로 나타났다. 이전 3자 단계에서
"HCX는 정확하지만 느림, gpt-4o-mini는 빠르지만 구어체 약함"으로 애매했던 것이, 더 강한 OpenAI 모델을
넣자 해소됐다.

| 방식 | 장점 | 단점 |
|---|---|---|
| ① TF-IDF (baseline) | 무료·즉시·결정론·오프라인 | 정확도 78.6%, 구어체 취약(68.8%) |
| ② HCX-007 | 높은 정확도, 기존 CLOVA 인프라 재사용 | 느림(평균 5.56·최대 62초), 비용 큼, native SO 미지원 |
| ③ gpt-4o-mini | 가장 빠르고(0.68초) 매우 저렴, native SO | 구어체 baseline 수준(68.8%) |
| ④ **gpt-5.4-mini** | **정확도·구어체·클래스F1 모두 최고 + 빠름(0.85초)·native SO** | 외부 벤더 의존, 비용 4o-mini보다 높을 수 있음(확인 필요) |

### 제안
1. **1순위: gpt-5.4-mini** — 전체 92.1%·구어체 93.8%로 최고이면서 0.85초로 빠르고 native structured
   output이라 형식 보장까지 된다. HCX의 느림·native 미지원 문제가 없고, gpt-4o-mini의 구어체 약점도
   해결한다. **성능·속도·안정성 종합 최선.**
2. **차선(외부 벤더 회피 시): HCX-007** — 정확도는 준수하나 응답 지연(최대 62초)과 native SO 미지원이
   운영 리스크. 지연을 감내하고 벤더를 CLOVA로 통일하려는 경우에만.
3. **비용 극단 우선: gpt-4o-mini** — 구어체가 덜 중요한 경우의 저비용 선택.
4. **운영 구조**: 어느 쪽이든 **답변 생성은 DASH-002 유지, intent 분류만 상위/외부 모델**로 두는
   분리 구조가 비용 면에서 합리적(질의당 API 2회). `.env`의 `INTENT_CLOVA_MODEL`·`OPENAI_INTENT_MODEL`
   처럼 모델을 설정으로 분리하면 파이프라인 코드 변경 없이 적용 가능하다.

### OpenAI(gpt-5.4-mini) 채택 시 고려사항 — 성능은 최선이나 아래를 함께 판단할 것
성능만 보면 gpt-5.4-mini가 명확한 최선이지만, "intent는 OpenAI + 답변생성은 HyperCLOVA X"라는
2-벤더 구성이 되면서 다음을 검토해야 한다. (참고: **코드 유지보수/통일성 자체는 큰 문제가 아니다** —
호출부가 `classify_intent()`·`call_hyperclova()`로 이미 모듈 격리돼 있어 벤더가 둘이어도 각자
캡슐화되며, pipeline은 어느 벤더인지 모른다.)

1. **🔴 데이터 국외 이전 (공공기관이라 가장 중요).** intent 분류를 OpenAI에 보내면 사용자 질문이
   OpenAI(해외) 서버로 전송된다. HyperCLOVA X는 국내(네이버)라 데이터가 국내에 머문다. KDIC는
   공공기관이므로 **질문(개인정보 포함 가능)을 해외 LLM에 보내는 것이 규정상 허용되는지**가 성능과
   무관하게 선행 조건이다. **규정상 불가하면 gpt-5.4-mini는 못 쓰고, 국내 대안인 HCX-007로 가야 한다.**
2. **🟡 외부 벤더 의존성 추가.** 지금은 CLOVA 하나에만 의존하는데 OpenAI를 넣으면 의존 벤더가 2개.
   OpenAI API 장애·요금정책 변경·모델 deprecated(gpt-5.4-mini도 언젠가 종료)에 노출되고, 관리할
   API 키·크레딧·사용량 모니터링 지점이 2곳이 된다.
3. **🟢 인증·SDK 이원화(부담 작음).** CLOVA(`langchain-naver`)와 OpenAI(`openai` SDK) 두 라이브러리를
   각각 버전 관리해야 한다(각자 업데이트·호환성 이슈 — langchain-naver 0.1.1 버그가 그 예). 다만
   이미 `.env`·requirements.txt로 둘 다 관리 중이라 실질 부담은 작다.
   (※ SDK = Software Development Kit. API를 코드에서 쉽게 호출하도록 벤더가 배포한 라이브러리.)

→ **정리**: gpt-5.4-mini가 성능·속도 최선이나 **데이터 국외 이전 규정 검토가 반드시 선행**되어야 하며,
규정상 불가할 경우 **HCX-007이 국내 대안**이다. 코드 통일성은 채택을 막는 요인이 아니다.

### 유의
- held-out 89문항(구어체 16·오타 30)은 표본이 작아, gpt-5.4-mini 92.1% vs HCX-007 91.0%의 근소한
  차이가 더 큰 셋에서도 유지되는지는 재확인이 필요하다. 특히 구어체 서브셋(16건) 수치(93.8% vs 75.0%
  vs 68.8%)는 건수가 적어 방향 신호로만 볼 것.
- LLM은 확률론적이라 재실행 시 값이 소폭 흔들린다(HCX 1차 92.1% → 2차 91.0%). 최종 채택 전 더 큰
  held-out으로 여러 번 측정해 안정적 우열을 확인하는 것을 권한다.
- HCX 프롬프트-JSON은 native SO가 아니라, 스키마 미준수(엉뚱한 라벨) 가능성이 이론상 남는다
  (본 실험 89건에선 폴백 0건). native가 필요하면 CLOVA 직접 호출/라이브러리 업그레이드 검토.
