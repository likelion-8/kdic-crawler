# 파이프라인 성능 평가 — 리랭킹 도입 전 베이스라인

KDIC RAG 챗봇의 확정된 파이프라인을 held-out 테스트셋으로 평가한 **초기 성능(베이스라인)** 기록이다.
리랭킹을 도입하기 전 상태를 측정해두고, 다음 주 리랭커 도입 후 **같은 코드로 재측정**해 향상폭을 비교한다.

- 측정일: 2026-07-30
- 평가 데이터: `data/testset/testset_pipeline.jsonl` (89문항, held-out)
- 설정: 리랭킹 **Off**, `K_CANDIDATES=20`, `K_FINAL=5`, 임베딩 `dragonkue/BGE-m3-ko`, LLM `HyperCLOVA X`
- 평가 코드: `src/eval_pipeline_retrieval.py`(1단계), `src/eval_pipeline_generation.py`(2단계)
- 결과 원본: `results/pipeline_holdout/retrieval_rerank_off.json`, `generation_rerank_off.json`

---

## 0. 이 평가의 성격 — 개발(dev)용과 다른 "최종(test)" 평가

지금까지의 Recall 측정(임베딩 모델 선정, 청킹, K, intent 분류 방식, link_guide 하이브리드 등)은
**"어떤 방식을 쓸지 고르기 위한 개발(dev)용" 평가였고, 주로 `testset_all.jsonl`로 했다.** 그런데
`testset_all`은 이 선택·분류기 학습에 이미 다 쓰여서 **오염(본 데이터)** 되었다. 그 데이터로 성능을
재면 부풀려진다(intent 분류에서 100% → 실제 81.5%로 확인된 바 있음).

이 평가는 성격이 다르다. **확정된 시스템이 "처음 보는 질문"에 실제로 얼마나 하는지 재는 최종(test)
평가**이며, 그래서 튜닝에 한 번도 쓰지 않은 held-out 세트 `testset_pipeline.jsonl`을 쓴다.

> ⚠️ **testset_pipeline은 앞으로도 "확인용"으로만 아껴 쓴다.** 이 점수를 보고 파라미터를 바꾼 뒤
> 같은 셋으로 재측정하는 것을 반복하면 이 셋도 오염된다(사람이 개입한 오버피팅). 튜닝은
> `testset_all`/별도 dev셋으로 하고, testset_pipeline 재측정은 큰 변경 후 가끔만 한다.

## 1. 검색 · 분류 평가 (1단계, LLM 호출 없음)

## 2. 생성(답변) 평가 (2단계, HyperCLOVA X 호출)

전체 89문항(답변형 79 + out-of-scope 10). 문항당 HCX 1회 이상 호출.

### 신뢰할 수 있는 지표 (객관적)

| 지표 | 값 | 의미 |
|---|---|---|
| 생성 성공률 | 100% (89/89) | 크래시 없이 답변 생성 |
| 평균 응답시간 | 5.2초 | (리랭킹 Off 기준) |
| 출처링크 포함률(답변형) | 0.380 | 답변에 출처 URL이 붙은 비율 |
| 출처 정확률(답변형) | 0.317 | 정답 페이지의 실제 URL이 답변에 있는 비율 |

### 참고 지표 (프록시 — 과신 금지)

| 지표 | 값 | 주의 |
|---|---|---|
| must_include 커버리지 | 0.526 | **엄격한 하한선** — 의미상 맞아도 표현이 다르면 실패(예: "금융시스템의 안정성" vs must "금융제도의 안정성"). 실제 정확도는 이보다 높음 |
| oos 적절 거절률 | 0.40 | 거절을 문자열 마커로 판정 → 부정확. 사람 확인 필요 |

> **설계 원칙**: 문자열로 '의미'를 자동 판정하는 지표(must_include·거절률)는 계속 새어 신뢰할 수 없다.
> 이런 항목은 하한선/참고로만 보고, 애매한 것은 `manual_review`(43건, 결과 json에 저장)를 사람이
> 직접 확인하는 것을 진짜 앵커로 삼는다.

## 3. 종합 — 좋은 점과 짚을 점

### 좋은 점
- **검색이 견고하다.** Recall@5 0.922 — LLM에 넣는 top-5 안에 정답 페이지가 92% 들어온다.
  리랭킹 없이도 이 정도라 1차 검색(BGE-m3-ko Dense)이 강하다.
- **오타에 완벽히 강하다.** 원본↔오타 Recall@5 하락 0.000. Dense 임베딩이 의미 기반이라 오타 영향 없음.
- **안정성.** 생성 성공률 100%, 평균 5.2초.

### 짚을 점 (개선 대상)
1. **🔴 출처 누락 (핵심 이슈).** 답변형 79개 중 39개가 거절도 아닌데 출처 URL이 안 붙는다.
   답은 맞는데 근거 링크가 없는 것 — 공공기관 챗봇에서 신뢰 문제. `_answer_one`의 citation 조립이
   많은 정보성 답변에서 비어 나오는 구조적 원인으로 보이며, **리랭킹과 무관하게 지금 고칠 수 있는 버그성 이슈.**
2. **🟡 Recall@1이 낮다 (0.606).** top-5엔 잘 들어오는데(0.922) 1등으로 올리는 게 약하다.
   **이것이 리랭커가 개선할 여지가 있는 지점** — 다음 주 리랭커 On에서 Recall@1·MRR 상승 여부가 핵심.
3. **🟡 거절 경계 불안정 (양방향).** 정답 있는 질문 일부를 과잉 거절하고, 반대로 out-of-scope 질문
   일부는 거절 없이 답을 지어낸다. intent/out-of-scope 판단 경계 개선 여지.
4. **🟡 intent 정확도 0.772.** held-out 실전 성능. (참고: 개발 단계 leave-page-out 89.6%보다 낮음 —
   완전히 다른 세트라 그럴 수 있음.) 개선 여지 있으나, 튜닝은 testset_pipeline이 아닌 다른 셋으로.

## 4. 다음 단계 — 리랭킹 도입 후 재측정 계획

다음 주 GPU 인스턴스 제공 시 리랭커를 도입한다(리랭킹 도입은 확정, 모델 미정). 절차:

1. 리랭커 모델 후보 선정
2. **같은 평가 코드**를 `--rerank`로 재실행:
   - `python3 src/eval_pipeline_retrieval.py --rerank`
   - `python3 src/eval_pipeline_generation.py --rerank`
   - 결과는 `results/pipeline_holdout/*_rerank_on.json`으로 자동 구분 저장
3. 이 베이스라인(rerank_off)과 나란히 비교 → **리랭커 하나만 바뀐 통제 A/B** → 향상폭으로 도입 최종 확정
   - 특히 **Recall@1·MRR** 변화가 핵심 (리랭킹이 직접 개선하는 지표)
   - intent/question_type/오타강건성은 리랭킹과 무관 → 재측정 불필요, 이 값 그대로 사용

> 리랭킹은 검색 순서(top-k 재정렬)에만 영향을 주므로, 재측정은 검색·생성만 하면 된다.

### 개선 작업의 순서 원칙
- **버그 수정(예: 출처 누락)**은 지금 진행 가능 — 특정 문항 점수를 맞추는 게 아니라 객관적으로 잘못된 것을
  고치는 것이라 오염이 아니다.
- **성능 튜닝(예: intent 분류기 개선)**은 `testset_all`/별도 dev셋으로 반복하고, testset_pipeline은
  최종 확인용으로만 재측정한다.
