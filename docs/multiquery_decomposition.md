# 복합 질문(Multi-Query) 분해 — 방식 비교 실험 정리

같은 문제("질문 하나 = 임베딩 하나 = 검색 한 번" 구조라 복합 질문에서 검색 벡터가 여러 주제
사이로 뭉개짐)를 두 단계로 풀었다. **1차 시도는 규칙(정규식)+Kiwi 형태소로 만든 게이트로
LLM 호출 자체를 거르는 방식이었고, 원하는 성능이 안 나와 2차 시도로 전환했다. 2차 시도는
판단부터 분해까지 항상 LLM에 맡기는 방식이며, 실측 결과가 더 좋아 이걸 최종 채택했다.**

> **참고**: 1차 시도(규칙+Kiwi 게이트) 당시의 코드(`_looks_compound()`, 형태소 버전 이력,
> 라벨링 표본 등)는 전체 브랜치·커밋 이력·stash를 확인해도 이 저장소 어디에도 없다(`git log
> --all`, `git branch -a`, `git stash list` 전부 무흔적) — 별도 환경에서 작업하고 커밋 없이
> 넘어온 것으로 보인다. 그래서 1차 시도 관련 수치·코드는 **작업 당시 기록을 그대로 재구성한
> 것**이며, 이 저장소에서 재검증한 게 아니다. 2차 시도(최종 채택안)만 실제 저장소 상태·실행
> 결과로 검증됐다.

## 1. 실험 개요

| | 1차 시도 (규칙+형태소 게이트) | 2차 시도 — 최종 채택 (항상-LLM) |
|---|---|---|
| 복합 여부 판단 | `_looks_compound()` 정규식+Kiwi 형태소, LLM 호출 없음 | `decompose_query()` 자체가 매번 HyperCLOVA 호출로 판단+분해를 함께 함 |
| 단일 질문 비용 | 게이트가 걸러내면 추가 비용 0 | 모든 질문에 분해 판단 LLM 호출 1회 고정 추가(웜 상태 ~0.9~1초) |
| 분해 수단 | 게이트 통과분만 LLM로 분해 | 항상 LLM(few-shot 프롬프트) |
| 답변 병합 | 하위질문 결정론적으로 문단 이어붙임(LLM 미사용) | 동일 — `pipeline.py`에서 LLM 없이 문자열 join |
| 파일 | `src/query_decomposition.py`(현재 부재) | `src/query_decomposer.py`(현재 존재) |
| 채택 여부 | 목표 성능 미달로 폐기 | **최종 채택** |

## 2. 1차 시도 — 규칙+형태소 게이트

정규식만으로 시작해 반복 튜닝하며 Kiwi 형태소를 더했다. 복합 질문 35건·단일 질문 40건 표본으로
매 버전 Recall(복합을 복합으로 잡는 비율)과 오탐(단일을 복합으로 잘못 잡는 비율)을 쟀다.

| 버전 | 구성 | Recall | 오탐 |
|---|---|---|---|
| v1 | 그리고/근데/그런데/그리고서/만약 + 물음표2+ + 쉼표+어미 | 0.314 | 0.075 |
| v2 | v1 + 및/이랑/랑 | 0.314 | 0.125 |
| v3 | v2 + 또는/혹은 + 마침표2+ + 쉼표2+ | 0.600 | 0.125 |
| 최종(v3+Kiwi 형태소) | v3 + 명사+접속조사(JC: 와/과/랑/이랑) 검출 | **0.743** | **0.150** |

**대안으로 검토했다가 기각한 것들**:
- 검색 다양성 방식(top-k 검색 결과의 business_function 분산도로 판단): Recall 0.400·오탐
  0.325로 정규식보다도 나빠서 기각.
- **always-LLM(게이트 없이 항상 LLM 호출)**: Recall은 100%였지만, **단일 질문을 강제로 분해
  LLM에 태우면 없는 내용을 지어내며 오분할하는 게 3/3 재현**돼 기각. (→ 이 실패 모드를 2차
  시도에서 다시 정면으로 맞닥뜨리게 된다, 아래 3절 참고.)

**한계**: 오탐 5~6건을 원본 테스트셋과 대조해 라벨링 왜곡이 아닌 진짜 오탐임을 확인했다.
그럼에도 최종 버전 성능(Recall 0.743/오탐 0.150)은 목표에 못 미쳤고, 원리적으로 못 잡는
패턴도 남아 있었다 — "~하고"(Kiwi가 XSV+EC로 쪼개 접속조사(JC)가 안 붙음), 접속사·조사·쉼표가
전혀 없는 순수 나열형(표본 35건 중 9건)은 형태소 규칙으로도 못 잡는다. **규칙+형태소만으로는
이 문제를 원하는 수준까지 못 푼다고 판단해 2차 시도로 넘어갔다.**

## 3. 2차 시도 — 항상-LLM 방식 (최종 채택)

**규칙 기반이 아니라 LLM 기반**이다. 새 모델을 추가로 붙이지 않고 기존 `llm_client.py`의
`call_hyperclova()`(HyperCLOVA X, `temperature=0.2`)를 그대로 재사용한다. 게이트 없이 매
질문을 이 호출 하나로 "안 나눠도 되면 원문 그대로, 나눠야 하면 여러 줄" 판단과 분해를 함께
처리한다.

### 방식 상세

- **프롬프트 구성** (`query_decomposer.py`): `(role, content)` 튜플 리스트 — `prompt_builder.py`와
  동일한 형식. `SYSTEM_INSTRUCTION`(원칙을 번호 매긴 규칙으로 명시) + `FEW_SHOT_EXAMPLES`(질문→
  출력 쌍, 최종 6개) + 실제 질문.
- **규칙 요지**(반복 수정을 거쳐 최종 7개 확정):
  1. 실제로 서로 다른 정보 요구가 있을 때만 나눈다(요구 1개면 문장이 길어도 안 나눔).
  2. 안 나눌 땐 입력을 단어 하나도 안 바꾸고 그대로 한 줄만 출력한다 — **답변을 쓰지 않는다.**
  3. 나눌 땐 각 하위 질문에 주어(제도·업무명)를 채워 넣어 문맥 없이도 이해되게 한다. 원문에
     없는 요구를 지어내지 않는다.
  4. 원 질문의 요구를 하나도 안 빠뜨리는 최소 개수로 나눈다.
  5. 출력은 줄바꿈으로만 구분 — 번호·불릿·따옴표·설명문구 금지(파싱이 줄바꿈만 봄).
  6. "방법"/"절차"처럼 표현만 다르고 실질적으로 같은 요구는 동의어로 보고 안 나눈다.
  7. 접속어·띄어쓰기가 없거나 서술어가 이어져 있어도, 실제 요구가 여러 개면 반드시 줄을
     나눈다.
- **few-shot 6개 구성**: 단일(정의형) 1 · 단일(절차형, 없는 하위항목 지어내기 방지) 1 ·
  동의어 함정(안 나눔) 1 · 동일업무 복합(log/0729.md 예시) 1 · 타업무 복합(log/0729.md 예시) 1 ·
  붙여쓰기 복합(오타 포함, 나눔) 1.
- **출력 파싱** (`decompose_query()`): JSON을 안 쓴다 — 응답을 줄바꿈으로 split → strip → 빈 줄
  제거만 한다. 파싱 결과가 비면(호출 실패 등) **원본 질문 1개짜리 리스트로 폴백**한다 — 분해
  실패가 검색 자체를 막지 않도록.

### 1차 시도가 기각했던 바로 그 실패를 다시 마주치다

1차 시도가 always-LLM을 기각한 이유("단일 질문 강제 분해 시 내용 지어내며 오분할, 3/3 재현")를
2차 시도 초기 버전에서 **독립적으로 그대로 재현**했다 — "착오송금 반환 신청은 어떻게 하나요?"
(단일 절차 질문)를 분해기에 태웠더니 "서류는?", "기간은?"을 원문에 없는데 지어내 3/3 오분할했다
(`dq_004`). 재현 횟수까지 일치한다 — 이 실패 모드가 always-LLM 방식의 실제 구조적 약점임을
두 차례 독립 시행이 교차검증한 셈이다.

**차이는 그다음이다.** 1차 시도는 이 실패를 이유로 always-LLM 자체를 포기했지만, 2차 시도는
이 정확한 실패 사례를 few-shot 예시로 박아 넣는 프롬프트 보강으로 **같은 실패 모드를 상당 부분
해결**했다(5절 수치 참고). 즉 "always-LLM은 안 된다"는 1차 시도의 결론은 "프롬프트 보강 없이
시도한 always-LLM"에 대한 것이었고, 2차 시도는 그 보강이 통한다는 근거를 새로 만든 것이다.

그 외 2차 시도 진행 중 추가로 잡은 문제:

1. **동의어 함정** — "방법하고 절차"처럼 사실상 같은 요구를 접속어만 보고 나누던 문제.
   few-shot 예시 추가로 해결(규칙 6).
2. **붙여쓰기·긴 문장 과소분해** — 접속어·띄어쓰기가 없거나 서술어가 이어진 문장에서 서로 다른
   요구를 한 줄로 합쳐버리던 문제. 규칙+few-shot 추가로 해결(규칙 7).
3. **"~인지와 ~에 대해 알고 싶습니다" 패턴** — 여러 요구를 서술어 하나로 정중하게 묶은 문장은
   여전히 불안정(3회 중 1회 성공 수준). 추가 규칙+few-shot으로 재시도했으나 **동의어 함정
   케이스를 회귀시켜서 되돌렸다** — few-shot을 계속 늘리는 방식의 한계로 판단, 미해결로 남김.
4. **[NO_SOURCE] 마커 신뢰성 버그 발견** — 복합질문 실사용 테스트 중 발견했지만 **멀티쿼리와
   무관함을 A/B 검증(디컴포지션 On/Off 각 3회, 6/6 동일 재현)으로 확인**하고 별도 이슈로 분리했다
   (`docs/pipeline_issue_history.md` 이슈 3).

## 4. 두 테스트셋의 역할 구분 — 왜 둘 다 필요한가

이 문서에는 서로 다른 목적의 테스트셋 두 개가 등장한다. 하나가 다른 하나를 대체하지 않는다 —
각자 다른 축을 검증하고, 둘 다 없으면 안전하게 배포했다고 말할 수 없다.

| | `data/testset/testset_query_decomposition.jsonl` (38건, 이 저장소 산출물) | cq01~cq15 (27건, 1차 시도가 만든 라벨셋) |
|---|---|---|
| 검증 대상 | **분해기 텍스트 자체가 안전한가** — 안 쪼개야 할 걸 잘못 쪼개지 않는지, 없는 요구를 지어내지 않는지 | **분해 결과가 실제 검색 품질을 올리는가** |
| 단일 질문(안 쪼개져야 하는) 케이스 | **있음**(20건 — 오분해 검증의 핵심 축) | **없음**(15건 전부 복합 질문) |
| 정답 page_id(`expected_sources`) | 없음 | 있음 |
| 그래서 쓸 수 있는 실험 | 오분해율·과소분해율·요구사항누락률(5절) | Recall@5/MRR 전후 비교(6절) |

**cq01~cq15는 구조적으로 오분해(과잉분해) 버그를 절대 잡을 수 없다** — 애초에 "안 쪼개져야 하는"
케이스가 하나도 없기 때문이다. 그런데 이번 세션에서 실제로 터진 가장 심각한 버그 두 개가
바로 그 축이었다:

- `dq_004`("착오송금 반환 신청은 어떻게 하나요?" — 단일 질문): 초기 버전이 "서류는?", "기간은?"을
  **원문에 없는데 지어내서** 3/3 오분할
- `dq_022`("방법하고 절차 좀 알려주세요" — 사실상 단일 요구): 동의어를 다른 요구로 착각해 오분할

이 두 버그는 이 저장소의 38건 테스트셋 없이는 발견도, 재현도, 수정 검증도 못 했을 것이다.
반대로 검색 품질(Recall@5/MRR) 전후 비교는 정답 page_id가 있는 cq01~cq15 없이는 불가능했다
(38건 테스트셋엔 page_id 라벨이 없음). **그래서 5절은 38건 테스트셋으로, 6절은 cq01~cq15로
검증했다 — 서로 다른 실험에 서로 다른 테스트셋을 쓴 것이며, 어느 한쪽이 다른 쪽을 대체하지
않는다.**

## 5. 정확도 비교 — 같은 지표(Recall/오탐)로 나란히 놓기

1차 시도는 "게이트가 복합 질문 35건 중 몇 건을 복합으로, 단일 질문 40건 중 몇 건을 잘못 복합으로
오판했는지"를 쟀다. 2차 시도는 분해기 자체 출력을 38건(easy 20 + hard 18) × 3회 반복으로 쟀는데,
같은 의미로 환산할 수 있다: **Recall = 1 − 과소분해율(복합인데 못 쪼갠 비율)**,
**오탐 = 오분해율(단일인데 쪼갠 비율)**.

| 방식 | 표본 | Recall(복합→복합) | 오탐(단일→복합) |
|---|---|---|---|
| 1차 v1 | 복합35·단일40 | 0.314 | 0.075 |
| 1차 v2 | 복합35·단일40 | 0.314 | 0.125 |
| 1차 v3 | 복합35·단일40 | 0.600 | 0.125 |
| 1차 최종(v3+Kiwi) | 복합35·단일40 | 0.743 | 0.150 |
| 1차 always-LLM(대안, 기각) | 복합35 | 1.000 | *(3/3 오분할 재현으로 기각, 오탐 수치 미기록)* |
| **2차(최종 채택) 전체** | 복합·단일 38×3=114회 | **0.955** | **0.000** |
| 2차 — easy만 (정형 문장) | 20×3=60회 | **1.000** | **0.000** |
| 2차 — hard만 (오타·반말·서사형·함정) | 18×3=54회 | **0.923** | **0.000** |

**2차 시도(항상-LLM)가 1차 시도의 어떤 게이트 버전보다도 Recall·오탐 둘 다 뚜렷하게 낫다** —
이 결과를 근거로 항상-LLM 방식을 최종 채택했다. 다만 표본이 다르고(1차 35/40건 vs 2차
38건×3반복, 2차 표본은 이번에 직접 설계한 것) 절대 수치를 엄밀한 동일조건 비교로 보긴 어렵다는
점, 그리고 6절의 재현성 이슈 때문에 "0.000 오탐"을 절대적으로 신뢰하긴 조심스럽다는 점은
한계로 남긴다.

## 6. 솔직한 한계 — 표본 크기와 재현성

- 정식 평가(38건×3회)에서는 오분해 0%였지만, **그 이후 임시로 몇 개 케이스를 개별 재실행하며
  스팟체크했더니 이미 "고쳤다"고 판단했던 케이스(`dq_022`, 심지어 최초에 고쳤던 `dq_004`)가
  적은 표본에서 다시 실패하는 걸 관찰했다.** `llm_client.py`에 고정된 `temperature=0.2`(전체
  파이프라인 공유 설정) 특성상 어떤 케이스든 10~20%대 확률적 흔들림이 남아있는 것으로
  판단된다 — 즉 "3회 반복 100%/95.5%" 수치를 절대적으로 신뢰하지 말고, 실제 운영 시엔 이 정도
  잔여 오류율을 감안해야 한다.
- 1차 시도의 always-LLM 실험은 "3/3 재현"이라고만 기록돼 있어 정확한 표본 크기·반복 방법론이
  2차 시도와 동일한지 알 수 없다. 절대치 비교보다 **"동일 실패 모드가 독립적으로 재현됐다"는
  정성적 교차검증**으로 읽는 게 안전하다.
- ~~2차 시도는 검색 단계(Recall@5/MRR) 전후 비교를 하지 않았다~~ → **2026-07-30 보완 완료.**
  1차 시도가 만든 27개 라벨링 하위질문(cq01~cq15, `expected_sources` 전부 현재 코퍼스 58페이지에
  실재 확인됨)을 그대로 이 저장소의 현재 검색 파이프라인(`retrieval.route_search`)에 돌려 재현했다.

  | 조건 | Recall@5 | MRR@20 |
  |---|---|---|
  | BEFORE — 원 복합질문 통째로 검색 | 0.556 | 0.334 |
  | AFTER-GOLD — 손라벨 하위질문으로 개별 검색(이론적 상한선) | **0.815** | **0.576** |
  | **AFTER-REAL — `decompose_query()` 실제 출력으로 개별 검색** | **0.815** | 0.50~0.53 (재실행마다 변동) |

  1차 시도가 보고한 수치(Recall@5 0.556→0.778, MRR 0.334→0.568)와 방향은 일치한다. **더 중요한 건
  AFTER-REAL의 Recall@5가 AFTER-GOLD와 여러 번 재실행해도 항상 정확히 같다는 것** — 실제 배포된
  `decompose_query()`가 이론적 상한선(완벽한 손라벨 분해)만큼의 검색 Recall 개선을 실제로
  실현한다. MRR은 `decompose_query()`가 매번 표현을 조금씩 다르게 뱉는(temperature=0.2) 탓에
  재실행마다 0.50~0.53 사이로 흔들린다 — 위 항목들에서 설명한 잔여 비결정성과 같은 원인.

  **채점 버그 정정 이력(중요)**: 처음엔 Recall@5=0.778로 측정했었다. 그런데 "'착오송금은 어떻게
  돌려받나요?'가 개별로는 왜 못 찾지?"라는 질문을 받고 재확인해보니, 검색은 실제로 정답을 1위로
  정확히 찾고 있었다 — 다만 그 정답이 `kmrs_proc`("착오송금반환지원 절차", www.kdic.or.kr)가
  아니라 **완전히 동일한 5단계 절차를 담은 자매 페이지 `mtrs_gvbk_proc`**("반환지원절차",
  fins.kdic.or.kr, 본문 대조로 확인)였다. 1차 시도의 정답 라벨이 이 중복 페이지 쌍 중
  하나만 등록해둬서 생긴 채점 오류였지, 검색이나 분해기의 실패가 아니었다. 이 한 쌍만 정답으로
  동일 취급하도록 고쳐서 재계산한 게 위 0.815다. (다른 미스 4건 중 3건은 이런 중복 페이지가
  top-10 안에 없어 순수 저성능으로 보이고, 1건(`kmrs_proc`, "신청 절차가 어떻게 되나요?")은
  골드 하위질문 자체가 "착오송금"이라는 핵심 맥락어를 빼먹은 라벨링 문제로 보인다 — 저장소
  전체 58페이지에 이런 중복 쌍이 더 있는지는 이번에 다 확인하지 못했다.)

  (스크립트는 저장소에 커밋하지 않고 임시 실행만 함 — 재현하려면 위 27건을 `data/testset/
  testset_query_decomposition.jsonl`과 같은 형식으로 옮기고 `retrieval.route_search` +
  `query_decomposer.decompose_query`로 이 절차를 반복하면 된다.)

## 7. 파이프라인 통합 — 실제 서비스 경로에서 어떻게 도는가 (2026-08-03 기준 · ⚠️ 08-09 교체됨)

> ⚠️ 이 절은 **현재 파이프라인이 아니다.** 2026-08-09에 쿼리 플래너로 교체됐다(상단 「현재 상태」
> 참고). 아래 흐름은 `USE_QUERY_PLANNER=False`로 되돌렸을 때의 폴백 경로 명세로 읽을 것.

분해기 단독 성능(5절)과 검색 개선(6절)까지 확인한 뒤 `pipeline.py`에 붙인 형태다.
분해 결과를 어떻게 쓰느냐가 답변 품질을 좌우하므로, 이 절이 실질적인 "채택안 명세"였다.

### 흐름

```
rag_answer(질문)
  └ _rag_answer_traced(질문)
      ├ decompose_query(질문) -> sub_queries          # USE_QUERY_DECOMPOSITION=True일 때만
      ├ len(sub_queries) <= 1  → _answer_one(원본 질문)
      └ len(sub_queries)  > 1  → [_answer_one(q) for q in sub_queries] → 문자열 join
```

`_answer_one(질문)`은 질문 하나에 대한 검색~답변 조립 전체이며, **단일 질문 경로와 복합
질문의 각 하위 질문이 똑같이 이 함수를 탄다**(경로가 갈리지 않으므로 단일 질문 동작이
분해 기능 때문에 달라질 여지가 없다):

`classify_intent` → `route_search_chunks(k=20)` → 리랭킹(`USE_RERANKER=False`라 통과) →
`top_k_cut(k=5)` → 근거 조립(`citation.py` 또는 `civil_petition.py`) → 프롬프트 조립 →
HyperCLOVA 호출 → 출처 결정론적 부착.

### 설계상 명시적으로 정한 것 네 가지

1. **단일 질문이면 분해기 출력이 아니라 원본 질문으로 검색한다.** 분해기는 "안 나눌 땐
   입력을 그대로 출력"하도록 지시받지만(3절 규칙 2) 실제로는 "이란"→"이라는 게" 같은
   미세한 재작성이 섞여 나온다. 나눌 필요가 없다고 판단된 상황에서 굳이 재작성된 문구로
   검색할 이유가 없으므로 원본을 쓴다 — 분해 기능이 켜져 있어도 단일 질문의 검색 입력은
   기능이 꺼졌을 때와 동일하다.
2. **하위 답변 병합에 LLM을 쓰지 않는다.** `"\n\n".join(f"**{q}**\n{a}")`로 하위 질문을
   굵은 제목으로 달고 결정론적으로 이어붙인다. 병합을 LLM에 맡기면 하위 답변에 없던 내용이
   섞여 들어갈 수 있고(이 프로젝트가 URL 할루시네이션에서 이미 겪은 실패 패턴), 무엇보다
   하위 답변별로 확정된 출처와 본문의 대응이 깨진다.
3. **하위 답변끼리 출처는 완전히 독립이다.** 초기 구현에는 "같은 문서가 여러 하위 질문에서
   검색되면 중복 제거"(log/0729.md 3항) 요구를 만족시키려고 요청 단위 누적 집합
   (`seen_pages`/`seen_urls`)이 있었으나 **삭제했고 다시 도입하지 않는다.** 이 집합은 출처를
   실제로 붙였는지가 아니라 검색됐는지 기준으로 걸러서, 앞 하위 답변이 근거 미사용으로
   거절한 경우 뒤 하위 답변의 진짜 출처까지 지웠다(`docs/pipeline_issue_history.md` 이슈 4).
   같은 문서가 여러 하위 답변의 근거라면 각각에 보이는 것이 맞다.
4. **기능 스위치는 `USE_QUERY_DECOMPOSITION` 하나**(`pipeline.py` 모듈 상수, 기본 `True`).
   `USE_RERANKER`와 같은 패턴이라, E2E 재검증에서 판단이 뒤집히면 여기만 `False`로 바꾸면
   분해 없는 기존 동작으로 즉시 돌아간다.

### 비용 — 분해를 켜면 반드시 따라오는 것

- **모든 질문에 HyperCLOVA 호출 1회가 고정 추가된다.** 단일 질문이어도 "쪼갤지 말지"를
  판단해야 하고, 그 판단이 곧 LLM 호출이기 때문에 게이트 없는 구조에서는 피할 수 없다
  (웜 상태 ~0.9~1초).
- 복합 질문은 하위 질문 수 N만큼 **분류·검색·생성이 각각 N번** 일어난다. 지연은 대략
  `분해 1회 + N × (단일 질문 처리 시간)`이다.
- 단계별 소요 시간은 `performance.measure_time(..., accumulate=True)`로 같은 키에 합산해
  기록한다 — 하위 질문이 몇 개든 `retrieval`, `llm_call` 같은 항목 하나로 집계된다.

### 출처 부착 판정과의 상호작용 (알아둘 것)

답변에 출처를 붙일지 말지는 `prompt_builder.py`가 LLM 자기보고 마커
(`[SOURCE_USED]`/`[NO_SOURCE]`)로 판정한다. 이 방식은 근거를 실제로 쓴 답변의 54%에서
출처를 잘못 생략하는 것이 실측됐고(라벨 107건), 한때 코드 판정(`source_verifier.py`)으로
교체됐다가 **2026-08-03 다시 마커로 롤백**됐다. 같은 날 그 누락을 마커 방식을 유지한 채
수리했다 — 마커가 "근거를 안 썼다"고 판정한 경우에만 생성과 분리된 별도 LLM 호출로 한 번
더 확인한다(`src/source_check.py`, `pipeline.USE_SOURCE_RECHECK`). 경위와 수치는
`docs/pipeline_issue_history.md` 이슈 3 → 이슈 5 → "이슈 5-A" → "이슈 5-B" 순서로 이어진다.

멀티쿼리 입장에서 중요한 건 둘이다.

1. **한 번의 사용자 질문이 N개의 독립 생성으로 늘어나므로, 생성 1회당 존재하는 이런 실패율이
   그대로 N배로 노출된다.** 분해가 만든 버그는 아니지만 분해가 노출 빈도를 키우므로, 출처
   관련 이상이 보고되면 분해를 의심하기 전에 먼저 `docs/pipeline_issue_history.md`의 해당 이슈를
   확인하는 편이 빠르다(3절 4항의 A/B 검증 사례가 바로 그런 오진을 걷어낸 기록이다).
2. **재확인 호출도 같은 배수로 늘어난다.** 하위 답변마다 독립적으로 발동하므로, 위 7절의
   지연 공식은 최악의 경우 `분해 1회 + N × (단일 질문 처리 + 재확인 1회)`가 된다. 재확인은
   한 토큰만 뱉는 판정이라 실측 0.80초(웜)로 생성 호출(3.4초)보다 가볍지만, N배로 곱해지는
   항이 하나 늘었다는 점은 E2E 응답시간을 잴 때(9절 2항) 같이 봐야 한다.

## 9. 남은 작업

1. **"~인지와 ~에 대해 알고 싶습니다" 패턴**: 미해결로 남은 잔여 케이스 — few-shot 늘리기
