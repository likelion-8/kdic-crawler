# 검색 데이터 버전 관리 — 결정 (2026-08-10)

재적재가 운영 검색을 망가뜨리지 않게 하는 구조. "평가를 통과해야만 반영된다"(README §3.5)를
실제로 강제하는 장치이고, 실험 A4 가 검증하려는 대상이다.

## 결정 요약

| 항목 | 결정 |
|---|---|
| **버전의 단위** | 청크가 아니라 **입력 스냅샷**. `corpus.jsonl` + 그때의 빌드 파라미터를 한 벌로 보관한다 |
| **활성 버전 관리** | `search_index_versions.status='ACTIVE'` 인 행 1개. 부분 유니크 인덱스로 DB 가 "활성 2개"를 막는다 |
| **평가 실패 시** | 운영 테이블을 아예 안 건드린다. **"실패하면 롤백"이 아니라 "통과해야 반영"** 이라 되돌리는 코드가 없다 |
| **Rollback** | 직전 스냅샷으로 재적재하는 **비동기 잡**. 평가는 건너뛴다 |

## 한 줄 모델 — 사진이 아니라 필름을 보관한다

청크·벡터(사진)는 **언제나 한 벌만** 둔다. 대신 그것을 만들어낸 재료(필름 = `corpus.jsonl` +
빌드 설정)를 버전으로 남긴다. 잘못되면 필름으로 다시 인화한다.

그래서 **"어느 문서가 어느 버전"이라는 상태는 존재하지 않는다.** 지금 DB 에 있는 것 전체가
곧 ACTIVE 버전의 내용물이다. 과거 버전의 문서를 보려면 그 버전의 `source_snapshot` 을 풀어야
한다(DB 조회가 아니다).

```
documents             58행   ┐
document_chunks      494행   ├─ 지금 인화된 사진 = 운영 인덱스 (한 벌뿐)
                             ┘
search_index_versions  1행   ← 필름. status=ACTIVE
                               source_snapshot  그때의 corpus.jsonl (gzip 106KB)
                               build_params     구조 인식 청킹 / BGE-m3-ko
                               doc_count 58 · chunk_count 494
                               metrics          recall@5 0.922 · mrr 0.806
```

### 지금 되는 것 / 3주차에 되는 것

| | 현재 | 3주차(워커) |
|---|---|---|
| "지금 무엇이 운영 중인가" 기록 | ✅ ACTIVE 1행 | ✅ |
| 활성 버전 2개 방지 | ✅ DB 가 거부 | ✅ |
| 스냅샷 저장·복원 | ✅ | ✅ |
| 새 버전 생성 · 평가 · 전환 | ❌ | 워커 |
| Rollback | ❌ (되돌아갈 직전 버전이 아직 없다) | 워커 |

지금 `index_document_chunks.py` 를 돌리면 **버전을 새로 찍지 않고 ACTIVE 행만 갱신한다.**
정합성·평가 게이트가 없는 개발용 스크립트가 버전을 찍어내면 "평가를 통과한 판"이라는 의미
자체가 사라지기 때문이다.

## 1. 왜 청크에 버전을 달지 않는가

처음 검토한 안은 `document_chunks.index_version` 컬럼을 두고 청크+벡터를 버전마다 보관하는
것이었다. 채택하지 않았다.

**결정적인 이유 — 롤백이 이미 비동기 잡으로 계약돼 있다.**

```
POST /api/admin/jobs/{id}/rollback  ->  202 + PipelineJob 본문
```

프론트가 이 응답을 받아 진행 상태를 폴링한다(`web/src/routes/admin/pipeline/api.ts:113`,
`docs/backend-structure.md` §3 함정 #8). 즉 **롤백이 시간이 걸리는 작업이라는 것을 화면이 이미
전제하고 있다.** 화면 문구도 "긴급 롤백은 **회귀·Smoke 없이** 직전 정상 버전 하나로 되돌립니다"
(`Pipeline.tsx:556`)이지 "즉시"가 아니다 — 생략하는 것은 평가지 시간이 아니다.

청크 버전의 가장 큰 장점이 "플래그 하나로 즉시 전환"인데, 그 즉시성이 요구사항이 아니면
벡터를 두 벌 들고 있을 이유가 없다.

**부차적 이유**

- 변경 단위가 페이지다. 크롤링도 `content_sha256` 도 페이지 단위이고, 청크는 본문을 분할한
  파생물이라 독립적으로 바뀌지 않는다.
- 과거 버전 벡터가 같은 테이블에 있으면 **검색 경로마다 버전 필터를 빠짐없이** 걸어야 한다.
  한 군데만 빠져도 챗봇이 옛 내용으로 답하는데 에러가 안 나서 아무도 모른다.
- 임베딩은 결정론적이고 `data/dense_cache/` 가 있다. 텍스트가 같으면 벡터도 같으므로 스냅샷
  복원 시 재임베딩은 대부분 캐시 히트다 — 롤백 비용이 생각보다 싸다.

### ⚠️ 근거로 쓰면 안 되는 것 두 개

같은 논의에서 나왔지만 **사실이 아니거나 무게가 없는** 근거다. 나중에 이걸로 결정을 다시
뒤집지 않도록 적어 둔다.

| 주장 | 실제 |
|---|---|
| "재청킹하면 494청크가 전부 새 chunk_id 를 받는다" | **틀렸다.** `chunk_id` 는 `{page_id}#{n}` 형식이라 페이지 스코프다(`citation.py:38`). 한 페이지가 바뀌어도 다른 페이지의 청크 id·본문·벡터는 그대로다 |
| "벡터가 배로 늘고 pgvector 인덱스가 커져 검색이 느려진다" | 배로 느는 건 맞지만 **2MB → 4MB** 다. 그리고 `embedding` 에 **ANN 인덱스가 없다**(exact search, `schema.py` 주석) — 커질 인덱스가 없다 |

## 2. 구조

### 테이블 하나 (`search_index_versions`)

청크·문서 테이블은 **손대지 않는다.** 운영 인덱스는 언제나 한 벌이다.

| 컬럼 | 용도 |
|---|---|
| `status` | `BUILDING` → `READY` → `ACTIVE` / `SUPERSEDED` / `FAILED` / `ROLLED_BACK` |
| `source_snapshot` | 그때의 `corpus.jsonl` **전문(gzip)**. 0.46MB → 압축 0.1MB |
| `build_params` | 청킹 방식·크기, 임베딩 모델 id 등 재현에 필요한 설정 |
| `doc_count`·`chunk_count` | 정합성 검증 기준값 |
| `metrics` | Smoke 평가 결과(Recall·MRR·응답시간) |
| `created_by_job_id` | 이 버전을 만든 재적재 작업 |

### 스냅샷을 파일이 아니라 DB 에 두는 이유

압축 0.1MB 라 용량이 문제가 안 되고, 파일시스템에 두면 배포 환경에서 볼륨을 붙여야 하며
컨테이너를 갈아끼우면 사라진다. 버전 행과 같은 트랜잭션으로 쓰이는 것도 장점이다.

### 보관은 2개

관리자 화면의 긴급 롤백이 **'직전 정상 버전' 하나**만 대상으로 하고(`Pipeline.tsx:207`,
REQ-OPS-003) 버전 목록 UI 자체가 없다. 3개째부터는 **행은 남기고 `source_snapshot` 만 비운다**
— 이력(언제 누가 무엇을 했고 평가가 얼마였나)은 보존하면서 용량만 회수한다.

## 3. 흐름

### 재적재

```
1. 버전 행 생성 (BUILDING) + 현재 corpus 스냅샷·빌드 파라미터 저장
2. 변경 페이지 재크롤 -> corpus.jsonl 갱신 -> 청킹 -> 임베딩(dense_cache 재사용)
3. 정합성 검증: doc_count·chunk_count 대조          -> 어긋나면 FAILED
4. Smoke 평가를 새 인덱스에 실행 -> metrics 저장     -> 기준 미달이면 FAILED
5. 통과 -> READY
6. 한 트랜잭션: documents/document_chunks UPSERT + 기존 ACTIVE -> SUPERSEDED + 새 버전 -> ACTIVE
7. API 프로세스 reload
```

**1~5 단계에서 운영 검색은 전혀 영향받지 않는다.** 운영 테이블을 6번에서 처음 건드린다.

### 평가 실패 시 기존 유지 — 구현할 것이 없다

`status` 를 `FAILED` 로 두고 6번을 안 하면 끝이다. 운영 테이블이 그대로이므로 "되돌리는" 동작
자체가 없고, 따라서 그 경로에 버그가 들어갈 자리도 없다. 실패한 버전의 스냅샷은 원인 분석을
위해 남긴다.

### 활성 전환이 원자적인 이유

6번이 한 트랜잭션이다. Postgres MVCC 라 커밋 전까지 챗봇은 옛 데이터를 본다 — 청크 버전을
따로 두지 않아도 "중간에 섞인 상태"가 생기지 않는다.

### Rollback

직전 `SUPERSEDED` 버전의 스냅샷으로 2·6·7 단계를 다시 실행한다. **평가(3~5)는 건너뛴다** —
그게 '긴급'의 의미다. 되돌린 뒤 24시간 안에 회귀·Smoke 를 돌리는 것은 사람의 책임이다
(화면 문구가 그렇게 안내한다).

## 4. 이 설계가 성립하려면 지켜야 할 전제 2개

### 전제 1 — 평가는 DB 가 아니라 메모리에서 한다

새 인덱스를 운영 테이블에 올리지 않으므로, 평가 대상이 DB 에 없다. `eval_retrieval.py` 가 이미
JSONL+npy 로 검색기를 조립하므로 그 경로를 쓴다. 494×1024 float32 = 2MB 라 메모리에서 충분하다.

**이 전제가 깨지면(평가하려면 DB 에 올려야 한다면) 설계 전체를 다시 봐야 한다** — 그때는 두 벌을
들고 있어야 하므로 청크 버전 안으로 돌아가게 된다.

### 전제 2 — 스냅샷에 입력만 담으면 재현되지 않는다

`corpus.jsonl` 만 보관하고 나중에 되돌리면, 그 사이 **청킹 파라미터가 바뀌었을 때 다른 결과가
나온다.** P3 의 목표 자체가 청킹 방식을 관리자가 바꿀 수 있게 하는 것이라 실제로 일어난다.
그래서 `build_params` 에 청크 방식·크기·임베딩 모델을 함께 박는다.

## 5. 선행 조건 (완료)

로더의 `DELETE FROM documents` → UPSERT 전환이 **먼저** 필요했다. 재적재마다 `documents.id` 가
새로 발급되면 무엇이 그 행을 가리키든 연결이 끊기기 때문이다. 2026-08-10 처리했다
(`src/crawler/index_document_chunks.py` 상단 주석 참고).

## 6. 아직 안 정한 것

- **Smoke 통과 기준값** — Recall·MRR 이 기존 버전 대비 몇 % 이내면 통과인가. `metrics` 를 비교할
  대상은 직전 ACTIVE 버전의 `metrics` 다. 기준선은 `pipeline_heldout_baseline_89q.md`(89문항,
  Recall@5 0.922 · MRR 0.806)를 첫 ACTIVE 행에 시드하면 된다
- **평가 결과를 어느 화면에 표시하나** — `PipelineJob` 타입에 지표 필드가 없다. 파이프라인 화면
  (AD-004)에 붙일지 평가 화면(AD-006)에서 볼지 미정
- **reload 트리거 방식** — 워커는 API 프로세스 메모리를 못 건드린다. 내부 엔드포인트 / 활성 버전
  폴링 / 프로세스 재시작 중 택일. 갱신 대상은 3개다: `corpus.jsonl` 교체 · `_build_engines()`
  재조립 · `citation._page_meta`·`civil_petition` 모듈 캐시 비우기
