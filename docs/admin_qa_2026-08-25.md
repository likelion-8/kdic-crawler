# 3. 우선순위별 이슈

## [P0] 파이프라인 실패 상세 진입 시 전체 화면 크래시

### 대상

`/admin/pipeline`

### 재현 조건

1. 파이프라인 실행 이력에서 실패 상태 행을 찾는다.
2. `[상세]`를 클릭한다.
3. 실패 상세 모달 대신 React 오류 화면이 표시된다.
4. 새로고침하면 정상 화면으로 돌아온다.

### 실제 증상

```text
Unexpected Application Error!
Cannot read properties of undefined (reading 'replace')
at JobFailureDetail
```

실제 백엔드 연동 상태에서 재현했다.

### 근본 원인

- `web/src/routes/admin/pipeline/JobFailureDetail.tsx:57`

```ts
const reasonText = JOB_ERROR_MESSAGE[code].replace('{단계}', stage)
```

- 프론트가 정의한 오류 코드는 다음 5종뿐이다.

```ts
STAGE_TIMEOUT
JOB_TIMEOUT
SOURCE_ERROR
RESOURCE_ERROR
INTERNAL
```

- 하지만 실제 워커는 다음 값을 기록한다.

- `src/worker.py:579`

```py
error={"code": "STAGE_FAILED", "stage": exc.stage, "detail": exc.detail}
```

`STAGE_FAILED`는 프론트 오류 코드 목록과 매핑 테이블에 없으므로 `JOB_ERROR_MESSAGE[code]`가 `undefined`가 된다.

또한 `api/schemas/pipeline.py:32`의 오류 코드는 단순 `str`이라 백엔드에서 계약 오류를 차단하지 못한다.

### 수정 방향

1. 서버에서 `STAGE_FAILED`를 허용된 코드 중 하나로 정규화한다.
2. 또는 프론트에 `STAGE_FAILED` 매핑을 추가한다.
3. 프론트에서도 알 수 없는 코드가 들어오면 `INTERNAL` 문구로 폴백한다.
4. API 응답 계약에 오류 코드 enum 검증을 추가한다.

### 완료 기준

- 모든 FAILED 작업의 상세가 정상 렌더링된다.
- 알 수 없는 오류 코드가 들어와도 화면이 크래시하지 않는다.
- 오류 코드, 실패 단계, 오류 사유, 자동 재시도, 인덱스 영향이 모두 표시된다.
- 워커 실패 응답과 프론트 `JobErrorCode` 계약 테스트가 추가된다.

## [P1] 사이드바 클릭 후 URL과 실제 화면 상태 불일치

### 대상

관리자 전체 메뉴

### 재현 조건

1. `/admin/logs`에서 시작한다.
2. 사이드바의 `파이프라인`을 클릭한다.
3. 화면 내용은 파이프라인으로 바뀐다.
4. 다시 `지식베이스`를 클릭한다.

### 실제 증상

- 화면은 지식베이스로 바뀐다.
- 브라우저 URL은 계속 `/admin/pipeline`에 남는다.
- 새로고침하면 URL 기준으로 파이프라인 화면이 다시 열린다.
- 뒤로가기와 북마크 진입도 잘못된 화면을 가리킬 수 있다.

### 확인 내용

- `AdminLayout.tsx:207-214`의 `NavLink`와 href는 정상이다.
- `web/src/app/router.tsx`의 라우트 정의도 정상이다.
- 따라서 단순 메뉴 설정 문제가 아니라 런타임에서 history push와 화면 렌더링이 어긋나는 문제로 보인다.

### 수정 방향

1. 클릭 시 `router.state.location.pathname`과 브라우저 `location.pathname`을 함께 로깅한다.
2. React Router 인스턴스 중복 생성 여부를 확인한다.
3. 화면 제목과 콘텐츠를 별도 상태로 관리하지 말고 라우터 location에서만 파생한다.
4. 사이드바 E2E 테스트에 URL 검증을 추가한다.

### 완료 기준

- 메뉴 클릭 후 URL, active 메뉴, 화면 콘텐츠가 항상 같은 경로를 가리킨다.
- 새로고침, 뒤로가기, 앞으로가기, 직접 URL 진입이 모두 같은 결과를 낸다.
- 모든 관리자 메뉴에 대해 `href === 실제 pathname` 검증이 통과한다.

## [P1] 파이프라인 워커와 배치 실행 주체가 서비스 구성에 연결되지 않음

### 대상

파이프라인, 변경 감지, 재수집, 재적재, 평가 재측정

### 실제 증상

현재 파이프라인에 다음 작업이 대기 상태로 남아 있다.

```text
08-24 15:38 변경 감지
상태: 대기
```

워커가 실행되지 않으면 작업이 `QUEUED`에 계속 남을 수 있다.

### 근본 원인

- 워커 코드는 `src/worker.py`에 존재한다.
- 하지만 수동 실행 방식만 제공한다.

```text
python src/worker.py
python src/worker.py --once
```

- `api/main.py`의 lifespan에는 워커 자동 기동 코드가 없다.
- 저장소 compose 구성에도 워커 서비스가 없다.
- 배치 스케줄러도 별도로 확인되지 않는다.
- 활동 로그의 보관 예정 건수는 계산하지만 실제 자동 파기 실행 주체는 없다.

### 영향

- 전체 재수집
- 선택 재수집
- 재적재
- 변경 감지
- 평가셋 재측정
- 지식베이스 신규 적재 후 REINDEX

위 작업이 별도 워커가 실행되지 않는 환경에서 영구 대기할 수 있다.

### 수정 방향

1. 워커를 Docker 서비스, supervisor, systemd 또는 launchd로 상시 실행한다.
2. 워커 heartbeat와 마지막 처리 시각을 관리자 화면에 표시한다.
3. 일정 시간 QUEUED에 머물면 워커 미실행 경고를 표시한다.
4. 변경 감지와 보관기간 파기용 스케줄러를 별도로 연결한다.
5. 재시작 후 QUEUED 작업을 안전하게 재처리하는 정책을 추가한다.

### 완료 기준

- 작업 생성 후 정상 환경에서 3초 안에 RUNNING으로 전환된다.
- 워커가 중단되면 관리자 화면에 명확한 경고가 표시된다.
- 워커 재시작 후 기존 QUEUED 작업이 중복 없이 처리된다.
- 정기 변경 감지와 보관기간 파기가 실제 지정된 시각에 실행된다.

## [P1] 계정 초대와 비밀번호 재설정 메일이 실제 발송되지 않음

### 재현 조건

3. 화면에는 발송 완료 문구가 표시된다.
4. 실제 메일 발송 경로는 없다.

### 근본 원인

- `api/routers/admin_auth.py:755-795`
- 토큰은 생성되지만 SMTP 또는 메일 제공자 연동이 없다.
- 현재 토큰은 서버 로그에 링크 형태로만 기록된다.

- `PasswordResetPanel.tsx:168-176`은 발송 완료로 안내한다.

### 영향

- 신규 관리자 초대 불가
- 기존 관리자 비밀번호 분실 시 셀프 복구 불가
- 서버 로그에 재설정 토큰이 남을 위험

### 수정 방향

1. SMTP 또는 외부 메일 서비스 연동
2. 메일 발송 outbox와 실패 재시도 추가
3. 토큰 원문 로그 제거
4. 발송 성공 여부와 사용자 안내 문구 분리
5. 초대와 재설정 링크의 만료, 1회 사용, 재요청 정책 테스트

### 완료 기준

- 초대 메일과 재설정 메일이 실제 수신된다.
- 메일 링크로 비밀번호 설정이 완료된다.
- 토큰 원문이 애플리케이션 로그에 남지 않는다.
- 존재하지 않는 이메일 요청은 현재처럼 계정 존재 여부를 노출하지 않는다.

## [P2] 운영 정책 일부가 저장만 되고 실제 집행되지 않음

### 확인된 정상 집행

- IP별 분당 요청 제한
- IP별 일일 요청 제한
- 10초 burst 제한
- 반복 위반 시 임시 차단

### 미집행 항목

- `session_per_30min`
  - 화면에서 저장과 표시 가능
  - `api/middleware.py:108-109`에서 세션별 집행은 후속 과제로 명시
- `auto_purge`
  - 정책 필드와 토글은 존재
  - 실제 자동 파기 소비자와 실행 스케줄러는 확인되지 않음

### 수정 방향

- 세션 ID를 기준으로 한 공유 저장소 기반 quota 추가
- `auto_purge`를 실제 보관기간 파기 작업과 연결
- 정책 저장 화면에 미집행 상태를 명시하거나 집행 완료 전에는 편집을 숨김

### 완료 기준

- 저장한 세션별 제한이 실제 챗봇 요청에 적용된다.
- 자동 비우기 설정이 실제 캐시 또는 보관 데이터 파기에 반영된다.
- 프로세스 여러 개를 실행해도 제한값이 공유된다.

## [P2] 기본 프롬프트의 서비스명 불일치

### 증상

화면과 서비스 기준 명칭은 `예솜24`다.

하지만 코드 기본 시스템 프롬프트는 다음처럼 `예솜`만 사용한다.

- `src/prompt_builder.py:45`
- `src/prompt_builder.py:56`

### 영향

게시된 프롬프트가 없을 때 정체성 질문에서 화면 브랜드와 답변 브랜드가 달라질 수 있다.

### 수정 방향

- 기본 시스템 프롬프트와 few-shot 답변을 `예솜24` 기준으로 통일
- 정체성 질문 selfcheck 추가

### 완료 기준

- 홈 화면, 관리자 화면, 시스템 프롬프트, 챗봇 정체성 답변이 모두 동일한 서비스명을 사용한다.

## [P2] 챗봇 복합 질문 진행상황 표시 부족

### 확인 결과

복합 질문은 여러 하위 질문으로 분해되어 순차 처리되며 기능 자체는 정상이다.

### UX 문제

처리 중에는 단순히 "생각 중" 상태만 표시되어 다음 정보를 알기 어렵다.

- 몇 개의 하위 질문을 처리 중인지
- 현재 어느 하위 질문을 처리하는지
- 전체 예상 진행률

### 수정 방향

스트리밍 이벤트에 하위 질문 진행 상태를 추가하거나, 최소한 복합 질문 처리 중이라는 안내를 표시한다.

### 완료 기준

- 복합 질문 처리 중 사용자에게 진행 상태가 표시된다.
- 완료 전까지 입력 잠금과 중단 동작이 유지된다.
- 최종 답변과 하위 답변의 순서가 일치한다.

- 검증 실패 규칙 수를 확인 모달에 표시
