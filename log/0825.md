# 8월 25일 스탠드업 미팅

## 전일 진행 사항

### 1. 리랭킹 도입 확정

기존 Dense / Hybrid 검색 결과와 리랭커 실험 결과를 바탕으로 **운영 파이프라인에 리랭킹을 도입하는 방향으로 최종 확정**했다.

단순 검색 지표뿐 아니라 실제 어려운 질문에서 검색 결과가 개선되는지, 추가 latency가 어느 정도인지까지 확인한 결과 현재 구조에서는 리랭킹을 적용하는 것이 적절하다고 판단했다.

앞으로는 최종 파이프라인에서:

```text
검색
→ 후보 문서 확보
→ 리랭킹
→ 상위 근거를 이용해 답변 생성
```

형태로 동작하도록 전체 흐름을 정리할 예정이다.

---

### 2. 관리자 금칙어 가드레일 구현

관리자 페이지에서 설정한 금칙어가 실제 사용자 질문에 반영될 수 있도록 **금칙어 가드레일을 작성했다.**

사용자 질문에 등록된 금칙어가 포함된 경우 일반 RAG 파이프라인으로 보내지 않고 별도의 고정 응답을 반환하도록 처리하는 구조다.

운영 중 관리자가 금칙어를 변경할 수 있기 때문에 단순 하드코딩이 아니라 **관리자 설정값과 실제 사용자 서비스가 연결되도록 구성**했다.

---

### 3. 운영정책 페이지 및 캐시 확인

운영정책 페이지에서 사용하는 값들이 어떤 방식으로 조회되고 있는지 확인하고 **캐시 적용 여부와 추가 기능을 점검했다.**

특히 변경 빈도가 낮은 운영 설정값을 매 요청마다 다시 조회할 필요가 있는지 확인했으며, 관리자에서 값이 변경됐을 때 실제 서비스에 언제 반영되는지도 함께 살펴봤다.

이를 통해 운영 설정값을 관리하는 흐름을 전체적으로 확인했다.

---

### 4. 추천질문 기능 완성

사용자가 챗봇에 처음 진입했을 때 보여줄 추천질문을 정리했다.

현재 corpus에서 안정적으로 답변할 수 있는 질문을 기준으로 **FAQ Top 10 질문을 추천질문으로 구성**해 두었다.

추천질문은 단순 UI 요소가 아니라 사용자가 챗봇에서 어떤 질문을 할 수 있는지 보여주는 역할도 하기 때문에, 실제 답변 가능한 질문을 우선해서 구성했다.

## 금일 진행할 사항

오늘은 **되묻기 기능을 최종 마무리하고, 전체 RAG 파이프라인을 팀원들과 다시 맞춘 뒤 발표 준비까지 연결하는 것**을 목표로 한다.

### 1. 되묻기 기능 완성

현재 구현 중인 Clarification 기능을 최종적으로 마무리한다.

기존에 정리한 모호 질문 케이스를 기준으로 실제 파이프라인에서 제대로 되묻기가 발생하는지 확인하고, 이후 사용자가 추가 정보를 입력했을 때 정상적인 검색·답변 흐름으로 돌아가는지까지 테스트한다.

추가로 **되묻기 기능 관련 표를 기존 5개 기준에서 6개 기준으로 수정**하고 현재 구현과 문서가 일치하도록 정리한다.

확인할 내용:

* 되묻기 대상 조건 최종 확인
* 표 5 → 6 수정
* 모호 질문 테스트
* 정상 질문 오차단 여부 확인
* 멀티턴에서 추가 정보 입력 후 RAG 복귀 확인
* OOS / Relevance Gate와 역할이 겹치지 않는지 확인

핵심 원칙은 그대로 유지한다.

```text
업무를 확정할 근거가 충분함
→ 정상 답변

업무를 확정할 수 없음
→ 추측하지 않고 되묻기
```

---

### 2. Rewriter 수정

되묻기와 멀티턴 처리가 추가되면서 기존 **Query Rewriter가 이전 대화 내용을 어떤 방식으로 반영하는지 다시 확인하고 수정**한다.

특히 되묻기 이후 사용자가:

```text
예금보험금 말한 거야
```

처럼 짧게 답했을 때, 해당 문장만 검색에 넣는 것이 아니라 앞선 질문과 결합해 완전한 검색 질문으로 만들어야 한다.

예를 들면:

```text
사용자: 얼마까지 가능해?
챗봇: 어떤 업무의 한도를 말씀하시는 건가요?
사용자: 예금자보호요

→ Rewriter
→ 예금자보호제도의 보호 한도는 얼마인가?
```

처럼 검색 가능한 형태로 만들어지는지 확인한다.

---

### 3. `0.35` 임계값 재측정 및 OOS 고정 응답 연결

현재 OOS / Relevance 판단에 사용하고 있는 **`0.35` 임계값을 현재 인덱스 기준으로 다시 측정**한다.

최근 청킹, prefix embedding, 검색 구조 등이 변경됐기 때문에 기존에 설정했던 임계값을 그대로 사용하는 것이 적절한지 다시 확인할 필요가 있다.

확인할 내용:

* In-Scope 질문 점수 분포
* OOS 질문 점수 분포
* `0.35` 주변 질문 사례
* 정상 질문 오차단률
* OOS 차단률
* 임계값 변경 시 영향

측정 결과를 바탕으로 최종 임계값을 확정한 뒤, OOS로 판단된 질문에는 생성 모델을 호출하지 않고 **OOS 고정 응답을 반환하도록 연결**한다.

```text
질문
→ OOS 판단
→ 기준 미달
→ RAG 실행하지 않음
→ 고정 안내 응답
```

형태까지 완성하는 것이 목표다.

---

### 4. 반복 질문 캐시 처리

동일하거나 반복되는 질문에서 불필요하게 검색·생성을 다시 수행하지 않도록 **반복 질문 캐시 처리 구조를 진행한다.**

해당 작업은 동엽님이 담당한다.

확인할 내용:

* 어떤 단위로 동일 질문을 판단할지
* exact match 기준 여부
* 캐시 저장 범위
* 캐시 만료 조건
* 운영정책이나 지식 데이터 변경 시 기존 캐시 처리
* 캐시 응답에서도 로그를 어떻게 남길지

특히 지식베이스가 업데이트됐는데 이전 답변 캐시가 계속 반환되는 문제는 피해야 하므로 **캐시 무효화 기준**도 함께 확인할 필요가 있다.

---

### 5. 최종 RAG 파이프라인 전체 파악

기능이 여러 단계로 추가되면서 현재 최종 파이프라인이 처음보다 많이 복잡해졌다.

따라서 개별 기능 구현뿐 아니라 **팀원들이 최종 파이프라인 전체 흐름을 동일하게 이해하도록 다시 정리**한다.

현재 확인해야 할 주요 단계는 다음과 같다.

```text
사용자 질문
→ 금칙어 Guardrail
→ OOS 판단
→ Clarification
→ Query Rewrite / Planner
→ Retrieval
→ Reranking
→ Relevance 판단
→ Answer Generation
→ Answer Validation
→ 출처 및 후처리
→ 응답
```

실제 코드 기준으로 각 단계의 실행 순서와 조건을 확인하고, 필요하면 문서나 다이어그램도 현재 구현에 맞게 수정한다.

특히 다음을 명확히 한다.

* 각 Gate가 담당하는 문제
* 어느 조건에서 파이프라인이 조기 종료되는지
* 어떤 단계에서 LLM이 호출되는지
* Dense / Hybrid가 언제 사용되는지
* Reranker가 어느 위치에 들어가는지
* Rewriter와 Clarification의 연결 방식
* Validation 실패 시 처리 방식

---

### 6. 발표자료 초안 작성

최종 발표 준비를 위해 지금까지 구현하고 실험한 내용을 바탕으로 **발표자료의 전체 구조를 먼저 잡는다.**

세부 디자인보다 발표에서 어떤 흐름으로 프로젝트를 설명할지를 우선 정리한다.

예상 구성:

```text
문제 정의
→ 기존 RAG의 문제
→ 검색 및 라우팅 개선
→ OOS / Clarification / Validation
→ 관리자 및 운영 기능
→ 최종 파이프라인
→ 실험 결과
→ 최종 서비스
```

특히 기능이 많아졌기 때문에 모든 구현 내용을 나열하기보다 **문제가 무엇이었고 → 어떤 실험을 했고 → 최종적으로 어떤 구조를 선택했는지**가 보이도록 구성한다.

### 7. 관리자 페이지 기능 최종 확인

발표 준비와 함께 실제 관리자 페이지를 띄워 현재 구현된 기능을 다시 확인한다.

주요 확인 대상:

* 관리자 로그인 및 권한
* 지식베이스 관리
* 변경 요청
* 파이프라인 Job
* 대화 로그 및 피드백
* 활동 로그
* 운영정책
* 금칙어 설정

발표에 관리자 화면을 사용할 가능성이 있으므로 **실제 화면에서 각 기능이 정상 동작하는지 확인하면서 기능 흐름도 함께 파악**한다.

## Blocker / 논의 필요 사항

* 되묻기 이후 사용자의 짧은 답변을 Rewriter가 제대로 이전 질문과 결합하지 못하면 검색 품질이 떨어질 수 있어 멀티턴 기준 테스트가 필요함
* `0.35`는 기존 실험에서 정한 값이므로 현재 인덱스와 검색 구조에서도 그대로 사용할 수 있는지는 재측정 결과를 봐야 함
* 반복 질문 캐시는 응답속도와 비용을 줄일 수 있지만, 지식베이스 변경 이후 오래된 답변이 반환되지 않도록 무효화 정책이 필요함
* Gate와 후처리 단계가 많아지면서 팀원별로 파이프라인을 다르게 이해할 가능성이 있어 최종 코드 기준 실행 순서를 한 번 맞출 필요가 있음
* 발표에서는 모든 기능을 나열하기보다 **문제 → 실험 → 판단 → 최종 구조**가 보이도록 핵심 내용을 선별할 필요가 있음
