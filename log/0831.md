# 8월 31일 스탠드업 미팅

## 전일 진행 사항

### 1. 최종 발표자료 및 발표 흐름 점검

기존에 작성한 발표자료와 발표 스크립트를 다시 확인하면서, 프로젝트에서 진행한 실험과 최종 RAG 구조가 자연스럽게 연결되도록 전체 흐름을 점검했다.

단순히 구현한 기능을 나열하기보다,

```text
기존 구조의 문제
→ 실험 및 개선
→ 결과 비교
→ 최종 선택
→ 최종 RAG 파이프라인
```

형태로 발표가 이어질 수 있도록 내용을 정리했다.

특히 검색, 리랭킹, Clarification, OOS, Validation 등 각각의 기능이 **왜 필요했고 최종 구조에 어떤 영향을 주었는지** 설명할 수 있도록 발표 내용을 다시 확인했다.

---

### 2. 최종 RAG 파이프라인 및 서비스 구조 확인

발표자료에서 설명하는 RAG 파이프라인과 실제 구현된 서비스 구조가 일치하는지 다시 확인했다.

주요 흐름인

```text
Guardrail
→ OOS / Relevance
→ Clarification
→ Query Rewrite
→ Retrieval
→ Reranking
→ Answer Generation
→ Validation
→ Response
```

을 기준으로 각 기능의 역할과 실행 순서를 확인하고, 발표에서 지나치게 세부적인 분기까지 설명하지 않도록 주요 흐름 중심으로 정리했다.

또한 사용자 서비스뿐 아니라 관리자 페이지, 로그, 피드백, 문서 관리 등 전체 서비스 구조가 발표 과정에서 자연스럽게 연결될 수 있도록 점검했다.

---

### 3. 발표 시연 및 최종 결과 정리

발표에서 실제 서비스를 시연할 때 어떤 질문을 사용할지와 사용자 화면에서 관리자 화면으로 넘어가는 흐름을 다시 확인했다.

단순히 챗봇이 답변을 생성하는 모습만 보여주기보다,

```text
사용자 질문
→ 질문 분석
→ 검색 및 답변 생성
→ 근거 및 출처 확인
→ 관리자 화면에서 실행 결과 확인
```

형태로 프로젝트에서 구현한 기능이 실제 서비스에서 어떻게 동작하는지 보여줄 수 있도록 시연 흐름을 정리했다.

## 금일 진행할 사항

오늘은 **RAG 파이프라인의 토큰 사용량과 비용을 정리하고, 발표대본을 최종 완성하는 것**을 중심으로 진행한다.

### 1. RAG 파이프라인 토큰 사용량 분석 및 최적화

현재 서비스에서 사용자 질문 1건을 처리할 때 각 단계에서 어느 정도의 토큰을 사용하는지 확인하고, 불필요하게 사용되는 부분이 없는지 점검한다.

현재 측정된 전체 사용량은 질문 1건당 약 **6,500 tokens 수준**으로, 단순 생성 LLM 한 번만 사용하는 구조가 아니라 질문 분석, Rewriter, 답변 생성, Validation 등 여러 단계가 포함된 최종 RAG 파이프라인 전체 사용량이다.

주요 확인 내용:

* 질문 1건당 전체 토큰 사용량 확인
* LLM 호출 단계별 토큰 사용량 확인
* System Prompt 및 Context 크기 확인
* Retrieval 결과로 전달되는 문서 토큰 확인
* Rewriter / Validation 등 추가 LLM 호출 비용 확인
* 동일한 정보를 여러 단계에서 반복 전달하는 부분 확인
* 불필요하게 긴 Prompt 또는 Context 축소 가능 여부 확인
* 답변 품질을 유지하면서 줄일 수 있는 토큰 확인

단순히 토큰을 줄이는 것보다 **답변 정확도와 안정성을 유지하면서 불필요한 사용량을 줄이는 것**을 목표로 한다.

---

### 2. 일반 RAG 구조와 프로젝트 토큰 사용량 비교

현재 프로젝트의 토큰 사용량이 어느 정도 수준인지 설명할 수 있도록 일반적인 RAG 구조와 비교 기준을 정리한다.

단순한 RAG 구조는 보통

```text
질문
→ 검색
→ 답변 생성
```

정도로 구성되지만, 현재 프로젝트는

```text
질문 분석
→ OOS 판단
→ Clarification
→ Query Rewrite
→ Retrieval
→ Answer Generation
→ Validation
→ 후처리
```

등 여러 단계에서 품질과 안정성을 확인하는 구조이기 때문에 단순 RAG와 동일한 기준으로 토큰 수만 비교하기 어렵다.

따라서 발표에서는 단순히

> "토큰을 적게 사용했다"

라고 설명하기보다,

> **여러 검증 단계를 포함한 파이프라인에서도 불필요한 Context와 LLM 호출을 줄여 비용을 관리했다**

는 방향으로 설명할 수 있도록 비교 기준을 정리할 예정이다.

---

### 3. 질문 1건당 예상 비용 계산 및 비교

현재 사용하고 있는 모델별 입력 / 출력 토큰 가격을 기준으로 질문 1건당 예상 비용을 계산한다.

계산 과정에서는 다음 내용을 구분해서 확인한다.

```text
입력 토큰 비용
+
출력 토큰 비용
+
파이프라인 내 추가 LLM 호출 비용
=
질문 1건당 전체 예상 비용
```

또한 단순 RAG 구조와 현재 프로젝트처럼 여러 Gate와 Validation이 포함된 구조를 비교해, **추가적인 품질 검증을 위해 어느 정도의 비용이 사용되는지** 설명할 수 있도록 정리한다.

가능하면 다음과 같은 형태로 발표자료에 활용할 수 있도록 정리한다.

| 구분      | 구조                   |          토큰 사용 | 예상 비용 |
| ------- | -------------------- | -------------: | ----: |
| 단순 RAG  | 검색 + 생성              |       비교 기준 조사 |    계산 |
| 현재 프로젝트 | 분석 + 검색 + 생성 + 검증    | 약 6,500 tokens |    계산 |
| 최적화 이후  | 동일 품질 유지 + 불필요 토큰 감소 |             측정 |    계산 |

외부 RAG 서비스의 정확한 평균값을 임의로 사용하지 않고, 확인 가능한 모델 가격과 실제 프로젝트 측정값을 기준으로 비교할 예정이다.

---

### 4. 토큰 최적화 가능한 부분 개선

분석 결과를 기준으로 실제로 줄일 수 있는 토큰이 있는지 확인하고 필요한 부분을 개선한다.

주요 확인 대상:

* 지나치게 긴 System Prompt
* 검색 문서에서 실제 답변에 필요하지 않은 Context
* 동일한 질문 정보가 여러 Prompt에 반복되는 부분
* Validation에 필요 이상의 검색 문서가 전달되는 부분
* Rewriter가 필요하지 않은 질문에서도 호출되는지 확인
* 고정 응답이 가능한 질문에서 LLM 호출을 줄일 수 있는지 확인
* 캐시 적중 시 불필요한 후속 호출 여부 확인

다만 발표 직전인 만큼 구조를 크게 변경하기보다는, **현재 정상적으로 동작하는 범위에서 안전하게 적용할 수 있는 최적화**를 우선적으로 확인할 예정이다.

### 5. 발표대본 최종 완성

현재까지 수정한 PPT를 기준으로 발표대본을 최종 완성한다.

슬라이드 내용을 그대로 읽는 방식이 아니라 각 실험마다

```text
문제가 무엇이었는지
→ 어떤 방법을 시도했는지
→ 결과가 어떻게 나왔는지
→ 그래서 어떤 선택을 했는지
```

가 명확하게 전달되도록 대본을 정리한다.

주요 작업:

* 슬라이드별 발표 문장 최종 작성
* 불필요하게 긴 설명 축소
* 핵심 실험 수치 확인
* 실험 결과와 최종 선택 연결
* 최종 RAG 파이프라인 설명 정리
* 토큰 / 비용 최적화 내용 추가
* 관리자 페이지 및 서비스 시연 연결
* 마지막 프로젝트 결과 및 회고 정리
* 전체 발표 시간에 맞게 분량 조정

특히 프로젝트에서 많은 기능을 구현했다는 점보다, **문제를 발견하고 실험을 통해 최종 구조를 선택한 과정**이 잘 전달되도록 발표대본을 정리할 예정이다.

## Blocker / 논의 필요 사항

* 일반적인 RAG 서비스의 질문당 토큰 사용량은 파이프라인 구성, 모델, 검색 문서 길이 등에 따라 차이가 크기 때문에 단일한 평균값으로 비교하기 어려움
* 따라서 외부 평균 토큰 수를 임의로 제시하기보다 **실제 프로젝트 측정값과 동일한 조건에서 비교 가능한 구조를 기준으로 설명할 필요가 있음**
* 토큰 사용량만 줄이는 경우 답변 품질이나 Validation 정확도가 떨어질 수 있으므로 비용과 품질을 함께 고려해야 함
* 여러 단계의 LLM 호출을 사용하는 구조이기 때문에 전체 6,500 tokens만 보는 것보다 단계별 사용량을 구분해 확인할 필요가 있음
* 발표 직전 구조 변경으로 기존 정상 동작에 영향을 줄 수 있으므로 큰 변경보다는 Prompt, Context 등 안전한 범위의 최적화를 우선할 필요가 있음
* 발표에서는 비용 절감 자체보다 **품질을 위한 여러 검증 단계를 유지하면서도 불필요한 토큰을 줄였다는 점**을 명확하게 설명할 필요가 있음
