## 전일 진행 사항

### 1. 최종 RAG 파이프라인 정리 진행

그동안 추가된 기능들을 기준으로 현재 RAG 파이프라인의 전체 실행 흐름을 다시 확인했다.

단순히 검색 후 답변을 생성하는 구조에서 여러 Gate와 후처리 로직이 추가되면서 파이프라인이 복잡해졌기 때문에, **각 단계가 어떤 문제를 해결하고 어느 조건에서 실행되는지**를 코드 기준으로 맞추는 작업을 진행했다.

현재 주요 흐름은 다음과 같다.

```text
사용자 질문
→ Guardrail
→ OOS / Relevance 판단
→ Clarification
→ Query Rewrite / Planner
→ Retrieval
→ Reranking
→ Answer Generation
→ Validation
→ 출처 및 후처리
→ 응답
```

각 기능을 개별적으로 보는 것이 아니라 최종 서비스에서 서로 어떻게 연결되는지를 중심으로 확인했다.

---

### 2. 발표 준비를 위한 기능 및 실험 내용 정리

최종 발표에 포함할 프로젝트 내용을 정리했다.

검색, 리랭킹, OOS, 되묻기, Validation, 관리자 기능 등 구현된 기능이 많기 때문에 모든 내용을 나열하기보다는,

```text
문제
→ 실험 및 개선
→ 결과
→ 최종 선택
```

의 흐름으로 설명할 수 있도록 발표 구조를 정리하는 방향으로 진행했다.

## 금일 진행할 사항

오늘은 **최종 RAG 파이프라인의 구조를 확장하고 실제 코드 흐름을 분석한 뒤, 이를 기반으로 발표자료를 완성하는 것**을 목표로 한다.

### 1. 파이프라인 구조 확장

현재 구성된 RAG 파이프라인을 기준으로 각 기능의 역할과 연결 관계가 명확하게 보이도록 구조를 확장한다.

현재는 기능이 계속 추가되면서 단순한 선형 구조만으로는 실제 동작을 설명하기 어려운 부분이 있기 때문에, **분기와 조기 종료 조건까지 포함한 최종 구조**로 정리할 예정이다.

특히 다음 내용을 포함한다.

* 금칙어 Guardrail에서 바로 종료되는 경우
* OOS 판단 후 고정 응답으로 종료되는 경우
* Clarification이 발생하는 조건
* 되묻기 이후 멀티턴 입력이 Rewriter로 연결되는 흐름
* Dense / Hybrid Retrieval 실행 위치
* Retrieval 결과가 Reranker로 전달되는 과정
* 검색 결과의 relevance 판단
* Answer Generation 및 Validation 흐름
* Validation 실패 시 재생성 또는 후처리 방식
* 최종 출처 부착 및 응답 반환

최종적으로는 단순히

```text
질문 → 검색 → 생성 → 응답
```

이 아니라 실제 서비스 로직을 반영한 형태로 파이프라인을 확장한다.


실제 구현과 다이어그램이 다르게 보이지 않도록 **코드 기준으로 최종 구조를 확정하는 것**이 목표다.

---

### 2. 파이프라인 구조 분석

확장한 파이프라인을 기준으로 각 단계가 왜 필요한지와 서로 어떤 역할 차이가 있는지 분석한다.

기능이 많아지면서 비슷하게 보이는 단계가 있기 때문에 단순 실행 순서만 확인하는 것이 아니라 **각 단계의 책임을 명확하게 구분**한다.

주요 확인 내용:

* Guardrail과 OOS Gate의 역할 차이
* OOS 판단과 Retrieval 이후 Relevance 판단의 차이
* Clarification과 Rewriter의 역할 차이
* Rewriter와 Query Planner의 연결 관계
* Retrieval과 Reranking이 각각 해결하는 문제
* Validation이 검색·생성 단계와 분리되어 있는 이유
* 어느 단계에서 LLM 호출이 발생하는지
* 어느 단계가 결정론적으로 처리되는지
* 각 Gate에서 조기 종료될 수 있는 조건
* 단계별 latency 및 비용이 발생하는 위치

특히 발표에서 단순히 **“기능을 많이 추가했다”**로 보이지 않도록 각각의 단계가 기존 RAG의 어떤 문제를 해결하기 위해 추가됐는지를 연결해서 정리한다.

예를 들면:

```text
모호한 질문
→ 잘못된 업무를 추측할 위험
→ Clarification

도메인 밖 질문
→ 관련 없는 문서를 근거로 답변할 위험
→ OOS Gate

검색 후보에는 정답이 있지만 순위가 낮음
→ 정답 문서가 생성 근거에서 탈락
→ Reranking

생성 결과가 검색 근거와 맞지 않을 가능성
→ Answer Validation
```

이런 방식으로 **문제와 해결 구조가 연결되도록 파이프라인을 분석**한다.

### 3. 발표자료 완성

지금까지 정리한 실험 결과와 최종 파이프라인을 기반으로 발표자료를 완성한다.

오늘은 단순 초안 수준이 아니라 실제 발표가 가능한 수준까지 내용을 정리하는 것을 목표로 한다.

발표자료의 전체 흐름은 다음과 같이 구성한다.

```text
1. 프로젝트 및 문제 정의

2. 기존 RAG 구조와 발견된 문제

3. 검색 품질 개선
   - Retrieval
   - Multi Query / Planner
   - Reranking

4. 잘못된 답변 방지
   - Guardrail
   - OOS
   - Clarification
   - Rewriter
   - Validation

5. 최종 RAG 파이프라인

6. 관리자 및 운영 기능

7. 주요 실험 결과

8. 최종 서비스 시연 및 결과
```

특히 발표에서는 구현한 기능을 하나씩 설명하기보다,

```text
어떤 문제가 있었는가
→ 왜 기존 방식으로 해결되지 않았는가
→ 어떤 실험을 했는가
→ 결과가 어떻게 나왔는가
→ 그래서 어떤 구조를 선택했는가
```

가 자연스럽게 이어지도록 구성한다.

추가로 확인할 내용:

* 슬라이드별 핵심 메시지 하나로 정리
* 실험 결과 표와 그래프 선정
* 최종 파이프라인 다이어그램 반영
* 관리자 페이지에서 발표할 기능 선정
* 실제 서비스 화면 캡처 또는 시연 범위 결정
* 발표 시간에 맞게 중요도가 낮은 내용 제거
* 슬라이드 간 이야기 흐름 확인
* 발표 대본과 슬라이드 내용 일치 여부 확인

## Blocker / 논의 필요 사항

* 파이프라인에 여러 Gate와 분기 처리가 추가되면서 실제 코드의 실행 순서와 기존 문서의 흐름이 다를 수 있으므로 최종 코드 기준 확인이 필요함
* Clarification, Rewriter, OOS, Relevance처럼 서로 연결되는 기능의 역할 경계를 명확하게 정리하지 않으면 발표에서 구조가 복잡하게 보일 수 있음
* 파이프라인 전체를 한 장에 모두 표현하면 다이어그램이 지나치게 복잡해질 수 있어 발표용 구조와 상세 기술 구조를 분리할지 검토가 필요함
* 발표자료에 모든 실험을 포함하면 핵심 메시지가 흐려질 수 있으므로 최종 구조를 결정하는 데 영향을 준 실험을 중심으로 선별할 필요가 있음
* 최종 발표에서는 개별 기능 구현 자체보다 **문제 → 실험 → 판단 → 최종 파이프라인**의 연결이 명확하게 보이도록 정리할 필요가 있음
