## 3. 임베딩 모델 선정

P1은 bge-m3를 그대로 썼으나, P2에서 후보 4종을 동일 조건(`all` 494청크, 557문항, GPU)으로
비교했습니다(`data/embedding_eval/dy.json` 원본 실행 결과).

| 모델 | 차원 | MRR | Recall@1 | 494청크 인코딩 |
|---|---|---|---|---|
| bge-m3 (P1 기본값) | 1024 | 0.724 | 0.589 | 8.0s |
| BGE-m3-ko | 1024 | 0.770 | 0.641 | 7.7s |
| Qwen3-Embedding-8B | 4096 | 0.767 | 0.643 | 19.0s |
| Nemotron-3-Embed-8B | 4096 | 0.846 | 0.752 | 17.7s |

지표 1위는 Nemotron이었으나 채택하지 않았습니다. 8B급이라 오프라인 CPU 배포 제약에 걸린다는
판단이었고, 검색 성능과 운영 가능성을 함께 고려해 **BGE-m3-ko**를 최종 선정했습니다
(`src/retrieval.py:15`). 미채택 사유는 문서 기재이며 코드로는 확인되지 않으므로, 배포 환경이
바뀌면 재검토 대상입니다.

후보 비교 과정에서 NV-Embed-v2(7B)도 시도했으나 sentence-transformers 버전 충돌로 실행하지 못해
기록만 남겼습니다.

## 4. 벡터 저장소와 라우팅

### 4.1 Qdrant 로컬 저장소

494청크와 1024차원 임베딩을 Qdrant 로컬(임베디드)에 적재하고, 원문·출처 URL·페이지 제목·업무
분류를 payload로 저장했습니다. 무결성 검증에서 청크 중복·누락 없음, 필수 payload 누락 없음,
원본 임베딩과 저장 벡터 일치, 프로세스 재실행 후 영속성을 확인했습니다. 기존 NumPy Dense 검색과
Qdrant 검색의 MRR·Top-K 결과가 동일함도 함께 확인했습니다.

### 4.2 질문 유형별 검색기 라우팅

P1에서 "질문 유형마다 최적 검색기가 다르다"는 관측이 나왔고, P2에서 이를 자동 라우팅으로
구현했습니다. 질문 유형 분류기(`QuestionTypeClassifier`)를 만들어 유형별로 검색기를 선택하는
구조입니다. P2 종료 시점 기본값은 `table_lookup`은 Dense, 그 외는 Hybrid였습니다.

> 이 기본값은 P3에서 뒤집힙니다. 유형별 재측정 결과 Dense가 대부분 우세해 기본을 Dense로 바꾸고,
> `link_guide`만 Hybrid(Linear fusion α=0.4)로 남겼습니다.

## 5. 답변 생성 레이어

### 5.1 파이프라인 구성

```
질문 → intent 분류 → 검색(k=20) → 재정렬 → top_k_cut(k=5)
     → 근거 조립(citation 또는 civil_petition 3단)
     → 프롬프트 조립 → HyperCLOVA X 호출
     → 출처·서류·신청 페이지를 코드가 결정론적으로 부착
```

`rag_answer()`가 Streamlit과 터미널이 호출하는 유일한 진입점입니다. 답변 문자열만 반환하는 단순한
인터페이스를 유지하되, 내부에 `_rag_answer_traced()`를 두어 단계별 실행 시간을 기록하도록 했습니다.

### 5.2 출처 표시 — URL을 LLM에 제공하지 않습니다

초기 구현에서 few-shot 예시의 URL을 그대로 복사하거나 존재하지 않는 URL을 생성하는 문제가 반복
재현됐습니다. 이에 구조를 바꿔 URL·전화번호를 프롬프트에 아예 포함하지 않고, 출처·서류·신청 페이지는
`citation.py`·`civil_petition.py`가 조회한 값을 코드가 답변 뒤에 부착하도록 했습니다
(`prompt_builder.py:23-32`, `:181-204`).

모델이 생성할 수 없는 값은 환각도 발생하지 않는다는 접근이며, 실제로 문제가 해소됐습니다.

### 5.3 민원 3단 조립

민원 의도로 분류되면 새로 검색하지 않고 동일한 top-5 청크에서 3단을 구성합니다
(`civil_petition.py:44-99`).

| 단계 | 내용 | 출처 |
|---|---|---|
| 절차 | 청크 본문 연결 | 검색 결과 |
| 서류 | `attachments` + `form_attachments`, (label,url) 중복 제거 | P1 메타 103건 |
| 신청 페이지 | `citation` 재사용 | P1 메타 |

`form_attachments`의 `resolved_url`은 POST 전용 서블릿이라(코퍼스 103건이 3개 URL로 중복)
그대로 열리지 않습니다. 따라서 다운로드 버튼이 있는 `page_url`로 대체합니다. P1이 원본 메타를
보존한 덕분에 가능했던 처리입니다.

## 6. 실측으로 껐습니다 (1) — 리랭커

`bge-reranker-v2-m3` cross-encoder를 도입해 1차 검색 top-20을 재정렬하고 top-5를 반환하도록
구현했습니다. 그런데 응답 지연을 측정하자 전체 실행 시간의 97% 이상을 리랭킹이 차지했습니다.

| 질문 유형 | 리랭킹 | LLM 호출 | 전체 |
|---|---:|---:|---:|
| 정보성 | 99.47초 | 2.17초 | 101.90초 |
| 민원성 | 105.42초 | 2.18초 | 107.78초 |
| 표 조회 | 131.72초 | 0.98초 | 132.83초 |
| 근거 부족 | 160.78초 | 4.93초 | 166.39초 |

원인은 모델 재로딩이 아니었습니다. 리랭커는 이미 싱글턴으로 관리되고 배치 처리도 적용된 상태였으며,
실제 원인은 **최대 5,502토큰에 이르는 긴 청크 20개를 CPU에서 cross-encoder로 처리하는 연산 비용**
이었습니다.

품질 개선이 그 비용을 정당화하는지 확인하기 위해 동일한 1차 검색 결과에 대해 On/Off를
비교했습니다(쉬운 질문 3 + 모호한 구어체 3, 총 6문항).

| 구분 | Off | On |
|---|---:|---:|
| Recall@5 | 0.83 | 0.83 |
| MRR@5 | 0.71 | **0.64** |

리랭커가 새로 찾아낸 정답 페이지는 없었고, 기존에 1위였던 정답이 2위로 내려간 사례가 있었습니다.
정답이 애초에 Top-20에 없으면 리랭커로 개선할 수 없다는 한계도 확인했습니다.

**기본 Off로 결정**했습니다(`src/pipeline.py:28-33`). 코드는 제거하지 않고 남겨, GPU 환경과 짧은
`max_length`가 확보되면 재검토할 수 있도록 상태와 근거를 파일 상단에 기록했습니다. 모듈명도 실제
역할에 맞춰 `reranker.py` → `candidate_ranking.py`로 변경했습니다.

## 7. 실측으로 껐습니다 (2) — 업무 필터

P1·P2 계획의 중심 가설이었습니다. "오답 원인이 타 업무 청크 혼입 25.4%로 특정됐으므로 검색 공간을
업무로 좁히면 원인이 사라진다"는 논리로, `business_function` 자동 분류와 Qdrant 검색 필터를
구현했습니다(07-22).

문제는 검증 방식이었습니다. 초기 측정에서는 필터가 유리해 보였으나, 같은 페이지에서 파생된 형제
질문들이 학습·평가에 함께 섞여 있었습니다. 형제 질문은 `business_function`이 100% 동일하므로
분류기 점수가 실제보다 높게 나옵니다.

자기 자신만 제외하는 leave-one-out이 아니라 같은 gold page의 형제 질문을 후보 풀에서 전부
제외하는 leave-page-out으로 재측정한 결과는 다음과 같습니다.

| 조건 | 필터 ON | 필터 OFF |
|---|---|---|
| 편향 포함 (821문항) | MRR 0.759 | 0.775 |
| leave-page-out | MRR 0.672 | 0.842 |

정확하게 측정하자 격차가 오히려 커졌고, 오분류로 정답 업무가 통째로 누락되는 all-or-nothing 실패가
63/821(7.7%) 발생했습니다. **하드필터를 기본 Off로 되돌렸습니다**(07-24 커밋 `20bf4fc`).

> 점수 가산·RRF 결합·Top-1 매칭 같은 절충안까지 전부 검증해 "검색 필터·점수 가산·라우팅 어디에도
> 쓰지 않는다"로 최종 확정한 것은 P3 기간(07-29)입니다.

검색 공간을 좁힌다는 방향 자체는 유효했으나, 그 축이 "업무"가 아니라 "질문 유형"이어야 했다는 것이
결론입니다.

## 8. 평가 도구 — 도입했다가 롤백했습니다

테스트셋 전체를 자동 채점하는 `evaluate_pipeline.py`를 구현했습니다(07-23). 민원 답변을 절차·서류·
공식페이지 3분리로 채점하고, 답변 정확도는 LLM judge로 판정하며, `--retry-failed`로 실패 문항만
재실행하는 기능까지 갖췄습니다. judge 신뢰도 검증(`--validate-judge`)도 함께 만들었습니다.

그러나 다음 날 **팀 협의로 롤백**했습니다(07-24). "파라미터 튜닝은 아직 이르다"는 판단이었고,
평가 전용 인터페이스(`rag_answer_eval`)까지 함께 제거해 프로덕션 경로를 원복했습니다.

라벨 품질 검증 도구(`validate_testset.py`·`validate_golden_labels.py`)는 남겼습니다. 즉 **라벨은
검증된 상태이고 채점기만 없는 상태**로 P2를 마쳤습니다.

## 9. 데모 UI와 응답 속도

Streamlit으로 챗봇 UI를 구성했습니다(`src/app.py`). 질문 입력, 답변, 출처, 다운로드·신청 링크를

- **BM25 토큰화 캐싱** — Kiwi 형태소 분석 결과를 디스크에 캐싱해 재기동 비용 절감

## 10. 평가셋 확장

- **복합 질문 처리** — "신청 방법과 필요한 서류, 처리 기간"처럼 한 문장에 여러 질문이 들어오는

- **멀티턴** — 계획대로 범위 밖으로 두었습니다.

## 13. P3로 인계한 것

- **동작하는 RAG 파이프라인** — 생성 레이어 8모듈과 `rag_answer()` 진입점.
- **검증된 비선택지 2건** — 업무 필터와 리랭커. 재도입 조건을 코드에 기록해 두었습니다.
- **미완 과제 3건** — E2E 채점기 재도입, 역할 되묻기, 복합 질문 처리.
- **운영 파라미터의 코드 상수화** — `USE_RERANKER`·`K_FINAL` 등이 코드 상수입니다. 이를 화면에서
  변경하고 전후를 비교할 수 있게 만드는 것이 P3의 과제입니다.
