## 1. 요약

P1의 검색 위에 답변 생성 레이어를 얹어 Streamlit 챗봇 데모(`src/app.py`)를 구현했습니다.
계획한 3원칙(출처 표시 · 민원 3단 안내 · 환각 방지)은 모두 구현했으며, 그중 환각 방지는 프롬프트가
아니라 구조로 차단했습니다. 다만 E2E 정량 평가는 확정 파이프라인 기준으로 수행하지 못했고,
역할 되묻기도 미구현으로 남았습니다.

## 2. 답변 생성 경로

```
질문
 └ 분해 판단 (HCX 1회) ──── 복합이면 하위 질문 N개로
    └ 각 하위 질문마다
       ├ intent 분류 (OpenAI) — informational / civil_petition
       ├ 검색 k=20 → top_k_cut k=5      (리랭킹 단계는 코드에 있으나 Off)
       ├ 근거 조립  citation.py  또는  civil_petition.py 3단
       ├ 프롬프트 조립 → HCX 생성
       └ [NO_SOURCE]면 근거 재확인 1회 (HCX) → 판정 뒤집기
    └ 출처·서류·신청 페이지를 코드가 결정론적으로 부착
```

`src/pipeline.py:55-108`입니다. `rag_answer()`가 Streamlit(`app.py`)과 터미널이 호출하는 유일한
진입점이며, 여기서만 `rag_runs` 테이블에 실행을 로깅합니다(`pipeline.py:136-155`).

질문 1건당 LLM 호출은 단일 질문이라도 분해 판단 1회(HCX) + intent 1회(OpenAI) + 생성 1회(HCX)가
고정이고, 마커가 `[NO_SOURCE]`면 재확인 1회가 추가됩니다. 복합 질문이면 분해 1회 +
N×(intent+생성+선택적 재확인)로 증가합니다.

확인했으나 수정하지 못한 사항이 하나 있습니다. `rag_answer()`는 `_rag_answer_traced()` 내부에서
이미 호출한 `classify_intent()`를 로깅 목적으로 한 번 더 호출합니다(`pipeline.py:63` vs `:148`).
Streamlit·CLI 경로에서 질문당 OpenAI intent 호출이 2회 발생합니다.

## 3. 계획대로 구현한 것

### 3.1 출처 표시

계획대로 URL·전화번호를 프롬프트에 포함하지 않습니다(`prompt_builder.py:23-32` 규칙 3).
출처·서류·신청 페이지는 `citation.py`·`civil_petition.py`가 조회한 값을 `assemble_*` 함수가
답변 뒤에 코드로 부착합니다(`prompt_builder.py:181-204`).

이 구조는 2026-07-23에 few-shot 예시 내용을 그대로 복사하거나 존재하지 않는 URL을 생성하는 문제가
반복 재현돼 도입했습니다. 모델이 생성할 수 없는 값은 환각도 발생하지 않는다는 접근이며, 실제로
효과가 있었습니다.

### 3.2 민원 3단 조립

민원 의도로 분류되면 새로 검색하지 않고 동일한 top-5 청크에서 3단을 구성합니다
(`civil_petition.py:44-99`).

| 단계 | 내용 | 출처 |
|---|---|---|
| 절차 | 청크 본문 연결 | 검색 결과 |
| 서류 | `attachments` + `form_attachments`, (label,url) 중복 제거 | P1 메타 103건 |
| 신청 페이지 | `citation` 재사용 | P1 메타 |

`form_attachments`의 `resolved_url`은 POST 전용 서블릿이라(코퍼스 103건이 3개 URL로 중복)
그대로 열리지 않습니다. 따라서 다운로드 버튼이 있는 `page_url`로 대체합니다. P1이 원본 메타를
버리지 않고 보존한 덕분에 가능했던 처리입니다.

### 3.3 복합 질문 분해

규칙·형태소 게이트 대신 매 질문마다 LLM에게 판단과 분해를 함께 맡기는 always-LLM 방식을
채택했습니다(`query_decomposer.py:15-80`, 지시 7원칙 + few-shot 6개).

- 38건×3회=114회 평가에서 Recall(복합→복합) 0.955, 오탐(단일→복합) 0.000
- hard-tier(오타·반말·서사형) 54회에서 0.923
- 검색 효과: Recall@5 0.556→0.815, MRR 0.334→0.50~0.53

문서 기재입니다(`docs/multiquery_decomposition.md`). 같은 문서 6절은 `temperature=0.2`로 인해
10~20%대 잔여 변동이 남는다며 "오탐 0.000을 절대 신뢰하지 말 것"이라고 자체 제한을 명시하고 있습니다.

LLM이 few-shot 형식(`질문:`/`출력:`)을 그대로 따라 쓰는 사례가 있어 해당 줄을 제외하는 정규식
필터를 추가했으며, 파싱·호출 실패는 전부 `[원본질문]`으로 폴백합니다(`query_decomposer.py:102-116`).

## 4. 계획에서 변경된 것

### 4.1 의도 분류기 교체

계획은 "규칙 · 통계 모델 · LLM API 비교"였고, 실제로 4종을 비교했습니다(held-out 89문항).

| 분류기 | 전체 정확도 | 구어체·모호 16건 | 평균 응답 |
|---|---|---|---|
| 형태소 TF-IDF + LogReg | 78.6% | — | 즉시 |
| HCX-007 | 91.0% | — | 5.56초 (최대 62.2초) |
| gpt-4o-mini | 87.6% | — | — |
| gpt-5.4-mini | 92.1% | 93.8% | 0.85초 |

문서 기재입니다(`docs/intent_classification_final_report.md:101-111`). 구어체 서브셋 16건은 표본이
작아 문서에서도 "방향 신호로만 볼 것"이라고 밝히고 있습니다.

2026-08-03에 OpenAI Structured Output으로 교체했습니다(`query_classifier.py:103`). 학습 모델과
`data/intent_classifier/*.pkl`은 저장소에서 제거됐습니다.

두 가지를 기록해 둡니다.

- **미해결 전제** — 채택 보고서는 선행 조건으로 "데이터 국외 이전 규정 검토"를 명시했고, 규정상
  불가하면 국내 대안 HCX-007로 전환해야 한다고 적었습니다. 코드는 이미 OpenAI로 교체된 상태이나,
  규정 검토가 실제로 이뤄졌는지는 저장소에서 확인되지 않습니다.
- **조용한 폴백** — API 실패 시 예외를 삼키고 `informational`로 처리합니다
  (`query_classifier.py:144-156`). 키가 없거나 장애가 발생하면 전량 정보성으로 분류되어 민원 3단
  경로가 실행되지 않습니다. 동일 증상의 버그를 이미 한 차례 수정한 이력이 있습니다(커밋 `8c167f6`).

`question_type` 분류(5유형)는 교체하지 않고 코사인 1-NN을 유지했습니다. 참조 예시는 2026-08-03에
로컬 캐시에서 Supabase `evaluation_dataset`으로 이관해, 프로세스 시작 시 한 번 읽어 메모리에
적재합니다(`query_classifier.py:32-56`).

### 4.2 근거 사용 판정 방식

답변 첫 줄에 `[SOURCE_USED]`/`[NO_SOURCE]` 중 하나를 반드시 쓰게 하고 그 자기보고 마커로 출처
부착을 결정합니다(`prompt_builder.py:32`). 2026-07-30에 코드 판정(`source_verifier`)으로 전환했다가
2026-08-03에 자기보고로 롤백한 이력이 있습니다.

마커 오판에 방향성이 있음을 라벨 107건으로 실측했습니다.

| 마커 | 건수 | 오판 |
|---|---|---|
| `[SOURCE_USED]` | 28 | 0건 |
| `[NO_SOURCE]` 또는 마커 없음 | 79 | 33건 (42%) |

근거를 실제로 사용한 답변 61건 중 33건(54%)이 출처를 누락했습니다. 반대 방향(사용하지 않았는데
사용했다고 표시)은 0건입니다. 이 비대칭에 맞춰 한쪽만 재확인하는 장치를 추가했습니다.
`[NO_SOURCE]`인 경우에만 생성과 분리된 별도 LLM 호출로 "이 답변이 이 자료를 사용했는가"를
YES/NO로 질의하고, YES면 판정을 뒤집습니다. `[SOURCE_USED]`는 재확인하지 않습니다
(`source_check.py:39-82`).

효과 검증은 착오송금 1개 주제·각 3회 반복으로, Off는 출처 부착 0/3, On은 3/3이었고 재확인 지연은
0.80초(생성 3.4초 대비)였습니다. 표본이 3회·1주제로 매우 작으며, 문서 또한 "마커 누락이 다른
주제에서 얼마나 흔한지는 아직 측정하지 않았다"고 명시하고 있습니다.

### 4.3 저장소 전환 (P2 진행 중)

2026-08-03에 Qdrant에서 Supabase Postgres(pgvector)로 전환했습니다. 운영 Dense는
`PgVectorDenseRetriever`가 `document_chunks`(`embedding vector(1024)`)를 조회하며, `is_active=false`
청크는 항상 제외합니다. ANN 인덱스는 적용하지 않아 exact search이며, 500개 안팎 규모에서 실익이
없다는 판단입니다(`retrieval.py:148-183`).

절반만 이관된 상태임을 명시해 둡니다. Dense 벡터만 DB로 이동했고, BM25 색인과 unit 텍스트는 여전히
로컬 `corpus.jsonl`에서 생성하며 `citation.py`·`civil_petition.py`도 로컬 파일을 직접 엽니다.
따라서 서버는 DB와 로컬 데이터 파일이 모두 있어야 기동합니다.

## 5. 수행하지 못한 것

### 5.1 E2E 정량 평가

계획한 4지표(정답성·출처 정확도·환각률·거절 품질)를 확정 파이프라인 기준으로 측정하지
못했습니다.

held-out 측정은 2026-07-30 리랭커 Off 베이스라인 1회뿐입니다
(`docs/pipeline_evaluation_baseline.md`, `results/pipeline_holdout/` 2파일).

| 지표 | 값 |
|---|---|
| Recall@5 / Recall@1 / MRR | 0.922 / 0.606 / 0.806 |
| intent 정확도 | 0.772 (당시 TF-IDF 기준) |
| 생성 성공률 | 100% |
| 평균 응답 | 5.2초 |
| 출처 링크 포함률 | 0.380 |

이 측정 이후 intent의 OpenAI 교체, 복합 질문 분해 On, 근거 재확인 도입, pgvector 전환이 있었으나
이를 반영한 재측정 결과가 저장소에 없습니다. 특히 출처 링크 포함률 0.380은 근거 재확인 도입 이전
수치이므로 현재는 다를 것으로 예상되나, 측정한 적이 없어 확인할 수 없습니다.

E2E 채점 스크립트(`evaluate_pipeline.py`)는 한 차례 구현·운용됐다가 "파라미터 튜닝은 아직 이르다"는
팀 판단으로 롤백됐습니다. 라벨 품질 검증 도구(`validate_testset.py`·`validate_golden_labels.py`)는
남아 있으므로, 라벨은 이미 검증된 상태이고 채점기만 다시 만들면 되는 상태입니다.

### 5.2 역할 되묻기

P1에서 인계된 과제가 그대로 남았습니다. 역할축 41개를 정리해 두었으나 되묻기는 구현하지
못했습니다. 파이프라인에 구조화된 신호 자체가 없어 `ChatResponse.out_of_scope`는 항상 `False`,
`clarification`은 항상 `None`입니다(`api/rag/answer.py:122`, `api/schemas/chat.py:102-108`).
범위 밖 처리도 `[NO_SOURCE]` 마커에 의존할 뿐 구조화된 판정이 없습니다.

### 5.3 멀티턴

계획대로 범위 밖으로 두었습니다. `session_id`는 발급·반환만 하고 이전 대화를 프롬프트에 포함하는
코드가 없습니다.

### 5.4 웹 경로 로깅 공백

`rag_runs` 로깅은 `pipeline.rag_answer()`에서만 수행됩니다. P3에서 만든 API(SSE) 경로는
`api/rag/answer.py`를 사용하므로 웹으로 유입된 대화는 `rag_runs`에 기록되지 않습니다. DB 실측
80행은 전부 Streamlit·CLI 경로에서 누적된 것입니다.

## 7. P3로 인계한 것

- **확정된 RAG 코어** — `src/`의 파이프라인 모듈 일습. P3의 FastAPI가 이 빌딩블록을 재조립해
  사용합니다.
- **미완 과제 3건** — E2E 정량 평가 재도입, 역할 되묻기, 웹 경로 로깅.
- **운영 파라미터의 코드 상수화** — `USE_RERANKER`·`USE_QUERY_DECOMPOSITION`·`USE_SOURCE_RECHECK`·
  `K_FINAL`이 모두 코드 상수입니다. 이를 화면에서 변경하고 전후를 비교할 수 있게 만드는 것이 P3의
  과제입니다.
