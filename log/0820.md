### 4. Grounding Verifier 실험

기존에는 모든 답변에 대해 다음과 같이 LLM 검증을 수행한다.

```text
HCX 답변 생성
→ luna(validate_answer) 검증
```

이를 줄이기 위해 수치·날짜·비율 등이 모두 근거에 있는 답변은 정규식으로 먼저 검사하고, 깨끗한 답변만 luna 검증을 생략할 수 있는지 실험했다.

66문항 테스트 결과:

* 정규식만으로 스킵 가능: **8건 / 66건**
* 예상 호출 절감률: **12.1%**
* 스킵 후보 중 정규식이 놓친 오류: **1건**
* 실제로 회사명과 날짜는 맞지만 **개명 방향을 반대로 답변한 의미 오류**가 확인됨

따라서 정규식만으로는 관계·방향·부정/긍정 등의 의미 오류를 잡을 수 없어 **luna 검증 스킵은 보류**했다.

현재 방향:

```text
Grounding Verifier
→ LLM 검증 대체 X
→ Shadow Mode로 운영 데이터 수집
→ 필요하면 수치 오류를 잡는 보조 검증기로 활용
```

### 5. 프롬프트 수정 및 FAQ 거절 문제 분석

* HCX가 근거를 가지고도 `NO_SOURCE`로 판단하거나 거절하는 문제를 확인하면서 프롬프트 수정
* 단순 프롬프트 문제인지 확인하기 위해 기존/수정 프롬프트 비교
* FAQ 질문에서 근거가 검색 Top-1에 존재하는데도 거절되는 문제를 추가 분석

분석 결과 FAQ 청크 안에 사이트의 **원본 질문 문구가 그대로 포함**되어 있고, HCX가 답변 내용보다 사용자 질문과 FAQ 원문 질문의 표현을 비교하는 경향이 확인됐다.

```text
사용자 패러프레이즈 질문
        ↓
FAQ 청크의 원문 질문과 표현 차이
        ↓
근거가 있어도 HCX가 NO_SOURCE / 거절
```

청크 포맷을 바꾸는 A/B 테스트를 진행했고,

* FAQ임을 알려주는 프레이밍 추가
* 크롤링 잔재인 `열기` 제거

조합에서 가까운 패러프레이즈의 거절이 개선됐다.

다만 표현 차이가 큰 질문은 여전히 해결되지 않아 **FAQ 처리 방식 자체를 추가로 고도화할 필요가 있음**을 확인했다.

## 금일 진행할 사항

오늘은 어제 확인된 문제를 바탕으로 **검색 임계값·리랭킹·FAQ 처리·출처 마커의 신뢰성을 다시 점검**한다.

### 1. 0.35 임계값 재측정

현재 검색 relevance gate에서 사용 중인 `0.35`가 지금의 인덱스와 데이터에서도 적절한지 다시 측정한다.

* 인스코프 질문의 검색점수 분포 확인
* OOS 질문의 검색점수 분포 확인
* `0.35` 근처 경계 질문 집중 확인
* 인스코프 질문이 잘못 차단되는 비율 측정
* OOS 질문을 실제로 얼마나 걸러내는지 확인
* 기존 `0.35` 유지 / 조정 여부 결정

중요하게 볼 지표:

```text
인스코프 오차단률
OOS 차단률
경계구간 질문 유형
```

단순히 전체 정확도가 높은 값보다 **정상 질문을 잘못 막지 않는 값**을 우선한다.

---

### 2. 리랭킹 도입 여부 최종 검토

기존 Dense / Hybrid 검색 결과에 리랭커를 추가했을 때 실제 개선 효과가 있는지 다시 확인한다.

* 기존 리랭커 실험 결과 정리
* Recall / MRR 등 검색 품질 개선 폭 확인
* 검색 지연시간 증가 확인
* FAQ·표·link_guide 등 어려운 유형에서 실제 개선되는지 확인
* 품질 향상 대비 latency가 감수할 만한지 판단

최종적으로:

```text
검색 품질 개선 효과
vs
추가 응답시간 및 복잡도
```

를 기준으로 도입 여부를 결정한다.

---

### 3. FAQ 처리 방식 고도화

어제 FAQ 패러프레이즈 거절의 원인을 확인했으므로 해결 범위를 넓힌다.

확인할 내용:

* FAQ 청크 포맷 개선 결과를 더 많은 질문에서 재검증
* 가까운 패러프레이즈 / 먼 패러프레이즈를 구분해서 평가
* 추천 질문 문구를 FAQ 원문과 맞출지 검토
* FAQ의 `질문 + 답변` 구조를 생성 모델에 어떻게 전달할지 정리
* 청크 변경 시 검색 품질에 영향이 있는지 확인

단순히 추천 질문만 고치는 것이 아니라 **실사용자가 자기 표현으로 질문했을 때도 정상적으로 답할 수 있는 방향**을 함께 검토한다.

---

### 4. Corpus 전체 확인

현재 검색·생성 문제 중 일부가 모델이 아니라 **원천 데이터나 청크 구조 문제일 가능성**이 있으므로 corpus 자체를 확인한다.

* 크롤링 잔재 확인

  * `열기`
  * 메뉴명
  * 버튼 문구
  * 불필요한 반복 텍스트
* FAQ 질문/답변 구조 확인
* 표 청크 구조 재확인
* 제목·본문·헤더 누락 여부 확인
* 동일하거나 거의 같은 청크 중복 여부 확인
* 검색에는 잡히지만 생성 모델이 이해하기 어려운 형태가 있는지 점검

목표는 모델이나 프롬프트를 수정하기 전에 **입력 데이터 자체에서 제거할 수 있는 문제를 먼저 찾는 것**이다.

---

### 5. `NO_SOURCE` / `SOURCE_USED` 마커 검증

Grounding Verifier 실험에서 의심 판정의 상당수가 **HCX의 마커 오표기**에서 발생했다.

실제로 근거를 사용했는데도:

```text
[NO_SOURCE]
```

로 표시하거나, 반대로 마커가 누락되는 사례가 있는지 다시 확인한다.

확인할 내용:

* 실제 context에 정답이 존재하는데 `NO_SOURCE`가 나온 사례 수집
* 답변 내용은 근거 기반인데 `SOURCE_USED`가 누락된 사례 확인
* 질문 유형별로 마커 오류가 몰리는지 확인
* FAQ 청크 문제와 마커 오류의 연관성 확인
* 마커 자체를 얼마나 신뢰할 수 있는지 수치화

필요하면 현재처럼 HCX 자기보고를 그대로 사용하는 대신:

```text
HCX 마커
+
luna 검증 결과
+
실제 context 사용 여부
```

를 조합해 최종 출처 판정을 내리는 방향도 검토한다.

## Blocker / 논의 필요 사항

* `0.35` 임계값은 전체 정확도만 보고 결정하면 인스코프 질문을 잘못 차단할 수 있으므로 **오차단률을 우선 확인해야 함**
* 리랭킹은 검색 성능이 조금 좋아져도 latency 증가가 크면 운영상 이득이 없을 수 있음
* FAQ 문제는 프롬프트만으로 완전히 해결되지 않았으며, **청크 데이터 구조와 HCX의 패러프레이즈 민감성이 함께 작용**하고 있음
* FAQ 포맷 변경을 인덱스에 반영할 경우 검색점수 분포가 달라질 수 있으므로 임계값 실험과 순서를 맞출 필요가 있음
* HCX의 `NO_SOURCE` / `SOURCE_USED` 마커가 안정적이지 않다면 마커를 단독 판정 기준으로 사용하기 어려움
* Grounding Verifier 실험에서 의미·관계 오류를 실제로 놓친 사례가 확인됐기 때문에 현재 luna 검증을 제거하기는 어려움
