## 금일 진행할 사항

오늘은 개별 구현보다는 **팀 전체가 현재 RAG 파이프라인을 다시 검토하고, 남은 기능의 적용 여부와 우선순위를 결정**한다.

### 1. 평가 ↔ 실제 서비스 파이프라인 정합 마무리

현재 남아 있는 출처 판정 방식 차이를 어떻게 통일할지 논의한다.

주요 논의:

* `pipeline.py`도 웹의 3표 다수결 방식을 사용할지
* 모든 답변에 Reference Validation을 적용할지
* 동일 내용을 가진 여러 페이지를 정답 Source로 인정할지
* 출처 판정 통일 후 Hard71 / HOLDOUT 재평가 방식

---

### 2. 청킹 수정 후 검색 성능 재확인

청킹 로직이 변경됐기 때문에 기존 검색 결과를 다시 확인한다.

* Supabase 재색인 완료 여부 확인
* 표 관련 질문 15개 재평가
* 수정 전·후 `table_lookup` 성능 비교
* 기존 Hard71 결과에 청킹 오류가 얼마나 영향을 줬는지 확인

---

### 3. Router / Retrieval 구조 결정

Question Type Router 정확도가 실제 검색 성능에 얼마나 영향을 주는지 확인하기 위해 Oracle Routing 실험 여부를 결정한다.

검토할 비교:

* 현재 Router
* Oracle Routing
* All Dense
* All Hybrid

주요 지표:

* R@20
* R@5
* MRR

결과를 바탕으로 **Router를 개선할지, 단순화할지, 제거할지** 결정한다.

---

### 4. Reranker 적용 방향 결정

현재 후보인 Dragonkue의 적용 시점과 운영 방식을 논의한다.

* Dragonkue 적용 시점
* 청킹·Retrieval 재평가 후 적용할지
* 기존 Gate Threshold `0.35` 재설정 방식
* 모든 질문에 적용할지 여부
* Reranker 적용 전·후 성능 및 Latency 비교 방식

---

### 5. AI 파이프라인 구조 논의

멘토링 피드백과 현재 실험 결과를 바탕으로 최종 RAG 구조를 정리한다.

주요 논의 항목:

* `NO_SOURCE` 구조를 유지할지 제거할지
* Out-of-Scope 판단 위치와 방식
* Reference Validation 적용 위치
* Supervisor / Validator Agent 필요 여부
* Validation용 Context Summary 활용 여부
* GraphRAG 적용 필요성
* 재질문이 필요한 상황과 처리 방식

과도한 Agent 구조를 추가하기보다는 **현재 프로젝트에서 실제 성능 개선에 필요한 기능만 적용**하는 방향으로 검토한다.

---

### 6. LLM 사용 구조 정리

현재 여러 단계에서 사용하는 모델을 어떤 방식으로 가져갈지 논의한다.

* Luna로 통일할지
* HCX를 계속 병행할지
* Planner / Validation / Generation 단계별 모델 분리 여부
* 모델 통일 시 품질·Latency·비용 영향

---

### 7. Redis 적용 필요성 검토

현재 파이프라인에서 Redis를 적용할 가치가 있는 지점을 정리한다.

검토 후보:

* Query Planner 결과 캐시
* 반복 Retrieval 결과 캐시
* 반복 질문 응답 캐시
* 향후 Pipeline Job / Worker Queue 활용

우선 Langfuse로 실제 병목과 반복 호출을 확인한 뒤 **캐시 효과가 있는 부분부터 적용할지 결정**한다.

---

### 8. Langfuse 후속 작업

기본 RAG Trace 연결은 완료됐으므로 실제 웹 서비스까지 관측 범위를 확장할지 결정한다.

* 실제 React / SSE 요청 단위 Trace 연결
* 관리자 대화 로그 → Langfuse Trace 이동 흐름 확인
* Question Type 오분류 및 Retrieval 실패 사례 분석
* 단계별 Latency / Token 사용량 확인
