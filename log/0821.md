# 8월 23일 스탠드업 미팅

## 전일 진행 사항

### 1. 되묻기(Clarification) 필요 케이스 분석

`신청 링크 알려줘`, `얼마까지 가능해?`, `얼마나 걸려요`처럼 **질문만으로 어느 업무를 의미하는지 확정할 수 없는 경우**를 확인했다.

현재 검색은 질문이 모호해도 항상 가장 유사한 문서를 반환하기 때문에, 특정 업무의 문서가 검색 상위에 나오면 해당 업무로 잘못 단정해서 답변할 수 있다.

예를 들어:

```text
얼마까지 가능해?
```

라는 질문은 예금자보호 한도를 물어본 것일 수도 있고 착오송금 반환지원 금액을 물어본 것일 수도 있다.

따라서 이런 경우 검색 결과를 그대로 답변에 사용하는 대신:

```text
질문만으로 업무를 특정할 수 없음
→ 사용자에게 어느 업무인지 되묻기
→ 추가 정보를 받은 뒤 검색·답변
```

형태로 처리하는 방향을 정리했다.

되묻기의 목표는 많은 질문을 막는 것이 아니라, **잘못된 업무를 확신해서 답변하는 사례를 줄이는 것**이다.

### 2. 기존 RAG 게이트 구조 재점검

OOS, relevance gate, 답변 매핑 등 앞단 게이트가 추가되면서 각 단계가 어떤 문제를 담당하는지 다시 확인했다.

특히 다음 문제를 구분해서 처리할 필요가 있다.

```text
도메인 밖 질문
→ OOS Gate

도메인 안이지만 검색 근거가 약함
→ Relevance Gate

질문 자체가 모호해서 업무를 결정할 수 없음
→ Clarification Gate

근거는 있지만 생성 답변이 잘못됨
→ Answer Validation
```

되묻기 기능이 기존 OOS나 relevance gate와 중복되지 않도록 적용 위치와 판정 기준을 계속 정리하고 있다.

## 금일 진행할 사항

오늘은 **되묻기 기능을 마무리하고, 검색 설정과 운영 단계에 필요한 가드레일·프롬프트·추천질문을 확정하는 것**을 목표로 한다.

### 1. 되묻기 기능 완성

어제 정리한 모호 질문 사례를 기반으로 실제 파이프라인에 되묻기 처리를 완성한다.

확인할 내용:

* 어떤 질문을 되묻기 대상으로 볼지 기준 확정
* 정상적인 짧은 질문이 과도하게 차단되지 않는지 확인
* OOS Gate / Relevance Gate와 역할 중복 여부 확인
* 멀티턴에서 사용자가 추가 정보를 주면 정상적으로 기존 RAG 흐름으로 복귀하는지 확인
* 실제 로그의 모호 질문을 대상으로 테스트

중요한 원칙은 다음과 같다.

```text
추측해서 답변
<
필요한 경우 한 번 더 질문
```

다만 지나치게 많은 질문에서 되묻기가 발생하면 사용성이 떨어지므로 **업무를 특정할 수 없는 것이 명확한 경우에만 동작하도록 precision을 우선**한다.

---

### 2. `0.35` 검색 임계값 재측정

현재 Relevance Gate에서 사용하는 `0.35` 임계값이 현재 인덱스에서도 적절한지 다시 측정한다.

확인할 내용:

* 인스코프 질문 점수 분포
* OOS 질문 점수 분포
* `0.35` 부근 질문 사례
* 정상 질문 오차단 비율
* OOS 차단 비율
* 질문 유형별 점수 차이

특히 전체 정확도보다 다음 지표를 우선해서 본다.

```text
인스코프 오차단률
OOS 차단률
경계구간 질문의 실제 내용
```

정상 질문을 잘못 막는 위험이 크다면 임계값을 조정한다.

---

### 3. 리랭킹 도입 여부 최종 확정

기존에 진행한 Dense / Hybrid + Reranker 실험 결과를 다시 정리하고 실제 운영 파이프라인에 포함할지 결정한다.

비교 기준:

* Recall / MRR 개선 정도
* 어려운 질문에서의 실제 검색 개선 사례
* 추가 latency
* 모델 운영 비용 및 복잡도
* 전체 사용자 응답시간에 미치는 영향

단순히 검색 지표가 조금 높아지는 것보다:

```text
실제 답변 품질 개선
vs
추가 latency 및 구조 복잡도
```

를 기준으로 최종 도입 여부를 결정한다.

---

### 4. 관리자 금칙어 가드레일 작성

관리자에서 설정한 금칙어를 사용자 질문 단계에서 처리할 수 있도록 가드레일 구조를 작성한다.

확인할 내용:

* 관리자 금칙어 데이터 조회 방식
* 질문에 금칙어가 포함됐을 때 처리 방식
* 정확히 일치하는 경우와 문장 안에 포함된 경우 처리 기준
* 대소문자·띄어쓰기 등 정규화 방식
* 금칙어 차단 시 사용자에게 반환할 고정 응답
* 차단된 질문의 로그 저장 여부

운영 중 관리자가 금칙어를 변경했을 때 **서비스에 어떻게 반영할지**도 함께 정리한다.

---

### 5. 시스템 프롬프트 완성

지금까지 실험하면서 수정된 답변 규칙을 하나의 최종 시스템 프롬프트로 정리한다.

포함할 주요 내용:

* 검색 근거를 벗어나지 않고 답변
* 근거가 부족한 경우 처리
* 모르는 내용을 추측하지 않는 규칙
* FAQ 근거 처리
* 질문과 무관한 내용 생성 방지
* 링크·절차·서류 안내 방식
* 멀티턴 대화에서 이전 답변과 검색 근거의 역할 구분
* 답변 표현 및 형식 통일

기존에 실험을 위해 추가된 임시 지시문도 정리해서 **운영용 프롬프트를 최대한 단순하게 만드는 것**을 목표로 한다.

---

### 6. 운영정책 페이지 처리 방식 확인

운영정책 페이지에서 반복적으로 사용하는 데이터가 어떤 방식으로 조회되고 있는지 확인한다.

특히:

* 현재 캐시 적용 여부
* 매 요청마다 DB를 조회하고 있는 기능 확인
* 변경 빈도가 낮은 데이터 중 캐시 가능한 항목 확인
* 관리자 수정 이후 캐시 갱신 방식 확인
* 운영정책 페이지에서 추가로 필요한 기능 확인

금칙어처럼 관리자 설정이 실제 사용자 서비스에 영향을 주는 값은 **DB 변경과 실제 서비스 반영 시점이 어긋나지 않도록** 구조를 확인한다.

---

### 7. 추천질문 기능 완성

현재 추천질문 기능을 실제 운영 가능한 형태로 마무리한다.

확인할 내용:

* 추천질문 문구 최종 정리
* 실제 corpus에서 안정적으로 답변 가능한 질문인지 확인
* FAQ 원문을 그대로 노출할지 사용자 친화적으로 바꿀지 결정
* 클릭 후 정상적으로 검색·답변되는지 확인
* 업무별 추천질문 분포 확인
* 잘못된 검색이나 거절을 유발하는 질문 제거

추천질문은 단순 UI 문구가 아니라 사용자가 처음 챗봇을 사용할 때 **질문의 범위와 사용 방법을 보여주는 역할**도 하므로 답변 성공률까지 함께 확인한다.

## Blocker / 논의 필요 사항

* 되묻기 범위를 넓히면 잘못된 답변은 줄일 수 있지만 정상 질문까지 계속 되묻게 될 수 있으므로 **precision 중심의 기준이 필요함**
* `0.35` 임계값은 인덱스나 청크 구조가 변경될 때 검색점수 분포도 달라질 수 있으므로 현재 데이터 기준으로 다시 측정해야 함
* 리랭킹은 검색 지표 개선만으로 판단하지 않고 실제 답변 개선과 latency를 함께 확인해야 함
* 금칙어를 DB에서 매 요청마다 조회할 경우 불필요한 비용이 발생할 수 있지만, 캐시할 경우 관리자 변경사항 반영 시점을 별도로 관리해야 함
* 시스템 프롬프트에 규칙을 계속 추가하면 오히려 모델 동작이 불안정해질 수 있어 **실제로 필요한 규칙만 남기는 정리 과정이 필요함**
* 추천질문은 실제로 안정적인 답변이 가능한 질문을 기준으로 구성해야 하며, FAQ 원문에 맞추기 위해 지나치게 인위적인 문장으로 만드는 것은 피할 필요가 있음
