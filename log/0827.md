# 8월 27일 스탠드업 미팅

## 전일 진행 사항

### 1. 최종 RAG 파이프라인 및 발표 흐름 정리

현재 구현된 기능을 기준으로 최종 RAG 파이프라인의 전체 구조를 다시 정리했다.

Guardrail, OOS, Clarification, Rewriter, Retrieval, Reranking, Validation 등 각각의 기능이 실제 서비스에서 어떤 순서로 동작하고 어떤 문제를 해결하는지 확인하면서, 발표에서도 단순 기능 나열이 아니라 **문제와 해결 과정이 연결되도록 흐름을 정리**했다.

특히 발표에서는 전체 구조를 한 번에 설명하기보다,

```text
기존 구조의 문제
→ 실험 및 개선
→ 최종 선택
→ 최종 파이프라인
```

형태로 설명할 수 있도록 구성했다.

---

### 2. 최종 발표자료 초안 작성

지금까지 진행한 실험과 구현 내용을 기반으로 최종 발표자료 초안을 작성했다.

모든 실험과 기능을 포함하면 발표 내용이 지나치게 많아질 수 있기 때문에, 최종 구조를 결정하는 데 영향을 준 내용들을 중심으로 정리했다.

주요 발표 내용은 다음과 같이 구성했다.

* 기존 RAG 구조에서 발견한 문제
* 검색 및 청킹 개선 과정
* Query Planner / Rewriter
* Reranking 도입 과정
* OOS 및 Clarification
* Answer Validation
* 최종 RAG 파이프라인
* 관리자 페이지 및 서비스 기능
* 주요 결과 및 시연

슬라이드별로 **“무엇을 구현했는가”보다 “왜 이 구조를 선택했는가”**가 드러나도록 내용을 배치했다.

---

## 금일 진행할 사항

오늘은 **어제 작성한 발표자료 초안을 수정하고, 실제 발표에 사용할 스크립트를 작성하는 것**을 중심으로 진행한다.

### 1. 발표자료 초안 수정 및 내용 정리

어제 작성한 발표자료를 다시 확인하면서 슬라이드별 내용을 정리한다.

현재 초안에는 프로젝트에서 진행한 다양한 실험과 기능이 포함되어 있기 때문에, 발표 시간 안에 핵심 내용이 전달될 수 있도록 **중요도가 낮거나 중복되는 내용을 줄이고 핵심 메시지를 명확하게 만드는 작업**을 진행할 예정이다.

주요 수정 내용:

* 슬라이드별 핵심 메시지 명확하게 정리
* 비슷한 내용을 설명하는 슬라이드 통합
* 중요도가 낮은 실험 내용 축소 또는 제거
* 실험 수치 및 결과 표기 확인
* 파이프라인 다이어그램과 실제 구현 내용 일치 여부 확인
* 슬라이드 간 이야기 흐름 정리
* 발표에서 설명하기 어려운 복잡한 문장 단순화
* 표와 그래프에서 발표에 필요한 핵심 결과만 강조
* 관리자 페이지 및 서비스 시연 슬라이드 정리

특히 발표 흐름이

```text
문제
→ 가설
→ 실험
→ 결과
→ 판단
→ 최종 구조
```

로 자연스럽게 이어지는지 확인한다.

단순히 기능을 많이 구현했다는 인상을 주기보다, **문제를 확인하고 실험을 통해 최종 구조를 선택했다는 과정**이 드러나도록 수정하는 것이 목표다.

---

### 2. 발표 스크립트 작성

수정한 발표자료를 기준으로 실제 발표에 사용할 스크립트를 작성한다.

슬라이드에 적혀 있는 내용을 그대로 읽는 방식이 아니라, 각 슬라이드에서 전달해야 하는 핵심 내용을 중심으로 발표 대본을 구성할 예정이다.

스크립트 작성 시 다음 내용을 중점적으로 확인한다.

* 슬라이드별 핵심 메시지를 한 문장으로 정리
* 문제 상황을 먼저 설명한 뒤 해결 방법으로 연결
* 실험 수치를 모두 읽기보다 의미 있는 결과 중심으로 설명
* 기술적인 내용은 필요한 수준까지만 설명
* 앞뒤 슬라이드가 자연스럽게 연결되도록 전환 문장 작성
* 최종 파이프라인까지 하나의 이야기로 이어지도록 구성
* 관리자 페이지 및 서비스 시연으로 자연스럽게 연결
* 발표 시간에 맞도록 전체 분량 조절

예를 들어 기능을 단순히

```text
리랭킹을 추가했습니다.
```

라고 설명하기보다,

```text
검색 후보 안에는 정답 문서가 존재했지만
상위 순위에 올라오지 못하는 문제가 있었습니다.

이를 개선하기 위해 리랭킹을 실험했고,
성능과 응답 속도를 비교한 뒤
최종 운영 구조를 결정했습니다.
```

처럼 **문제와 판단 과정이 드러나도록 설명**할 예정이다.

---

### 3. 발표자료와 스크립트 일치 여부 확인

스크립트 작성 이후 발표자료와 실제 설명 내용이 서로 맞는지 확인한다.

발표자료에는 없는 내용을 대본에서 지나치게 길게 설명하거나, 반대로 슬라이드에 중요한 결과가 있는데 대본에서 빠지는 경우가 없도록 맞춘다.

주요 확인 내용:

* 슬라이드 순서와 발표 대본 순서 일치 여부
* 실험 결과 및 수치 일치 여부
* 최종 파이프라인 설명과 다이어그램 일치 여부
* 슬라이드 한 장당 설명 분량 확인
* 반복해서 설명하는 내용 제거
* 발표에서 반드시 강조해야 하는 내용 확인
* 기술 설명과 서비스 설명의 비중 조정

최종적으로는 **슬라이드만 보더라도 흐름이 이해되고, 발표 대본을 함께 들으면 선택 이유까지 이해되는 구조**를 만드는 것이 목표다.

---

### 4. 발표 시간에 맞춘 전체 흐름 점검

작성한 발표 스크립트를 기준으로 실제 발표 시간을 확인하고 내용의 우선순위를 다시 조정한다.

시간이 부족한 경우 모든 실험을 설명하기보다는 최종 구조에 직접 영향을 준 실험을 중심으로 남길 예정이다.

특히 다음 부분의 분량을 확인한다.

```text
프로젝트 소개
→ 문제 정의
→ 주요 실험 및 개선 과정
→ 최종 RAG 파이프라인
→ 관리자 기능
→ 서비스 시연
→ 마무리
```

발표 후반의 최종 파이프라인과 서비스 시연 시간이 부족해지지 않도록 앞부분의 실험 설명을 적절하게 조절한다.

## Blocker / 논의 필요 사항

* 발표자료에 포함된 실험과 기능이 많아 모든 내용을 설명하면 발표 시간이 부족할 수 있으므로 핵심 실험을 중심으로 내용 조정이 필요함
* 기술적인 실험 과정을 너무 자세히 설명하면 전체 프로젝트 흐름이 끊길 수 있어 발표에서 필요한 수준까지 설명 범위를 정할 필요가 있음
* 최종 파이프라인 다이어그램에 모든 분기와 Gate를 표현하면 복잡해질 수 있으므로 발표용 표현 수준을 조정할 필요가 있음
* 슬라이드 내용과 발표 스크립트가 중복되지 않도록 슬라이드는 핵심 결과, 대본은 문제와 판단 과정을 설명하는 방식으로 역할을 구분할 필요가 있음
* 발표 후반부의 최종 파이프라인 및 서비스 시연 시간이 부족하지 않도록 앞부분 실험 설명의 분량을 조절할 필요가 있음
