## 1. Problem Definition

### 무엇을 만드는가

P1이 만든 코퍼스(58페이지)·검색 유닛(494청크)·평가셋(580문항) 위에 **답변 생성 레이어**를 얹어,
6개 업무 자연어 질의에 근거 기반으로 답하는 챗봇을 만듭니다. 산출물은 대화형 데모 UI입니다.

### 왜 필요한가

기존 대외 챗봇 '예솜24'는 **키워드 매칭 기반 카드형**이라 정의된 동작·키워드를 벗어난 자연어
질의에 대응하지 못한다. 그런데 예금보험 도메인은 금액·수수료·기간이 조건부이므로, 근거 없는
단정 답변이 곧 민원 리스크가 됩니다.

P1에서 확인한 사례가 그대로 위험 시나리오입니다. 보호한도가 페이지마다 5천만원과 1억원으로
갈리는데 둘 다 맞습니다(2025.9.1 이후 사고는 1억, 이전 사고는 5천만). 검색이 어느 페이지를
근거로 잡는지, 답변이 사고 시점을 명시하는지에 따라 답의 사실성이 달라집니다.

### P1이 넘겨준 미해결 과제

- **역할이 답을 뒤집습니다.** 착오송금인과 수취인은 정답이 정반대입니다. 역할축 41개를 정리해
  두었으나 라우팅 로직은 P1에서 구현하지 못했습니다.
- **E2E 정량 평가가 없습니다.** 검색 지표(MRR·AnswerRecall)까지만 측정했고, 답변 정답성·환각률·
  거절 품질은 생성 레이어가 있어야 측정할 수 있습니다.
- **업무 필터가 미검증 상태입니다.** 계획의 중심 가설이지만 P1에서 구현·판정하지 못했습니다.
  타 업무 청크 혼입이 top-1의 25.4%라는 진단만 나와 있습니다.

## 2. 답변 원칙 (시스템 프롬프트·검증 기준의 원천)

세 가지를 지킵니다. 기능이 아니라 제약으로 취급합니다.

1. **출처 표시** — 모든 답변에 근거가 된 원문 페이지 URL을 함께 제공합니다.
2. **민원 처리 안내** — 민원 질문은 절차 안내 → 첨부 서류 양식 → 민원 처리 페이지까지 연결합니다.
3. **Hallucination 방지** — 검색된 근거가 없으면 생성하지 않고, 모른다는 사실과 문의 경로를 안내합니다.

## 3. Proposed Method

### 3.1 검색 — P1 위에서 결정할 것

청킹(구조 인식 `all` 494유닛)은 P1 결과를 그대로 가져옵니다. P1이 남긴 선택지를 P2에서
결정합니다.

| 항목 | P1 상태 | P2에서 할 일 |
|---|---|---|
| 임베딩 모델 | bge-m3(기본값) | 후보 4종 비교 후 선정 — BGE-m3 · BGE-m3-ko · Qwen3-Embedding-8B · Nemotron-3-Embed-8B |
| 검색기 선택 | 유형별로 우열이 갈린다는 관측만 | 질문 유형 분류기 + 라우팅으로 구현 |
| 업무 필터 | 미구현(진단만) | 구현 후 실측으로 채택 여부 판정 |
| 벡터 저장소 | NumPy 캐시 | 벡터 DB(Qdrant)로 이관, 결과 동일성 검증 |
| 리랭커 | 없음 | Cross-Encoder 도입 후 비용 대비 효과 판정 |

### 3.2 답변 생성 — 의도에 따라 조립을 나눈다

질의를 정보 질문(informational)과 민원 처리(civil_petition)로 분류하고 답변 조립을 나눕니다.

- **정보 질문**: 검색된 근거로 답하고 참고 출처를 부착합니다.
- **민원 질문**: 3단으로 조립합니다.
  1. **절차 안내** — 신청 대상·기한·처리 단계를 근거 청크 기반으로
  2. **서류 안내** — 필요한 첨부 서식 다운로드 링크 (P1이 모은 `form_attachments` 103건 활용)
  3. **페이지 연결** — 실제 신청 페이지 URL로 안내해 답변에서 신청까지 동선을 연결

### 3.3 환각을 구조로 막는다

프롬프트에 "생성하지 말라"고 기술하는 것만으로는 충분하지 않다는 전제에서 출발합니다. 두 축으로
차단합니다.

- **URL을 LLM에 제공하지 않습니다.** 출처·서류·신청 페이지 URL은 모델이 생성하지 않고, 검색
  결과에서 조회한 값을 코드가 결정론적으로 답변 뒤에 부착합니다. 모델이 생성할 수 없는 값은
  환각도 발생하지 않습니다.
- **근거 사용 여부를 답변이 명시하게 합니다.** 근거 사용 여부를 모델이 표시하게 하고, 그 표시를
  기준으로 출처 부착을 결정합니다.

### 3.4 응답 속도 (추가 과제)

대국민 공개를 전제하면 응답 시간이 품질만큼 중요합니다. 단계별 소요 시간을 측정해 병목을 찾고,
비용 대비 이득이 없는 단계는 제거합니다.

## 4. Experiment Design

### 4.1 무엇을 비교하는가

| 실험 | 비교 대상 | 판단 기준 |
|---|---|---|
| G1 | 임베딩 4종 | MRR·Recall@1, 인코딩 시간, 배포 가능성 |
| G2 | 질문 유형별 검색기 (Dense · BM25 · Hybrid) | 유형별 MRR |
| G3 | 업무 필터 On/Off | leave-page-out MRR, all-or-nothing 실패율 |
| G4 | 리랭커 On/Off | Recall@5·MRR 변화, 질문당 소요 시간 |
| G5 | 답변 품질 E2E | 아래 4지표 |

### 4.2 Evaluation Metrics

**검색 단계** — P1 기준을 그대로 사용합니다. Recall@1/3/5, MRR, AnswerRecall@5.

**E2E 응답 단계** — P1에서 수행하지 못한 항목입니다. 네 가지를 측정합니다.

- **정답성**: LLM-as-a-judge가 생성 답변을 정답·원문 근거와 대조해 correct/partial/wrong
- **출처 정확도**: 인용 URL이 정답 페이지 URL과 일치하는가
- **환각률**: 컨텍스트에 없는 사실을 답변에 넣은 비율
- **거절 품질**: 범위 밖 정상 거절률 / 범위 안 과잉 거절률

평가셋은 `testset_all.jsonl`을 전체 평가로 사용하고, 실사용 표현을 반영하기 위해 구어체·복수정답
성격의 모호 질문을 추가합니다. 파이프라인 회귀용 held-out 세트도 별도로 만듭니다.

### 4.3 반영 기준

평균 점수가 상승하더라도 민원·범위 밖 질문에서 치명적 오류가 증가하면 반영하지 않습니다.
성능이 같거나 미미하게 나은 기능이 응답 시간을 크게 악화시키는 경우도 반영하지 않습니다.
