## 1. Problem Definition

### 무엇을 만드는가

P1이 만든 코퍼스(58페이지)·검색 유닛(494청크)·평가셋(851문항) 위에 **답변 생성 레이어**를 얹어,
6개 업무 자연어 질의에 **근거 기반으로 답하는 챗봇**을 만든다. 산출물은 대화형 데모 UI다.

### 왜 필요한가

기존 대외 챗봇 '예솜24'는 **키워드 매칭 기반 카드형**이라 정의된 동작·키워드를 벗어난 자연어
질의에 대응하지 못한다. 그런데 예금보험 도메인은 금액·수수료·기간이 **조건부**라, 근거 없는
단정 답변이 곧 민원 리스크다.

P1에서 실제로 본 사례가 그대로 위험 시나리오다 — 보호한도가 페이지마다 5천만원과 1억원으로
갈리는데 **둘 다 맞다**(2025.9.1 이후 사고는 1억, 이전 사고는 5천만). 검색이 어느 페이지를
근거로 잡느냐, 답변이 사고 시점을 붙이느냐에 따라 답의 사실성이 갈린다.

### P1이 넘겨준 미해결 과제

- **역할이 답을 뒤집는다.** 착오송금인 vs 수취인은 정답이 정반대다. 역할축을 41개 찾아 뒀지만
  라우팅 로직은 P1에서 만들지 못했다.
- **E2E 정량 평가가 없다.** 검색 지표(MRR·AnswerRecall)까지만 쟀고, 답변 정답성·환각률·거절
  품질은 생성 레이어가 있어야 잴 수 있다.

## 2. 답변 원칙 (시스템 프롬프트·검증 기준의 원천)

세 가지를 지킨다. 이건 기능이 아니라 **제약**이다.

1. **출처 표시** — 모든 답변에 근거가 된 원문 페이지 URL을 함께 준다.
2. **민원 처리 안내** — 민원 질문은 절차 안내 → 첨부 서류 양식 → 민원 처리 페이지까지 연결한다.
3. **Hallucination 방지** — 검색된 근거가 없으면 지어내지 않고, 모른다는 사실과 문의 경로를 안내한다.

## 3. Proposed Method

### 3.1 검색 — P1 결론을 그대로 쓴다

새로 실험하지 않는다. P1이 실측으로 고른 구성을 고정값으로 가져온다.

| 항목 | 값 | P1 근거 |
|---|---|---|
| 임베딩 | `dragonkue/BGE-m3-ko` (1024차원) | 4종 비교 MRR 0.770 |
| 기본 검색기 | Dense 단독 | 유형별 실측에서 대부분 우세 |
| Hybrid | `link_guide` 유형만 (Linear α=0.4) | 이 유형만 Hybrid 우세 |
| 청킹 | 구조 인식 `all` 494유닛 | 꼬리 프로브 AnswerRecall 0→1 |
| 업무 필터 | **Off** | leave-page-out MRR 0.672 < 0.842 |
| 리랭커 | **Off** | 개선 0에 질문당 27~210초 |

### 3.2 답변 생성 — 의도에 따라 조립을 나눈다

질의를 **정보 질문(informational) / 민원 처리(civil_petition)** 로 분류하고 답변 조립을 나눈다.

- **정보 질문**: 검색된 근거로 답하고 참고 출처를 붙인다.
- **민원 질문**: 3단으로 조립한다.
  1. **절차 안내** — 신청 대상·기한·처리 단계를 근거 청크 기반으로
  2. **서류 안내** — 필요한 첨부 서식 다운로드 링크 (P1이 모은 `form_attachments` 103건 활용)
  3. **페이지 연결** — 실제 신청 페이지 URL로 안내해 **답변 → 신청까지 동선**을 잇는다

### 3.3 환각을 구조로 막는다

프롬프트로 "지어내지 마라"라고 쓰는 것만으로는 안 된다는 전제에서 출발한다. 두 축으로 막는다.

- **URL을 LLM에게 주지 않는다.** 출처·서류·신청 페이지 URL은 LLM이 쓰게 하지 않고, 검색 결과에서
  조회한 값을 **코드가 결정론적으로** 답변 뒤에 붙인다. 모델이 만들 수 없으면 환각도 없다.
- **근거 사용 여부를 답변이 스스로 표시하게 한다.** 근거를 썼는지 여부를 모델이 명시하게 하고,
  그 표시를 기준으로 출처 부착을 결정한다.

### 3.4 복합 질문 분해 (추가 과제)

"신청 방법과 필요한 서류, 그리고 처리 기간은?"처럼 한 문장에 여러 질문이 들어오면 검색이
한쪽만 맞힌다. 하위 질문으로 나눠 **각각 검색·답변**한 뒤 합치는 방식을 검토한다.

## 4. Experiment Design

### 4.1 무엇을 비교하는가

| 실험 | 비교 대상 | 판단 기준 |
|---|---|---|
| G1 | 의도 분류기 후보 (규칙 · 통계 모델 · LLM API) | held-out 정확도, 응답시간, 비용 |
| G2 | 복합 질문 분해 On/Off | 분해 정확도(Recall·오탐), 검색 Recall@5·MRR 변화 |
| G3 | 근거 사용 판정 방식 | 출처 부착률, 오판 방향 |
| G4 | 답변 품질 E2E | 아래 4지표 |

### 4.2 Evaluation Metrics

**검색 단계** — P1 기준을 그대로 쓴다. Recall@1/3/5, MRR, AnswerRecall@5.

**E2E 응답 단계** — P1에서 못 한 것이다. 네 가지를 본다.

- **정답성**: LLM-as-a-judge가 생성 답변을 정답·원문 근거와 대조해 correct/partial/wrong
- **출처 정확도**: 인용 URL이 정답 페이지 URL과 일치하는가
- **환각률**: 컨텍스트에 없는 사실을 답변에 넣은 비율
- **거절 품질**: 범위 밖 정상 거절률 / 범위 안 과잉 거절률

평가셋은 `testset_all.jsonl`(851문항)을 전체 평가로, `testset_pipeline.jsonl`(89문항 held-out)을
Smoke 회귀로 쓴다.

### 4.3 반영 기준

P1과 같은 기준을 유지한다 — **평균 점수가 올라도 민원·범위 밖 질문에서 치명적 오류가 늘면
반영하지 않는다.** P1에서 업무 필터·리랭커를 이 기준으로 걸러냈다.

## 5. 구현 목표 체크리스트

- [ ] 하이브리드 검색 + 업무 단위 필터링 동작 (※ P1 실측으로 **필터는 폐기**됐다 — 이 항목은
      "타 업무 혼입 차단"이라는 목적으로 재해석하고, 수단은 구조 인식 청킹 + 유형 라우팅으로 본다)
- [ ] 출처 URL이 표시되는 자연어 답변 생성
- [ ] 민원 처리 질문 대응 (절차 + 서류 양식 + 신청 페이지)
- [ ] 평가 테스트셋 기반 성능 평가 및 검색 로직 개선
