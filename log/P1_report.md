## 1. 요약

6개 업무 웹페이지 58페이지를 수집·정제해 코퍼스와 494개 검색 유닛, 580문항 평가셋을 구축하고,
BM25·Dense·Hybrid 세 검색기를 색인 단위별로 비교했습니다. 계획과 가장 크게 달라진 지점은
청킹입니다. 500자 고정 분할 대신 페이지 구조를 판별해 나누는 방식을 채택했고, 그 효과를
검증하는 과정에서 페이지 회수율만으로는 검색 품질을 판단할 수 없다는 사실을 확인했습니다.

## 3. 수집과 변환

사전조사 후보는 49건이었으나 이는 사람이 손으로 정리한 목록이었습니다. 사이트 메뉴를 훑어
대조한 결과 업무 구역 안에 미수집 페이지가 더 있어(지급대행점 조회, 착오송금 지원현황, 보호대상
검색 등) 전부 추가해 58페이지로 확정했습니다.

변환은 계획대로 전 과정 규칙 기반이며 HTML→텍스트에 LLM을 쓰지 않았습니다. 표는 ` | ` 구분 행으로
보존하고, 사이트 공통 UI 노이즈는 라인 전체가 정확히 일치할 때만 제거합니다(`crawler_dy.py:3`,
`parse_raw_html.py:5,21`). 부분 일치로 제거하면 본문이 함께 잘리기 때문입니다.

갱신 감지는 본문 텍스트의 `content_sha256`을 기준으로 하며, 공백·줄바꿈을 정규화한 뒤 해시를
생성해 `new`/`updated`/`unchanged`를 판정합니다. HTML을 기준으로 삼지 않은 이유는 판본·세션
토큰 때문에 값이 불안정하기 때문입니다.

## 4. 구조 인식 청킹

계획은 "500자 고정 분할 + 헤딩 프리픽스 유지"였으나, 실제로는 페이지 구조를 판별해 나누는 방식으로
변경했습니다.

| 모드 | 유닛 수 | 규칙 |
|---|---|---|
| `page` | 58 | 페이지 통째 |
| `faq_atomic` | 135 | '질문'·'답변'이 각 2회 이상이면 FAQ로 판정, QA쌍 단위 분할 |
| `table_row` | 417 | ` | `가 20개 이상이면 표로 판정, 3행씩 묶고 청크마다 헤더 반복 |
| `all` | 494 | 제품 모드 — 위 규칙을 페이지 성격에 따라 적용 |

`python3 src/crawler/chunking.py` 자체검사 출력으로 확인한 값입니다. 페이지 ID 하드코딩이 아니라
마커 규칙이므로 재수집으로 새 FAQ가 들어와도 자동 대응합니다.

주목할 성질은 58페이지 중 40페이지가 통째 1청크로 남는다는 점입니다. 일반 안내문을 쪼개지 않으므로
"조각마다 헤딩을 다시 붙이지 않으면 대리인 질문에 상속인 서류를 답한다"던 초기 우려가 발생할
여지 자체가 사라졌습니다. 청크 길이는 median 323.5자 · 평균 387자 · 최대 9,811자입니다.

### 4.1 두 지표가 상반된 결과를 보였습니다

파산재단 표 페이지(`uc_bkrp_mng`, 본문 54,505자)의 8192토큰 잘림 경계 뒤에만 존재하는 회사 4곳의
관재인을 묻는 꼬리 프로브 4문항을 만들어 측정했습니다(07-15).

| 지표 | page / faq_atomic | table_row / all |
|---|---|---|
| 표 유형 페이지 MRR | 0.854 | 0.866 |
| 꼬리 프로브 AnswerRecall@5 | 0.000 | 1.000 |

페이지 회수율만 보면 표 행 청킹의 이득이 거의 없어 보이지만, 답을 실제로 뽑을 수 있는지로 보면
0에서 1로 갈립니다. 표 크기 스윕에서도 40행·10행은 0.250, 3행에서 1.000이 됐고, 1행도 1.000이지만
유닛이 1,148개로 늘어나 3행을 기본값으로 채택했습니다.

이 경험은 P1의 방법론적 소득으로 남았습니다. 페이지 회수율(MRR)만 보면 응답 가능성을 과대평가하게
되므로, 이후 모든 실험에서 MRR과 AnswerRecall@5를 함께 확인했습니다.

## 5. 검색기 비교

P1의 검색 실험은 **BM25·Dense·Hybrid를 색인 단위별로 비교하는 것**까지입니다. 임베딩 모델 선정과
질문 유형 라우팅은 P2에서 진행했습니다.

### 5.1 초기 169문항 평가

| 검색기 | page | faq_atomic | all |
|---|---|---|---|
| BM25 | 0.534 | 0.691 | — |
| Dense (bge-m3) | 0.752 | — | 0.759 |
| Hybrid (RRF c=60) | 0.695 | — | 0.716 |

문서찾기 MRR 기준이며 Dense가 모든 색인 단위에서 최고였습니다(문서 기재).

### 5.2 평가셋 확장으로 수치가 하락했습니다

평가셋을 580문항으로 확장하고 범위 밖을 제외한 557문항으로 재평가하자 Dense MRR이 `page` 기준
0.752→0.718, `all` 기준 0.759→0.724로 떨어졌습니다. 성능 저하가 아니라 초기 표본의 낙관 편향이
해소된 결과로 판단합니다. 같은 확장에서 BM25는 `page` 0.534→0.570으로 상승했습니다.

BM25는 청킹에 민감하고(page 0.570 → faq_atomic 0.711) Dense는 둔감합니다(0.718~0.724).
FAQ 유형에서는 Dense도 page 0.696 → all 0.926~0.928로 크게 상승합니다. 전 검색기 공통 최약
유형은 `link_guide`(Dense MRR 0.514~0.520)로 확인됐고, 이 관측이 P2의 유형별 라우팅 설계로
이어졌습니다.

이후 모든 비교는 확장 세트를 기준으로 합니다.

## 6. 평가셋 신뢰성 확보 방법

평가셋은 담당자 5명이 업무별로 작성한 뒤 통합했으며, 페이지당 3문항에서 10문항으로 확장해
174건에서 580건이 됐습니다(07-16).

근거가 원문에 문자열로 실재하는지 스크립트가 전수 검사합니다(`src/crawler/validate_testset.py`).
근거가 원문에 없으면 해당 문항은 폐기합니다. `validate_golden_labels.py`는 `must_include`가 실제
정답 페이지의 본문·링크·첨부에 존재하는지 별도로 대조합니다. 라벨 품질은 사람이나 모델의 판단이
아니라 원문 대조로 보증됩니다.

## 7. 재현성 확보

- **공유 임베딩 캐시** — `data/dense_cache/`를 커밋해 팀원이 pull만 받으면 동일한 벡터를 씁니다.
  파일명이 내용 해시라 코퍼스가 바뀌면 자동으로 무효화됩니다. `embed_corpus.py`가 유일한 생성
  진입점입니다.
- **크로스 플랫폼** — 팀에 macOS와 Windows가 섞여 있어 모든 텍스트 I/O에 `encoding="utf-8"`을
  명시하고, `.gitattributes`로 `.jsonl` 줄바꿈을 LF로 고정했습니다. CRLF가 섞이면 공유 임베딩
  캐시의 해시가 어긋나 팀 전원의 벡터가 불일치합니다.
- **평가 속도** — 평가 실행 시간을 2분 53초에서 27초로 단축해(약 6배) 반복 실험이 가능하도록
  했습니다.

- **업무 필터 미검증** — 계획의 중심 가설이었던 `business_function` 계층 필터는 P1에서 구현·검증하지

  보았으나, 실제 구현과 판정은 P2로 넘어갔습니다.
- **생성 레이어 부재** — P1의 범위는 검색까지입니다. 답변 정답성·환각률·거절 품질은 생성 레이어가
  만들어진 뒤의 과제로 넘겼습니다.
- **Parent-Child 보류** — FAQ 검색에 Parent-Child 구조를 적용하기로 논의했으나(07-15), 검색 성능
  검증 단계로 미뤘습니다.
- **시점 조건 태깅 미구현** — 보호한도 5천만원/1억원처럼 경과규정상 둘 다 맞는 수치가 있으나,
  전용 메타 태그 없이 본문의 시점 문구("2025.9.1 이후")에 의존합니다.
