## 1. 요약

6개 업무 웹페이지 58페이지를 수집·정제해 494개 검색 유닛과 851문항 평가셋을 만들었고, 검색 구성을
실측으로 선정했습니다. 계획의 중심 가설이었던 업무 필터는 폐기했으며, 대신 계획에 없던 구조 인식
청킹이 성능 개선의 핵심 축이 됐습니다.

## 2. 최종 산출물

| 산출물 | 규모 | 위치 |
|---|---|---|
| 원본 HTML | 58 + 페이지네이션 109 + 상세 31 | `data/raw_html/` |
| 정규화 본문 | 58 txt · 총 172,860자 (median 1,118자, max 54,505자) | `data/text/` |
| 페이지 메타 | 58 json — links 51 · form_attachments 103 · images 73 · videos 1 | `data/meta/` |
| 코퍼스 | 58행 (메타 + 본문) | `data/corpus.jsonl` |
| 검색 유닛 | 494 (구조 인식 청킹 `all` 모드) | `data/chunks_all.jsonl` |
| 공유 임베딩 | 4모드 × 1024차원 | `data/dense_cache/` |
| 평가셋 | 851문항 (범위 안 819 + 범위 밖 32) | `data/testset/testset_all.jsonl` |
| held-out | 89문항 | `data/testset/testset_pipeline.jsonl` |

정적 `<a href>` 첨부는 0건입니다. KDIC는 첨부를 JS 다운로드 함수로 제공하므로, 함수를 역해석해
수집한 `form_attachments` 103건이 그 역할을 대신합니다.

## 3. 수집

사전조사 후보는 49건이었으나 이는 사람이 손으로 정리한 목록이었습니다. 사이트 메뉴를 훑어
대조한 결과 업무 구역 안에 미수집 페이지가 더 있어(지급대행점 조회, 착오송금 지원현황, 보호대상
검색 등) 전부 추가해 58페이지로 확정했습니다.

변환은 계획대로 전 과정 규칙 기반이며 HTML→텍스트에 LLM을 쓰지 않았습니다. 표는 ` | ` 구분 행으로
보존하고, 사이트 공통 UI 노이즈는 라인 전체가 정확히 일치할 때만 제거합니다(`crawler_dy.py:3`,
`parse_raw_html.py:5,21`). 부분 일치로 제거하면 본문이 함께 잘리기 때문입니다.

## 4. 구조 인식 청킹

계획은 "500자 고정 분할 + 헤딩 프리픽스 유지"였으나, 실제로는 페이지 구조를 판별해 나누는 방식으로
변경했습니다.

| 모드 | 유닛 수 | 규칙 |
|---|---|---|
| `page` | 58 | 페이지 통째 |
| `faq_atomic` | 135 | '질문'·'답변'이 각 2회 이상이면 FAQ로 판정, QA쌍 단위 분할 |
| `table_row` | 417 | ` | `가 20개 이상이면 표로 판정, 3행씩 묶고 청크마다 헤더 반복 |
| `all` | 494 | 제품 모드 — 위 규칙을 페이지 성격에 따라 적용 |

`python3 src/crawler/chunking.py` 자체검사 출력으로 확인한 값입니다. 페이지 ID 하드코딩이 아니라
마커 규칙이므로 재수집으로 새 FAQ가 들어와도 자동 대응합니다.

주목할 성질은 58페이지 중 40페이지가 통째 1청크로 남는다는 점입니다. 일반 안내문을 쪼개지 않으므로
"조각마다 헤딩을 다시 붙이지 않으면 대리인 질문에 상속인 서류를 답한다"던 초기 우려가 발생할
여지 자체가 사라졌습니다. 청크 길이는 median 323.5자 · 평균 387자 · 최대 9,811자입니다.

### 4.1 두 지표가 상반된 결과를 보였습니다

파산재단 표 페이지(`uc_bkrp_mng`, 본문 54,505자)의 8192토큰 잘림 경계 뒤에만 존재하는 회사 4곳의
관재인을 묻는 꼬리 프로브 4문항으로 측정했습니다.

| 지표 | page / faq_atomic | table_row / all |
|---|---|---|
| 표 유형 페이지 MRR | 0.854 | 0.866 |
| 꼬리 프로브 AnswerRecall@5 | 0.000 | 1.000 |

페이지 회수율만 보면 표 행 청킹의 이득이 거의 없어 보이지만, 답을 실제로 뽑을 수 있는지로 보면
0에서 1로 갈립니다. 표 크기 스윕에서도 40행·10행은 0.250, 3행에서 1.000이 됐고, 1행도 1.000이지만
유닛이 1,148개로 늘어나 3행을 기본값으로 채택했습니다.

이 경험은 P1의 방법론적 소득으로 남았습니다. 페이지 회수율(MRR)만 보면 응답 가능성을 과대평가하게
되므로, 이후 모든 실험에서 MRR과 AnswerRecall@5를 함께 확인했습니다.

## 5. 검색 구성

### 5.1 평가셋 확장으로 수치가 하락했습니다

169문항에서 557문항(범위 밖 제외)으로 확장하자 Dense MRR이 `page` 기준 0.752→0.718로 떨어졌습니다.
성능 저하가 아니라 초기 표본의 낙관 편향이 해소된 결과로 판단합니다. 같은 확장에서 BM25는
0.534→0.570으로 상승했습니다. 이후 모든 비교는 확장 세트를 기준으로 합니다.

### 5.2 임베딩 4종 비교

동일 조건(`all` 494청크, 557문항, GPU)의 실측입니다(`data/embedding_eval/dy.json` 원본 실행 결과).

| 모델 | 차원 | MRR | Recall@1 | 494청크 인코딩 |
|---|---|---|---|---|
| bge-m3 | 1024 | 0.724 | 0.589 | 8.0s |
| BGE-m3-ko | 1024 | 0.770 | 0.641 | 7.7s |
| Qwen3-Embedding-8B | 4096 | 0.767 | 0.643 | 19.0s |
| Nemotron-3-Embed-8B | 4096 | 0.846 | 0.752 | 17.7s |

지표 1위는 Nemotron이었으나 채택하지 않았습니다. 8B급이라 오프라인 CPU 배포 제약에 걸린다는
판단이었습니다. 프로덕션은 `dragonkue/BGE-m3-ko`로 고정돼 있고(`src/retrieval.py:15`),
`dense_cache` 벡터도 1024차원입니다.

다만 미채택 사유는 문서 기재이며 코드로는 확인되지 않으므로, 배포 환경이 바뀌면 재검토 대상입니다.

### 5.3 질문 유형별로 최적 검색기가 달랐습니다

BM25는 청킹에 민감하고(page 0.570 → faq_atomic 0.711) Dense는 둔감합니다(0.718~0.724). FAQ 유형에서는
Dense도 page 0.696 → all 0.926~0.928로 크게 상승합니다. 전 검색기 공통 최약 유형은 `link_guide`
(Dense MRR 0.514~0.520)였고, 이 유형에서만 Hybrid가 Dense를 앞섰습니다.

따라서 라우팅을 "전부 Hybrid"가 아니라 "기본 Dense, `link_guide`만 Hybrid"로 확정했습니다
(`src/retrieval.py:284`). 결합 방식도 RRF보다 나은 Linear fusion(α=0.4)을 적용했습니다. 다만 α는
59문항 소표본 스윕 결과라 코드 주석에 "확정값 아님"으로 명시해 두었습니다.

## 6. 계획이 뒤집힌 지점 — 업무 필터 폐기

P1 계획의 중심 가설이었습니다. "오답 원인이 타 업무 청크 혼입 25.4%로 특정됐으므로 검색 공간을
업무로 좁히면 원인이 사라진다"는 논리였고, 초기 측정에서도 필터를 켜면 Recall@3가 63.5%→75.1%로
오르는 것으로 나타났습니다.

문제는 그 측정이 낙관적이었다는 점입니다. 같은 페이지에서 파생된 형제 질문들이 학습·평가에 함께
섞여 있었는데, 형제 질문은 `business_function`이 100% 동일하므로 분류기 점수가 실제보다 높게
나옵니다.

이에 자기 자신만 제외하는 leave-one-out이 아니라, 같은 gold page의 형제 질문을 후보 풀에서 전부
제외하는 leave-page-out으로 재측정했습니다(`src/crawler/bf_score_fusion_eval.py`).

| 조건 | 필터 ON | 필터 OFF |
|---|---|---|
| 편향 포함 (821문항) | MRR 0.759 | 0.775 |
| leave-page-out | MRR 0.672 | 0.842 |

정확하게 측정하자 격차가 오히려 커졌습니다. 또한 오분류로 정답 업무가 통째로 누락되는
all-or-nothing 실패가 63/821(7.7%) 발생했습니다. 점수에 약하게 반영하는 절충안(가중합·RRF 가산)도
모두 순정 검색보다 손해였습니다.

2026-07-24 커밋 `20bf4fc`로 기본 Off 처리했습니다. 코드는 제거하지 않고 남겼으나
`_build_engines()`가 `bf_classifier`를 전달하지 않아 완전 비활성이며, `BusinessFunctionClassifier`
클래스 자체도 주석 처리돼 있습니다(`src/retrieval.py:337`, `src/query_classifier.py:59-68`).

검색 공간을 좁힌다는 방향 자체는 유효했으나, 그 축이 "업무"가 아니라 "질문 유형"이어야 했다는 것이
결론입니다.

## 7. 계획에 없던 시도 — 리랭커

`bge-reranker-v2-m3`로 top-20을 재정렬해 측정했습니다. Recall@5 개선은 0이고 MRR은 소폭 하락한
반면 질문당 27~210초(CPU)가 소요됐습니다. 2026-07-23 팀 결정으로 기본 Off 처리했습니다
(`src/pipeline.py:28-33`). 코드는 재도입에 대비해 남겼으며, GPU·경량 설정에서 재검증할 수 있습니다.

## 8. 평가셋 신뢰성 확보 방법

851문항 전부에 대해 근거가 원문에 문자열로 실재하는지 스크립트가 전수 검사합니다
(`src/crawler/validate_testset.py`, 851/851 통과, 오류 0건). 근거가 원문에 없으면 해당 문항은
폐기합니다. `validate_golden_labels.py`는 `must_include`가 실제 정답 페이지의 본문·링크·첨부에
존재하는지 별도로 대조합니다. 라벨 품질은 사람이나 모델의 판단이 아니라 원문 대조로 보증됩니다.

## 9. 남긴 한계

- **역할 라우팅 미착수** — "모르는 돈이 잘못 들어왔어요"(수취인) 질의가 착오송금인용 서류를
  검색하는 문제는 데이터로 확인했으나, 되묻거나 역할을 판별하는 로직은 P1 범위에서 구현하지
  못했습니다. 역할축은 6개 업무에서 41개를 정리해 두었습니다.
- **E2E 정량 평가 미실시** — P1의 범위는 검색까지였습니다. 답변 정답성·환각률·거절 품질은 생성
  레이어가 만들어진 뒤의 과제로 넘겼습니다.
- **시점 조건 태깅 미구현** — 보호한도 5천만원/1억원처럼 경과규정상 둘 다 맞는 수치가 있으나,
  전용 메타 태그 없이 본문의 시점 문구("2025.9.1 이후")를 생성 단계가 읽는 데 의존합니다.
- **문서 기재 수치의 재현** — 5장 표의 상당수는 `docs/`의 실험 기록에서 인용했으며 이번 보고를
  작성하며 전부 재실행하지는 않았습니다. 임베딩 4종 비교만 원본 실행 결과
  (`data/embedding_eval/dy.json`)로 교차 확인했습니다.
