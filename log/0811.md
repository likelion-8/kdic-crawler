## 금일 진행할 사항

### 1. 기존 문서·청크 조회 기능 마무리

Supabase에 저장된 기존 문서와 청크를 관리자 화면에서 안정적으로 조회할 수 있도록 조회 API를 마무리한다.

구현 범위:

```text
documents 목록 조회
document_chunks 목록 조회
페이지네이션
문서 상세 조회
문서별 연결 청크 조회
```

최종적으로 다음 흐름이 가능하도록 한다.

```text
관리자 로그인
→ 문서 목록 조회
→ 검색·필터
→ 문서 선택
→ 문서 상세 조회
→ 연결된 청크 확인
```

---

### 2. `pipeline_jobs` Jobs API 구현 마무리

향후 문서 재적재 및 검색 데이터 변경 작업을 비동기 작업으로 관리할 수 있도록 `pipeline_jobs` 기반 API를 구현한다.

구현 범위:

```text
Job 생성
Job 목록 조회
Job 상세 조회
Job 상태 저장
```

대상 API 예시:

```text
POST /api/admin/jobs
GET  /api/admin/jobs
GET  /api/admin/jobs/{job_id}
```

이번 단계에서는 Redis·ARQ Worker를 실제 실행하지 않고, DB 기반으로 Job 생성·조회 및 상태 관리가 가능한 구조까지만 구현한다.

---

### 3. 신규 URL 검증 기능 구현

관리자가 신규 문서를 등록하기 전에 URL 자체를 검증하는 기능을 구현한다.

검증 항목:

```text
URL 형식 검증
허용 도메인 여부 확인
기존 documents.url 중복 여부 확인
실제 접근 가능한 URL인지 확인
```

잘못된 URL이나 기존에 등록된 URL에 대해 불필요한 크롤링 및 후속 처리가 실행되지 않도록 Preview 이전 단계에서 검증한다.

---

### 4. 신규 문서 Preview 구조 구현

신규 URL을 실제 운영 데이터에 바로 반영하지 않고 관리자가 먼저 내용을 확인할 수 있도록 Preview 기능을 구현한다.

처리 흐름:

```text
신규 URL
→ 크롤링
→ 본문 파싱
→ 업무 분류
→ 청킹
→ Preview 반환
```

구현 범위:

* URL 크롤링
* 본문 파싱
* 문서 제목 및 기본 메타데이터 추출
* 업무 분류 결정
* 기존 RAG 청킹 로직 적용
* 생성된 청크 목록 반환
* Preview 단계에서는 `documents`, `document_chunks` 운영 데이터 미반영

관리자가 실제 반영 전 크롤링 결과와 청킹 결과를 확인할 수 있도록 하는 것을 목표로 한다.

---

### 5. `change_requests` 구조 설계 및 구현

관리자 승인 또는 삭제 요청이 바로 운영 검색 데이터에 적용되지 않도록 변경 요청을 별도로 저장하는 구조를 구현한다.

대상 변경 유형:

```text
신규 문서 추가
기존 문서 삭제
```

구현 범위:

```text
change_requests 테이블 생성
신규 문서 추가 요청 저장
기존 문서 삭제 요청 저장
요청 상태 저장
```

상태 예시:

```text
PENDING
APPLYING
APPLIED
REJECTED
FAILED
```

Preview 승인 이후 실제 운영 반영 작업과 분리하여 관리할 수 있도록 구성한다.

---

### 6. 변경 요청 조회 API 구현

관리자가 현재 적용 대기 중인 변경 요청을 확인할 수 있도록 조회 기능을 구현한다.

구현 범위:

```text
변경 요청 목록 조회
상태별 필터
변경 요청 상세 조회
```

관리자 화면에서 신규 문서 추가 및 기존 문서 삭제 요청의 처리 상태를 확인할 수 있도록 한다.

---

### 7. 검색 데이터 버전 관리 정책 마무리

현재 결정된 `index_version`, `active_version` 구조를 기반으로 평가 실패 및 Rollback 정책을 확정한다.

논의 및 확정 항목:

```text
새 버전 평가 실패 시 기존 버전 유지 방식
Rollback 시 이전 버전 복구 방식
버전별 상태 관리
```

기본 방향:

```text
현재 active_version
        ↓
새 index_version 생성
        ↓
검색 데이터 생성 및 평가
      ↙             ↘
   평가 성공          평가 실패
      ↓                ↓
새 버전 활성화      기존 버전 유지
```

Rollback은 기존 검색 데이터를 다시 생성하기보다 이전 정상 버전을 다시 `active_version`으로 지정하는 방식을 우선 검토한다.

---

### 8. RAG 토큰 사용량 최적화 방향 검토

현재 측정한 단계별 토큰 사용량을 바탕으로 답변 품질을 유지하면서 불필요한 LLM 호출과 토큰 사용을 줄일 수 있는 방법을 검토한다.

주요 검토 대상:

```text
멀티쿼리 분해 단계
Intent 분류
출처 재확인(Source Recheck)
최종 답변 생성
```

특히 출처 재확인 과정과 멀티쿼리 과정에서 발생하는 추가 토큰 사용을 줄일 수 있는 구조를 비교한다.

검토 항목:

* 여러 LLM 호출을 하나의 Structured Output 호출로 통합할 수 있는지
* 멀티쿼리 생성 개수를 동적으로 제한할 수 있는지
* 단순 질문의 경우 멀티쿼리를 생략할 수 있는지
* 출처 재확인 단계의 호출 조건을 제한할 수 있는지
* 프롬프트 길이 및 검색 컨텍스트 크기를 줄일 수 있는지
* 토큰 절감에 따른 정확도 및 응답 품질 영향
