## 1. Problem Definition

### 무엇을 해결하려는가

P2까지 만든 챗봇은 동작하지만 운영할 수 없는 상태입니다.

답변 품질을 좌우하는 것은 적재된 데이터와 검색 파라미터 두 가지인데, 지금은 둘 다 코드에
있습니다. 새 안내 페이지가 생기면 개발자가 크롤러를 실행하고 적재 스크립트를 돌려야 하고,
Top-K를 5에서 3으로 바꾸려면 `src/pipeline.py`의 상수를 수정해야 합니다. `USE_RERANKER`,
`K_CANDIDATES`, `K_FINAL`이 모두 코드 상수입니다.

> 매 변경마다 개발자가 개입해야 하는 시스템은 지속적으로 운영되기 어렵습니다. 운영자가 데이터를
> 추가하고, 파라미터를 조정하고, 그 변경이 품질에 미치는 영향을 직접 확인할 수 있어야 합니다.

### 왜 어려운가 — 파라미터마다 반영 비용이 다르다

이 프로젝트의 설계를 가르는 핵심 구분입니다.

| 구분 | 예시 | 반영 비용 |
|---|---|---|
| **검색 시점** 파라미터 | Top-K, 리랭킹 유무, Hybrid 결합비 | 질의 시 적용 → 즉시 비교 가능 |
| **적재 시점** 파라미터 | Chunk Size, 청킹 방식 | 변경 시 기존 데이터 전체 재청킹·재적재 |

단순하게 구현하면 파라미터를 하나 바꿔볼 때마다 494청크 전체 재적재가 발생합니다. 두 종류를
서로 다른 방식으로 다루지 않으면, 관리자 화면은 만들어도 실제로는 쓰이지 않게 됩니다.

### 왜 지금 중요한가

P1·P2가 남긴 미완 과제 중 셋은 관리 도구가 있어야 해결됩니다.

- **E2E 정량 평가 부재** — P2에서 테스트셋 전체를 자동 채점하는 `evaluate_pipeline.py`를 만들었다가
  "파라미터 튜닝은 아직 이르다"는 판단으로 롤백했습니다. 라벨 검증 도구는 남아 있으므로 라벨은
  검증된 상태이고 채점기만 없습니다. 평가를 사람이 매번 손으로 돌리는 한 이 공백은 반복됩니다.
- **파라미터 튜닝 보류** — 롤백 사유의 배경에는 바꿔 보고 비교할 수단이 없다는 점이 있었습니다.
  P2에서 업무 필터를 끈 것도, 리랭커 판정을 GPU까지 미룬 것도 매번 스크립트를 손으로 돌려
  얻은 결론입니다.
- **데이터 갱신 추적** — 원본 사이트는 바뀝니다(공시이율 표는 매월). 갱신 감지는 `content_sha256`
  으로 만들어 두었으나, 재수집을 누가 언제 트리거하고 결과를 어디서 확인하는지가 없습니다.

## 2. Background & Baseline

### 2.1 물려받는 것

| 영역 | P2 종료 시점 상태 |
|---|---|
| 코퍼스 | 58페이지 · 494검색유닛(구조 인식 청킹) |
| 평가셋 | 골든셋 853문항 + 파이프라인 회귀용 held-out 세트 |
| 임베딩 | BGE-m3-ko (1024차원), 공유 캐시 커밋 |
| 벡터 저장소 | Qdrant 로컬(임베디드) — 494청크 적재 |
| 검색 | 질문 유형별 라우팅. 업무 필터는 배제, 리랭커는 GPU 검증 전까지 Off |
| 생성 | 8모듈 + `rag_answer()` 단일 진입점 |
| UI | Streamlit 단일 프로세스 데모 |

### 2.2 지금 구조가 관리에 맞지 않는 지점

- **단일 프로세스** — Streamlit 한 프로세스가 UI와 RAG를 함께 들고 있습니다. 관리자 기능을 여기에
  얹으면 일반 사용자 화면과 권한 경계가 없습니다.
- **파일 기반 상태** — 코퍼스·청크·임베딩이 JSONL과 npy 파일이라, 화면에서 "이 페이지만 검색에서
  빼기" 같은 조작을 반영할 자리가 없습니다.
- **관측 부재** — 어떤 질문이 들어와 어떤 근거로 답했는지 남지 않아, 운영 중 품질 저하를 발견할
  방법이 없습니다.
- **파라미터가 코드에 있음** — 위에 적은 그대로입니다.

### 2.3 실측으로 배제한 것

P1·P2가 데이터로 판정해 끈 것들입니다. 되살릴 근거가 나오기 전에는 다시 켜지 않습니다.

| 항목 | 배제 근거 |
|---|---|
| 업무(`business_function`) 하드필터 | leave-page-out MRR 0.672(ON) < 0.842(OFF), 오분류로 정답 업무가 통째로 빠지는 실패 7.7% |
| Parent-Child 검색 | 근거가 이미 단일 청크 안에 온전해 불필요 |

이 둘은 P3의 평가 게이트가 제대로 동작하는지 확인하는 **시험 케이스**로도 씁니다(4장 A4).

### 2.4 보류한 것 — 리랭커는 GPU에서 다시 판정합니다

리랭커(cross-encoder)는 배제가 아니라 **판정 보류** 상태입니다. CPU에서는 문항당 96초가 걸려
실서비스에 쓸 수 없다는 것만 확정됐고, **품질 판정은 아직 끝나지 않았습니다.**

측정이 두 번 엇갈렸습니다. 6문항 소표본에서는 MRR이 0.71→0.64로 떨어졌는데, 이후 측정에서는
검색 품질이 개선되는 것으로 나왔습니다. 표본이 작아 어느 쪽도 결론으로 쓸 수 없습니다.

**AWS GPU 자원이 확보되면 재검증합니다.** 비교 조건은 이미 정해 두었습니다.

| 축 | 조건 |
|---|---|
| 모델 | `dragonkue/bge-reranker-v2-m3-ko` vs `BAAI/bge-reranker-v2-m3` |
| 정밀도 | FP32 · FP16 |
| 후보 수 | 5 · 8 · 10 · 15 · 20 |
| 지표 | MRR · Recall@5 · 문항당 리랭킹 시간 · 전체 응답 시간 |

**평가셋은 소표본이 아니라 held-out 세트 전체를 씁니다.** 앞선 두 측정이 엇갈린 이유가 표본
크기이므로 같은 실수를 반복하지 않기 위해서입니다.

리랭커 실험은 서비스 개발을 막지 않는 **별도 개선 후보**로 관리합니다. GPU 결과가 나오기 전까지
기본값은 Off이고, 도입이 결정되면 3.5절의 3단계 게이트를 그대로 통과해야 반영됩니다 — 이 도구의
첫 실사용 사례가 됩니다.

## 3. Proposed Method

### 3.1 웹 서비스로 분리한다

Streamlit 데모를 프론트엔드·백엔드가 분리된 웹 서비스로 확장하고, 그 위에 관리자 기능을 얹습니다.

- 프론트엔드와 백엔드는 API 스키마를 먼저 확정한 뒤 병렬 개발합니다. 프론트엔드는 확정된 스키마로
  만든 Mock 데이터로 화면부터 완성합니다.
- 기존 `src/`의 RAG 파이프라인은 그대로 두고 백엔드가 호출만 합니다. 관리 기능 때문에 검증된
  검색·생성 로직을 건드리지 않습니다.
- 사용자 화면과 관리자 화면은 인증·권한 경계로 분리합니다.

### 3.2 관리 범위

기업(클라비)이 정한 관리 대상 3종을 화면으로 만듭니다.

| 관리 대상 | 하는 일 |
|---|---|
| **검색 데이터** | 적재된 페이지·청크·메타데이터 조회, 신규 URL 추가, 검색 대상 제외/포함 |
| **데이터 파이프라인** | 재수집·재적재 트리거, 단계별 처리 상태 확인 |
| **RAG 파라미터** | Top-K·청킹 방식 등 변경, 변경 전후 검색 결과 비교, 운영 반영 |

여기에 운영에 필요한 화면을 더합니다 — 대화 로그(실사용 관찰), 평가(테스트셋 기반 정량 비교),
활동 로그(누가 무엇을 바꿨는가).

> 페이지 **본문을 직접 수정하는 기능은 만들지 않습니다.** 재크롤링하면 수정 내용이 사라지므로,
> 고칠 수 있게 두면 화면이 사실과 다른 상태를 보여주게 됩니다. 검색 대상에서 빼거나 다시 넣는
> 것까지만 허용합니다.

### 3.3 핵심 설계 1 — 적재 전에 확인하고 넣는다

신규 URL을 입력해도 곧바로 적재하지 않습니다. 파싱 → 청킹 → 검증을 미리 실행해 결과를 보여주고,
담당자가 확인한 뒤에만 적재합니다.

잘못 잘린 청크나 누락된 메타데이터를 적재 전에 걸러내기 위한 장치입니다. P1에서 표가 잘리면
페이지는 검색되는데 답을 못 뽑는 사례(AnswerRecall 0.000)를 확인했습니다. 같은 실패를 운영 중에
반복하지 않으려면 사전 확인이 필요합니다.

미리보기는 운영 데이터에 영향이 없는 단계까지만 실행하고, 색인·반영은 적재를 승인한 뒤에
수행합니다.

### 3.4 핵심 설계 2 — 파라미터를 반영 비용으로 나눠 다룬다

| | 검색 시점 (Top-K·리랭킹·결합비) | 적재 시점 (Chunk Size·청킹 방식) |
|---|---|---|
| 비교 방법 | 운영 인덱스에 그대로 두 설정으로 질의해 나란히 비교 | 테스트용 소량 재적재 후 비교 |
| 반영 | 즉시 | 결정한 경우에만 전체 재적재 |

적재 시점 파라미터를 소량으로 비교하려면 **소량 테스트가 전체를 재현해야 합니다.** 이를 위해
테스트 데이터에 Hard Negative(타 업무의 유사 문구 청크)를 원본 분포대로 포함합니다. P1이 측정한
"top-1의 25.4%가 타 업무" 혼입이 그 분포이며, 이를 빼고 소량 테스트를 하면 실제보다 좋은 결과가
나옵니다.

> 재현성이 확보되어야만 전체 재적재 없이 소량 비교로 반영 여부를 판단할 수 있습니다. 재현되지
> 않으면 적재 시점 파라미터는 전체 재적재로만 판단해야 합니다.

### 3.5 핵심 설계 3 — 변경은 3단계를 거친다

파라미터·프롬프트 변경이 즉시 운영에 나가지 않도록 ①초안 편집 → ②초안 평가 → ③운영 반영 순서를
강제합니다. 최신 평가가 기준을 통과해야 반영 버튼이 열리고, 초안을 수정하면 평가는 무효가 됩니다.

P1·P2에서 "평균 점수가 올라도 민원·범위 밖 질문에서 치명적 오류가 늘면 반영하지 않는다"는 기준으로
업무 필터를 배제했습니다. **그 기준을 사람의 판단이 아니라 화면의 게이트로 만드는 것**이
P3의 핵심 과제입니다.

### 3.6 핵심 설계 4 — 위험 작업은 사유를 남기고 통제한다

관리자 작업은 운영 데이터를 바꿉니다. 되돌릴 수 있는 것과 없는 것을 구분해 통제합니다.

- 쓰기 요청에 멱등키를 요구합니다. 같은 요청이 중복 전달돼도 두 번 실행되지 않게 합니다.
- 위험 작업은 확인 단계에서 변경 사유를 필수로 받고, 결과를 활동 로그에 남깁니다.
- 되돌리기 어려운 작업(전체 캐시 비우기, 권한 변경, 롤백)은 비밀번호 재확인을 요구합니다.
- 활동 로그는 추가 전용으로 두고 수정·삭제 기능을 만들지 않습니다.

권한은 4단계로 나눕니다 — 조회 전용 / 파이프라인 운영 / 편집·게시 / 계정·롤백 관리. 화면에서
감추는 것은 편의 기능일 뿐이며, 최종 판정은 서버가 합니다.

### 3.7 관측 — 무엇이 들어오고 무엇으로 답했는가

운영 중 품질 저하를 발견하려면 실사용 기록이 필요합니다. 질문·답변·의도·검색 경로·응답 시간·사용
모델을 저장하고, 대화 로그 화면에서 조회합니다. 개인정보는 마스킹해 저장하고 원문 복호화 경로는
두지 않습니다.

## 4. Experiment Design

관리 도구는 동작 여부만으로 평가할 수 없습니다. **운영자가 내리는 결정이 실제로 나아지는가**를
측정합니다.

| 실험 | 질문 | 측정 |
|---|---|---|
| **A1** | 소량 테스트가 전체를 재현하는가 | 같은 파라미터 변경을 소량 세트와 전체 골든셋에서 각각 평가해 순위 일치도와 MRR 차이 |
| **A2** | Hard Negative 비율이 재현성을 좌우하는가 | 타 업무 청크 비율 0% / 실제 분포 / 과다 세 조건에서 A1을 반복 |
| **A3** | 미리보기가 불량 적재를 막는가 | 의도적으로 잘리는 페이지(대형 표·FAQ)를 넣어 적재 전 발견율 측정 |
| **A4** | 게이트가 나쁜 변경을 막는가 | P1·P2가 폐기한 설정(업무 필터 On)을 초안으로 넣고 게이트가 반려하는지 확인 |
| **A5** | 파라미터 변경이 품질에 주는 영향 | Top-K 3/5/10, 청킹 방식 변경의 전후 비교 |
| **A6** | 리랭커가 GPU에서 이득이 되는가 | 2.4절 조건표대로 모델 2종 × 정밀도 2종 × 후보 수 5조건을 held-out 전체로 비교 |

A4가 특히 중요합니다. 이미 실측으로 폐기한 설정을 시스템이 걸러내지 못하면, 이 도구는 사람의
판단을 보조하는 것이 아니라 잘못된 결정을 빠르게 반영하는 장치가 됩니다.

### Evaluation Metrics

- **검색 품질**: Recall@1/3/5, MRR, AnswerRecall@5 — P1 기준 그대로
- **답변 품질**: 정답성(LLM-as-a-judge), 출처 정확도, 환각률, 거절 품질 — P2가 수행하지 못한 항목
- **운영 지표**: 적재 전 불량 발견율, 파라미터 변경 리드타임, 재적재 없이 판단한 비율

평가셋은 골든셋을 전체 평가로, held-out 세트를 Smoke 회귀로 사용합니다.

## 5. 기술 스택과 핵심 결정

| 영역 | 후보 | 판단 기준 |
|---|---|---|
| 프론트엔드 | React + TypeScript | API 타입을 코드로 관리하고 Mock과 실제 응답 구조를 동일하게 유지 |
| 백엔드 | FastAPI | 기존 RAG 코드가 Python이라 직접 연결 가능, 스키마 명시와 문서 자동 생성 |
| RDB | PostgreSQL | 대화·피드백·문서 메타·관리자 활동 로그와 변경 이력 저장 |
| 벡터 저장소 | ~~현행 Qdrant 유지 vs PostgreSQL + pgvector 통합~~ → **Supabase Postgres + pgvector로 확정(2026-08-03)** | 운영 대상 수, 관리자 화면에서의 조작 편의, 정합성 검증 비용 |
| 실행 환경 | Docker Compose | 저장소·백엔드·프론트엔드를 한 번에 띄워 팀원 환경 차이를 없앰 |
| 리랭킹 실행 환경 | AWS GPU 인스턴스 | CPU에서 문항당 96초가 걸려 실서비스 불가. GPU 확보 후 도입 여부 재판정(2.4절) |

**벡터 저장소를 어디에 둘지가 이번 단계의 첫 결정입니다.** 관리자가 페이지를 검색에서 빼거나
다시 넣는 조작을 하려면 메타데이터와 벡터가 함께 움직여야 하는데, 파일·Qdrant·RDB가
따로 있으면 정합성을 사람이 맞춰야 합니다. 착수 첫 주에 두 안을 비교해 확정하기로 했습니다.

두 안의 목표 구조는 다음과 같았습니다.

- **분리안** — Qdrant가 벡터 검색을, PostgreSQL이 메타데이터 CRUD와 변경 이력을 담당하고
  docker-compose로 함께 관리합니다. 각 저장소가 잘하는 일만 맡는 대신, 페이지를 검색에서
  뺄 때 두 저장소를 함께 갱신해야 하므로 정합성 책임이 애플리케이션에 남습니다.
- **통합안** — PostgreSQL에 pgvector를 얹어 메타데이터와 벡터를 한 트랜잭션에서 다룹니다.
  운영 대상이 하나로 줄지만, 검색 성능이 현행과 같은지 확인이 필요합니다.

> ✅ **2026-08-03 통합안으로 확정·전환 완료.** Supabase Postgres에 pgvector를 얹어
> `documents`(58) · `document_chunks`(494 · `embedding vector(1024)`)를 함께 둡니다.
> 운영 Dense 검색은 `PgVectorDenseRetriever`가 그 테이블을 직접 읽습니다(`src/retrieval.py:328`).
> 거리 방식은 Qdrant와 같은 코사인이고, 현재 규모에서는 HNSW·IVFFlat 없이 exact search입니다.
> `QdrantDenseRetriever`는 롤백 대비로 코드에만 남아 있고 운영 경로에서 호출되지 않습니다.
> 검색 제외는 `documents.is_active` 플래그로 처리하며, 내리면 트리거가 그 페이지의 청크까지
> 함께 내립니다.

전환 시 **이관 전후 동일 질의로 MRR과 Top-K가 일치하는지 검증한 뒤에만 전환한다**는 기준을
지켰습니다 — 494청크 전량에 대해 DB 저장 임베딩과 재생성 임베딩을 대조해 불일치 0건(최대 오차
7.27×10⁻⁹), 질문 유형 분류기도 로컬 기반과 Supabase 기반 결과가 819건 전부 일치했습니다.

## 11. 완료 기준

- 프론트엔드에서 들어온 질문이 백엔드를 거쳐 기존 RAG 파이프라인으로 연결되고, 답변·출처·첨부가
  화면에 표시됩니다.
- 신규 URL을 관리자 화면에서 입력해 미리보기 → 적재 → 재색인 → 검색 반영까지 이어집니다.
- 파라미터를 바꿔 전후 검색 품질을 화면에서 비교하고, 게이트를 통과해야 운영에 반영됩니다.
- 데이터 정합성이 검증됩니다(코퍼스 청크 수 = 벡터 저장소 건수 = BM25 대상 문서 수).
- 모든 위험 작업이 사유와 함께 활동 로그에 남습니다.
- P1·P2가 폐기한 설정(업무 필터)을 초안으로 넣으면 게이트가 반려합니다.
- 리랭커는 GPU 재검증 결과가 나오면 게이트를 통과한 경우에만 반영됩니다.
