## 1. Problem Definition

### 어떤 task인가

예금보험공사(KDIC)의 6개 업무 안내 페이지를 근거로 사용자 질문에 답하는 한국어 RAG 챗봇을
만들고, 그것을 **개발자 없이 운영할 수 있는 상태**까지 끌어올리는 것이 과제입니다.

대상 업무는 예금자보호제도 · 예금보험금 안내 · 고객 미수령금 신청 · 착오송금 반환 신청 ·
채무조정 안내 · 은닉재산 신고 여섯 가지입니다. 기존 룰베이스 챗봇 **예솜24**를 RAG로 다시
만드는 과제이며, 서비스 이름은 그대로 씁니다.

### 왜 검색 품질이 이 문제의 핵심인가

**틀린 답이 곧 금전 피해로 이어지는 도메인**입니다. 예금자 보호한도는 시점에 따라 5천만원과
1억원으로 갈리고(2025-09-01 경과규정), 착오송금 반환지원은 금액 조건을 넘으면 아예 대상이
아닙니다. 어느 페이지를 근거로 잡느냐가 답의 사실성을 그대로 좌우합니다.

그래서 이 프로젝트는 처음부터 **"그럴듯한 답변을 생성하는 모델"이 아니라 "맞는 근거를 정확히
찾고, 없으면 정직하게 모른다고 말하는 파이프라인"** 을 우선순위로 두었습니다. 생성 모델의
성능을 올리는 것보다 검색과 거절 경계를 정하는 데 훨씬 많은 측정을 썼습니다.

### 문제를 세 단계로 쪼갠 이유

| 단계 | 풀어야 할 문제 | 성공 조건 |
|---|---|---|
| **P1** | 근거가 될 데이터가 없다 | 사이트를 정확히 수집·정규화하고, 검색 가능한 단위로 자르고, 그 품질을 잴 평가셋을 만든다 |
| **P2** | 데이터는 있는데 답을 못 한다 | 검색·생성 레이어를 얹되 환각을 구조로 막는다 |
| **P3** | 답은 하는데 운영을 못 한다 | 데이터와 파라미터를 코드에서 화면으로 옮기고, 변경의 영향을 측정 가능하게 만든다 |

P3의 문제 정의를 한 문장으로 옮기면 이렇습니다 — **답변 품질을 좌우하는 두 가지(적재된 데이터,
검색 파라미터)가 모두 코드 상수로 있어, 매 변경마다 개발자가 개입해야 하는 시스템은 지속적으로
운영되기 어렵다.**

### 왜 어려운가 — 파라미터마다 반영 비용이 다르다

| 구분 | 예시 | 반영 비용 |
|---|---|---|
| **검색 시점** 파라미터 | Top-K, 리랭킹 유무, Hybrid 결합비 | 질의 시 적용 → 즉시 비교 가능 |
| **적재 시점** 파라미터 | Chunk Size, 청킹 방식 | 변경 시 기존 데이터 전체 재청킹·재적재 |

이 둘을 같은 방식으로 다루면 파라미터 하나를 바꿔볼 때마다 전체 재적재가 발생합니다. 관리
화면을 만들어도 실제로는 쓰이지 않게 되는 지점이며, P3 설계 전체를 가르는 구분입니다.

### 2.1 대상 데이터

필드 정의는 [`docs/metadata_schema.md`](docs/metadata_schema.md), 수집 범위 카탈로그는
[`docs/search_scope_definition.md`](docs/search_scope_definition.md)에 있습니다.

### 2.2 사이트가 실제로 던진 문제들

수집은 단순 크롤링이 아니었습니다. 이 문제들이 이후 설계를 상당 부분 결정했습니다.

- **판본 혼재** — 같은 URL이 세션마다 다른 판본을 서빙하는 것을 실측으로 확인했습니다. 같은
  페이지를 새 세션으로 두 번 받아 diff하고, 자동으로 못 좁히면 관측된 판본을 전부 남겨 사람이
  판단하게 했습니다.
- **soft 404** — 없는 페이지에 404가 아니라 200 + "오류" 제목을 줍니다. 상태 코드만 보는 방식으로는
  깨진 링크를 못 잡습니다.
- **JS 뒤에 숨은 링크** — 서류 다운로드·신청 버튼이 `href`가 아니라 onclick 함수 호출입니다.
  인자가 암호화돼 있지만 HTML에 정적으로 박혀 있고 세션과 무관하게 유효함을 확인해, 브라우저
  자동화 없이 정규식 역해석으로 받았습니다.
- **동적 표 페이지네이션** — hidden 필드를 흉내 내 POST하는 방식으로 전체 행을 받았습니다.
  페이지 상한을 임의로 낮게 잡았다가 **실제 289행인 표가 200행에서 잘리는 것**을 발견해 조정했습니다.

### 2.3 Baseline과 단계 간 인계

| 시점 | 물려준 것 |
|---|---|
| P1 → P2 | 58페이지 코퍼스, 구조 인식 청킹, 골든셋, 검색기 비교 결과 |

### 2.4 착수 시점에 이미 정해져 있던 제약

- **변환은 전부 규칙 기반**(LLM 미사용) — 원문 보존과 재현성이 원칙입니다.

  재측정은 큰 변경 후에만 합니다.

## 3. Proposed Method

### 3.1 검색 — 페이지가 아니라 "답이 들어 있는 단위"로 자른다

페이지 전체를 하나의 검색 단위로 쓰면 정답 페이지는 찾아도 **답을 못 뽑는** 실패가 생깁니다.
그래서 FAQ 항목·표 행 같은 구조를 규칙으로 탐지해 자릅니다. 검색기는 BM25 · Dense · Hybrid(RRF)를
질문 유형별로 라우팅하는 구조로 만들었지만, 2026-08-19 실측 후 **전 유형 Dense 단일 경로**로
통일했습니다(4.1절). Hybrid·BM25 코드는 평가와 재도입에 대비해 보존합니다.

색인 텍스트에는 `[제목 · 업무]` 프리픽스를 붙입니다 — contextual retrieval의 결정론 버전입니다.

### 3.2 생성 — 환각을 프롬프트가 아니라 구조로 막는다

이 프로젝트의 일관된 방법론입니다. **LLM의 자유 출력을 문자열로 거르는 접근은 반복적으로 샜기
때문에**(5.3절), 세 가지를 구조로 옮겼습니다.

| 무엇 | 어떻게 |
|---|---|
| **출처 URL·구비서류** | LLM에 URL을 주지 않고, 검색된 업무에서 코드가 결정론적으로 부착 |
| **근거 없는 답변 차단** | 근거 점수가 낮으면 **생성 이전에** 종료(Gate 3) |
| **답변이 근거를 실제로 썼는가** | 자기보고 마커를 믿지 않고 별도 검증 호출로 판정, 문제 시 재생성·본문 교체 |

여기에 질문이 들어오는 입구를 두 겹으로 막습니다 — 인사·욕설·프롬프트 인젝션은 규칙으로(Gate 1),
도메인 이탈은 참조 사전과의 임베딩 거리로(Gate 2) 처리하며 **둘 다 LLM을 부르지 않습니다.**

### 3.3 운영 — 데이터와 파라미터를 화면으로 옮긴다

P3의 핵심 설계 넷입니다.

1. **적재 전에 확인하고 넣는다** — 신규 URL은 파싱→청킹→검증 결과를 보여준 뒤 승인해야 적재됩니다.
   P1에서 표가 잘려 "페이지는 검색되는데 답을 못 뽑는" 실패(AnswerRecall 0.000)를 겪었기 때문입니다.
2. **파라미터를 반영 비용으로 나눈다** — 검색 시점은 즉시 비교, 적재 시점은 소량 재적재 후 비교.
   단 소량 비교가 성립하려면 **소량이 전체를 재현해야 합니다**(4.1절 A1·A2).
3. **변경은 3단계를 거친다** — ①초안 → ②평가 → ③반영. 최신 평가가 기준을 통과해야 반영이
   열리고, 초안을 고치면 평가는 무효가 됩니다.
4. **위험 작업은 사유를 남기고 통제한다** — 멱등키, 사유 필수, 되돌리기 어려운 작업은 재인증,
   활동 로그는 추가 전용. 권한 4단계의 최종 판정은 서버가 합니다.

그리고 **관측** — 질문·답변·의도·검색 경로·응답 시간·모델을 남기지 않으면 운영 중 품질 저하를
발견할 방법이 없습니다. 질의 1건은 성공·실패와 무관하게 정확히 한 행을 남깁니다.

## 4. Experiment Design

### 4.1 무엇을 비교했는가

**데이터·검색 (주로 P1~P2)**

| 비교한 것 | 결론 | 근거 |
|---|---|---|
| 색인 단위 4종 × 검색기 3종 | **구조 인식 청킹 채택** | 169·557문항 두 규모 + 청크 크기 스윕 → [retrieval_eval](docs/retrieval_eval.md) |

| Parent-Child 검색 | **미채택** | 근거가 이미 단일 청크 안에 온전 |

| | 실험 | 수행 |
|---|---|---|
| A1 | 소량 테스트가 전체를 재현하는가 | ❌ 미수행 |
| A2 | Hard Negative 비율이 재현성을 좌우하는가 | ❌ 미수행 |
| A3 | 미리보기가 불량 적재를 막는가 | ⚠️ 기능 완성, 발견율 미측정 |
| A4 | 게이트가 나쁜 변경을 막는가 | ⚠️ 게이트 구현, 통제 실험 미수행 |
| A5 | 파라미터 변경이 품질에 주는 영향 | ⚠️ 비교 화면 완성, 실험 기록 없음 |
| A6 | 리랭커가 GPU에서 이득이 되는가 | ✅ 수행 완료 |

**A1~A5가 밀린 이유는 하나로 모입니다.** 이 기간에 실제로 급했던 것은 "운영자의 결정이
나아지는가"가 아니라 **"웹으로 열었더니 답변이 무너지는 것"** 이었습니다. 데모에서 안 보이던
실패(맥락 없는 후속 질문, 인젝션, 인사말, 근거 없는 답변)가 한꺼번에 들어왔고, 측정 자원이
파이프라인 재설계 쪽으로 갔습니다. 계획한 실험이 관리 도구의 *가치*를 재는 것이었다면, 실제로
한 실험은 파이프라인의 *동작*을 정하는 것이었습니다.

### 4.2 Evaluation Metrics

- **검색 품질**: Recall@1/3/5, MRR, AnswerRecall@5
- **답변 품질**: 생성 성공률, 출처 정확률·포함률, must_include 커버리지, OOS 적절 거절
- **비용**: 질문당 원화 비용, 단계별 호출당 토큰
- **분류 품질**: intent 정확도, question_type 정확도, link_guide 이진 정확도

평가셋은 골든셋을 개발용 전체 평가로, held-out 89문항을 최종 확인용으로 씁니다.

> **LLM-as-a-judge는 도입하지 않았습니다.** 문자열로 의미를 자동 판정하는 지표(must_include·
> 거절률)가 계속 새는 것을 P1부터 반복 확인했기 때문에, 자동 지표는 **하한선**으로만 읽고
> 애매한 문항은 사람이 직접 확인하는 방식(43건 수동 검토)을 앵커로 삼았습니다.

### 4.3 측정 원칙

이 프로젝트가 실패를 겪으며 세운 규칙들입니다.

1. **dev 평가와 test 평가를 가른다.** 튜닝에 쓴 세트로 성능을 재면 부풀려집니다 — intent
   분류에서 100% → 실제 81.5%로 확인했습니다.
2. **수치를 인용할 때는 평가셋을 함께 적는다.** 같은 지표가 169 / 557 / 849 / 89문항 기준으로
   여러 번 측정됐습니다.
3. **분류기 평가는 leave-page-out까지 간다.** 같은 페이지에서 나온 질문끼리 표현도 라벨도
   비슷해, leave-one-out만으로는 누수가 남습니다.
4. **상한·기본값을 근거 없이 잡지 않는다.** 표 청크 3행도, 동적 표 페이지 상한도 실측으로
   못을 박았습니다.

## 5. 결과

### 5.1 리랭커 — "껐다"와 "효과 없다"는 다른 말이다

이 프로젝트에서 가장 오래 끌었던 판정이고, 방법론적으로도 대표 사례입니다.

P2에서 리랭커를 끈 직접 사유는 **CPU 속도**(문항당 27~210초)였고 품질 판정은 표본 6문항이라
보류였습니다. P3에서 GPU(L4)로 held-out 전량을 다시 쟀습니다.

| 지표 (held-out 79문항) | Off | BAAI/bge-reranker-v2-m3 | dragonkue/bge-reranker-v2-m3-ko |
|---|---|---|---|
| Recall@1 | 0.650 | 0.654 | **0.793** |
| MRR | 0.857 | 0.847 | **0.946** |
| **Recall@5 (= K_FINAL, 운영 지표)** | **0.956** | 0.945 ↓ | 0.956 (동률) |
| 총 소요(79문항) | 427s | 1,595s | 1,611s |

순수 랭킹 품질은 dragonkue가 확실히 낫습니다(Recall@1 +0.143, MRR +0.089). **그런데 운영은
top-1을 쓰지 않습니다** — 상위 5개를 이어붙여 컨텍스트로 넘기므로 답변을 좌우하는 지표는
Recall@5이고, 그 값이 동률입니다. 리랭커는 top-5 **안에서의 순서**만 바꿀 뿐 top-5에 못 들던
정답을 새로 끌어오지 못합니다. 문항당 +8~9초를 내고 얻는 것이 그 순서 변경뿐이라 **Off 유지**가
결론입니다.

**부수 소득으로 버그를 하나 찾았습니다.** `MIN_TOP1_SCORE=0.35`는 bi-encoder 점수 분포로 튜닝한
값인데, 리랭킹을 켜면 게이트가 리랭커 점수에 그 값을 그대로 들이댑니다. dragonkue 조건에서 근거
확보 실패 22건 중 18건이 이 패턴 — **검색이 못 찾은 게 아니라 찾아놓고 게이트가 버린 것**이며,
로그에는 "관련 문서 없음"으로만 보여 원인을 찾기도 어렵습니다.
상세: [`docs/reranker_gpu_eval_2026-08-24.md`](docs/reranker_gpu_eval_2026-08-24.md)

### 5.3 반복해서 드러난 패턴

개별 실험보다 이쪽이 이 프로젝트에서 남길 것에 가깝습니다.

- **초기 측정을 곧이곧대로 믿지 않는다.** 업무 필터도 사이트 커버리지도 "낙관적으로 보이는 초기
  수치"가 더 엄격한 재검증에서 뒤집혔습니다. intent 분류가 극단적인 사례입니다 — 운영 방식대로
  재면 100%(자기참조 누수), 자기 자신만 빼도 88.8%(형제질문 누수), **"제대로 측정한 것처럼 보이는"
  두 단계를 더 거치고서야** 정직한 81.5%가 나왔습니다. 누수는 한 번 걷어냈다고 끝나지 않습니다.
- **지표 하나만 보면 반대 결론이 나온다.** 표 청킹에서 MRR과 AnswerRecall이 정반대 결론을 냈습니다.
  어떤 실패는 특정 지표 구조상 원리적으로 보이지 않습니다.
- **LLM 자유 출력을 문자열로 거르는 접근은 반복적으로 샌다.** URL 문제도 마커 문제도, "표현을
  추측해서 거르기"가 아니라 **"LLM이 애초에 그걸 못 쓰게 구조를 바꾸기"** 로 가서야 해결됐습니다.
- **같은 실패가 독립적으로 재현되면 우연이 아니라 방식의 구조적 약점이다.** 복합 질문 분해에서
  1차가 기각한 실패를 2차가 다시 만났을 때, 그것이 always-LLM 방식 자체의 특성임을 확인하고서야
  올바른 대응을 찾았습니다.
- **평가 경로와 운영 경로가 다르면 게이트는 게이트가 아니다.** P3에서 3단계 게이트가 ③에 도달하지
  못한 결함 2건이 정확히 이 형태였습니다 — 운영에는 있는 복구 로직이 평가 경로에 없어 같은 초안도
  실행마다 판정이 뒤집혔고, 목(mock)이 프론트의 틀린 가정에 맞춰져 있어 실서버에서만 실패했습니다.

## 8. 한계와 남은 과제

**측정하지 못한 것**

1. **소량 테스트의 전체 재현성(A1·A2)** — 이것이 없는 한 적재 시점 파라미터는 전체 재적재로만
   판단해야 합니다. **관리 도구의 핵심 가치가 아직 증명되지 않았다는 뜻**이기도 합니다.
2. **게이트의 반려 능력(A4)** — 게이트가 나쁜 변경을 실제로 막는지 통제 실험으로 확인해야 합니다.
   막지 못한다면 이 도구는 잘못된 결정을 빠르게 반영하는 장치가 됩니다.
3. **답변 품질의 정량 평가** — 자동 지표는 하한선이고 사람 검토는 43건에 그쳤습니다.
4. **실사용 지표** — 관측에 팀 테스트와 실사용을 가르는 필드가 없어, 어떤 수치도 아직 "실사용
   지표"라고 부를 수 없습니다.

**만들지 못한 것**

5. **주기 배치 스케줄러** — 변경 감지 로직은 있으나 주기적으로 도는 주체가 없습니다.
6. **통합 실행 환경** — 저장소·백엔드·프론트를 한 번에 띄우는 compose가 없습니다.
7. **파라미터 테스트 시나리오 문서 · 단일 운영 가이드** — 계획한 산출물 중 이 둘이 빠졌습니다.

**구조적 부채**

8. **서빙 경로가 둘** — SSE 토큰 스트리밍 때문에 웹 경로와 CLI/평가 경로가 갈렸습니다. 두 경로가
   다른 한 게이트의 판정은 운영을 설명하지 못합니다(5.3절).
9. **리랭커 재도입 시 `MIN_TOP1_SCORE` 재보정 필수** — 하지 않으면 정답률이 조용히 깎입니다.

## 9. 결론

7주 동안 세운 목표는 **"맞는 근거를 찾고, 없으면 정직하게 모른다고 말하고, 그 판단 기준을 사람이
운영할 수 있게 한다"** 였습니다.

앞의 둘은 수치로 확인했습니다. held-out 89문항에서 Recall@5 0.956, 출처 정확률 0.785, 생성
성공률 100%, 질문당 2.24원이며, 근거가 약하면 생성 이전에 끊고 답변이 근거를 실제로 썼는지를
별도로 검증합니다. 특히 **환각을 프롬프트가 아니라 구조로 막는다**는 원칙은 URL·마커·게이트
세 곳에서 일관되게 적용됐고, 프롬프트로 풀려던 시도가 35회 통제 실험 끝에 막힌 뒤에 나온
결론이라는 점에서 근거가 있습니다.

세 번째는 절반입니다. 데이터와 파라미터를 화면으로 옮겼고 변경에 3단계 게이트를 세웠지만,
**그 도구가 실제로 더 나은 결정을 만드는지는 아직 측정하지 못했습니다**(8장 1·2). 도구를 만드는
일과 도구의 가치를 증명하는 일은 다른 작업이고, 이번에는 앞의 것이 뒤의 것을 밀어냈습니다.

가장 크게 배운 것은 방법론 쪽입니다 — **초기 측정을 의심하고, 지표 하나로 결론 내지 않고,
평가 경로와 운영 경로를 같게 유지하는 것.** 이 셋을 지키지 못했을 때 나온 잘못된 결론들이
이 저장소의 결정 기록 대부분을 차지합니다.
