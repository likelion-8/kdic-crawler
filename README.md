## 1. Problem Definition

### 무엇을 해결하려는가

P2까지 구축한 챗봇은 동작하지만 운영할 수 없는 상태입니다.

답변 품질을 좌우하는 것은 적재된 데이터와 검색 파라미터 두 가지인데, 현재는 둘 다 코드에
있습니다. 새 안내 페이지가 생기면 개발자가 크롤러를 실행하고 적재 스크립트를 돌려야 하며,
Top-K를 5에서 3으로 변경하려면 `src/pipeline.py`의 상수를 수정해야 합니다. P2가 남긴 상태가
실제로 그러합니다. `USE_RERANKER`·`USE_QUERY_DECOMPOSITION`·`USE_SOURCE_RECHECK`·`K_FINAL`이
모두 코드 상수입니다.

> 매 변경마다 개발자가 개입해야 하는 시스템은 지속적으로 운영되기 어렵습니다. 운영자가 데이터를
> 추가하고, 파라미터를 조정하고, 그 변경이 품질에 미치는 영향을 직접 확인할 수 있어야 합니다.

### 왜 어려운가 — 파라미터마다 반영 비용이 다르다

이 프로젝트의 설계를 가르는 핵심 구분입니다.

| 구분 | 예시 | 반영 비용 |
|---|---|---|
| **검색 시점** 파라미터 | Top-K, 리랭킹 유무, Hybrid 결합비 | 질의 시 적용 → **즉시 비교 가능** |
| **적재 시점** 파라미터 | Chunk Size, 청킹 방식 | 변경 시 **기존 데이터 전체 재청킹·재적재** |

단순하게 구현하면 파라미터를 하나 변경할 때마다 494청크 전체 재적재가 발생합니다. 따라서 두
종류를 서로 다른 방식으로 다뤄야 합니다.

### 왜 지금 중요한가

P1·P2가 남긴 미완 과제 중 세 가지는 관리 도구가 있어야 해결됩니다. P3 전반부(07-28~08-05)에
검색·분류·저장소를 크게 손봤으나, 아래 세 가지는 도구 없이는 반복해서 되돌아옵니다.

- **E2E 정량 평가 부재** — P2가 만든 채점기는 착수 다음 날 롤백됐고(07-24), 이후 측정은 07-30
  held-out 베이스라인 1회뿐입니다. 그 뒤 intent 교체(08-03)·분해 On(07-30)·근거 재확인·pgvector
  전환(08-03)이 전부 미측정 상태입니다. 평가를 사람이 매번 손으로 돌리는 한 이 공백은 반복됩니다.
- **파라미터 튜닝 보류** — 채점기를 롤백할 때의 사유가 "파라미터 튜닝은 아직 이르다"였고, 그
  배경에는 변경해 보고 비교할 수단이 없다는 점이 있었습니다.
- **데이터 갱신 추적** — 원본 사이트는 변경됩니다(공시이율 표는 매월). 갱신 감지는
  `content_sha256`으로 구현해 두었으나, 재수집을 누가 언제 트리거하고 결과를 어디서 확인하는지가
  정의돼 있지 않습니다.

## 2. Background & 현재 기준선

### 2.1 P3에서 이미 진행한 것 (07-28 ~ 08-05)

P3는 관리자 화면만 만드는 단계가 아니라, P2가 남긴 RAG 코어를 운영 가능한 형태로 다시 세우는
작업을 병행해 왔습니다.

| 시기 | 내용 |
|---|---|
| 07-28 ~ 29 | 검색 구성 최종 확정 — 기본 Dense, `link_guide`만 Hybrid(Linear α=0.4). 업무 필터를 결합 방식까지 전부 검증해 폐기 확정 |
| 07-29 ~ 30 | intent 분류를 1-NN에서 형태소 TF-IDF+LogReg로 교체(leave-page-out 80.5% → 89.6%) |
| 07-30 | 복합 질문 분해(멀티쿼리) 구현 · 출처 부착 판정 방식 실험 · held-out 베이스라인 측정 |
| 07-31 | 중복 정답 라벨 정정으로 평가셋 853 → 851문항 · PostgreSQL pgvector 환경 구성 |
| 08-03 | Qdrant → Supabase pgvector 전환 · RAG 본 스키마 구축 · intent를 OpenAI structured output으로 재교체 |
| 08-04 | 실사용 로깅(`rag_runs`) · 저장소 구조 정리(`project1_src` → `crawler`) |
| 08-05 | FastAPI 백엔드 착수 · React SPA 구축(챗봇 5화면 + 관리자 12화면) |

## 3. Proposed Method

### 3.1 관리 대상과 화면 매핑

기업(클라비)이 정한 관리 범위 3종을 화면에 매핑합니다.

| 관리 대상 | 화면 | 하는 일 |
|---|---|---|
| **검색 데이터** | AD-002 지식베이스 | 페이지·청크 조회, 신규 URL 추가, 검색 제외/포함 |
| **데이터 파이프라인** | AD-004 파이프라인 | 재수집·재적재 트리거, 6단계 진행 상태 |
| **RAG 파라미터** | AD-007 RAG 파라미터 | Top-K 등 변경, 변경 전후 비교, 운영 반영 |

여기에 P2가 남긴 공백을 메우는 화면을 추가합니다. AD-005 대화 로그(실사용 관찰), AD-006 평가
(테스트셋 기반 정량 비교), AD-008 프롬프트·가드레일, AD-009 운영 정책, AD-010 보안·권한,
AD-011 활동 로그.

### 3.2 핵심 설계 1 — 적재 전에 확인하고 넣는다

신규 URL을 입력해도 곧바로 적재하지 않습니다. 파싱 → 청킹 → 검증 4단계를 미리 실행해 결과를
제시하고, 담당자가 확인한 뒤에만 적재합니다(AD-003, AD-002 내 인라인 블록).

잘못 잘린 청크나 누락된 메타데이터를 적재 전에 걸러내기 위한 장치입니다. P1에서 표가 잘리면
AnswerRecall이 0이 되는 사례를 확인했으므로, 같은 실패를 운영 중에 반복하지 않으려면 사전 확인이
필요합니다.

미리보기는 운영에 영향이 없는 앞 4단계까지만 실행합니다. 색인·반영(5·6단계)은 적재 후에 이어서
수행합니다.

### 3.3 핵심 설계 2 — 파라미터를 반영 비용으로 나눠 다룬다

| | 검색 시점 (Top-K·리랭킹·결합비) | 적재 시점 (Chunk Size·청킹 방식) |
|---|---|---|
| 비교 방법 | **운영 인덱스에 그대로 두 설정 질의** → 나란히 비교 | **테스트용 소량 재적재** 후 비교 |
| 반영 | 즉시 | 결정 시에만 전체 재적재 |

적재 시점 파라미터를 소량으로 비교하려면 소량 테스트가 전체를 재현해야 합니다. 이를 위해 테스트
데이터에 Hard Negative(타 업무의 유사 문구 청크)를 원본 분포대로 포함합니다. P1이 측정한
"top-1의 25.4%가 타 업무" 혼입이 그 분포이며, 이를 제외하고 소량 테스트를 수행하면 실제보다
좋은 결과가 나옵니다.

> 재현성이 확보되어야만 전체 재적재 없이 소량 비교로 반영 여부를 판단할 수 있습니다.

### 3.4 핵심 설계 3 — 변경은 3단계를 거친다

파라미터·프롬프트 변경은 즉시 운영에 반영되지 않습니다. ①초안 편집 → ②초안 평가 → ③운영 반영
순서를 강제하고, 최신 평가가 게이트를 통과해야 [운영 반영]이 활성화됩니다. 초안을 수정하면 평가는
무효화됩니다.

P1·P2에서 "평균 점수가 상승하더라도 민원·범위 밖 질문에서 치명적 오류가 증가하면 반영하지
않는다"는 기준으로 업무 필터와 리랭커를 배제했습니다. 그 기준을 사람의 판단이 아니라 화면의
게이트로 구현하는 것이 P3의 과제입니다.

### 3.5 핵심 설계 4 — 위험 작업은 사유를 남기고 되돌릴 수 있게

관리자 작업은 데이터를 변경합니다. 되돌릴 수 있는 것과 없는 것을 구분해 통제합니다.

- 모든 쓰기에 멱등키(`request_id`)를 요구합니다. 같은 요청이 중복 전달돼도 두 번 실행되지 않습니다.
- 위험 작업은 확인 모달에서 변경 사유를 필수로 받고, 결과를 활동 로그에 기록합니다.
- 되돌리기 어려운 3종(전체 캐시 비우기·계정 권한 변경·긴급 롤백)은 비밀번호 재확인을 요구합니다.
- 활동 로그는 추가 전용으로 두고 수정·삭제 API를 만들지 않습니다.
- 원문 직접 수정은 지원하지 않습니다. 재크롤링하면 수정 내용이 사라지므로, 수정 가능하게 두면
  화면이 사실과 다른 상태를 보여주게 됩니다.

### 3.6 권한 모델

`VIEWER(0) < OPERATOR(1) < EDITOR(2) < ADMIN(3)` 4단 서열입니다.

| 역할 | 할 수 있는 일 |
|---|---|
| VIEWER | 조회 전용 |
| OPERATOR | 파이프라인 실행·취소·재시도, 질의 캐시 관리 |
| EDITOR | 초안·콘텐츠·테스트셋·설정 편집, 게시, 적재 |
| ADMIN | 전체 캐시, 롤백, 계정 관리 |

화면 숨김은 편의 기능이며 최종 판정은 서버 403입니다. 프론트엔드가 감춘 것을 보안 조치로 간주하지
않습니다.

## 4. Experiment Design

관리 도구는 동작 여부만으로 평가할 수 없습니다. 운영자가 내리는 결정이 실제로 개선되는지를
측정합니다.

| 실험 | 질문 | 측정 |
|---|---|---|
| **A1** | 소량 테스트가 전체를 재현하는가 | 같은 파라미터 변경을 소량 세트와 전체 851문항에서 각각 평가해 **순위 일치도**와 MRR 차이 |
| **A2** | Hard Negative 비율이 재현성을 좌우하는가 | 타 업무 청크 비율 0% / 실제 분포 / 과다 세 조건에서 A1을 반복 |
| **A3** | 미리보기가 불량 적재를 막는가 | 의도적으로 잘리는 페이지(대형 표·FAQ)를 넣어 **적재 전 발견율** |
| **A4** | 게이트가 나쁜 변경을 막는가 | P1에서 이미 폐기된 설정(업무 필터 On, 리랭커 On)을 초안으로 넣고 **게이트가 반려하는지** |
| **A5** | 파라미터 변경이 품질에 주는 영향 | Top-K 3/5/10, 분해 On/Off, 근거 재확인 On/Off의 전후 비교 |

A4가 특히 중요합니다. P1·P2가 실측으로 폐기한 설정을 시스템이 걸러내지 못하면, 이 도구는 사람의
판단을 보조하는 것이 아니라 잘못된 결정을 빠르게 반영하는 장치가 됩니다.

### Evaluation Metrics

- **검색 품질**: Recall@1/3/5, MRR, AnswerRecall@5 — P1 기준 그대로
- **답변 품질**: 정답성(LLM-as-a-judge), 출처 정확도, 환각률, 거절 품질 — P2가 수행하지 못한 항목
- **운영 지표**: 적재 전 불량 발견율, 파라미터 변경 리드타임, 재적재 없이 판단한 비율

평가셋은 `evaluation_dataset`(851)을 전체 평가로, `test_set`(89 held-out)을 Smoke 회귀로 사용합니다.

## 5. 우선순위

| 순위 | 항목 |
|---|---|
| **P0** | SSE 계약 정합(목 없이 붙기) · 관리자 인증/세션 · 지식베이스 조회 · 신규 URL 추가 + 미리보기 · 파이프라인 트리거·상태 · **E2E 평가 스크립트 재도입** |
| **P1** | RAG 파라미터 변경 전후 비교 · 대화 로그 조회 · 활동 로그 · 역할별 권한 서버 판정 |
| **P2** | 프롬프트·가드레일 관리 · 운영 대시보드 · 질의 캐시 · LLM 기반 변경 리포트 |

P0에서는 E2E 평가 재도입이 병목입니다. 이것이 없으면 A1·A4·A5를 수행할 수 없고, 파라미터 비교
화면도 수치를 채우지 못합니다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 관리자 백엔드 79개를 모두 구현할 시간이 부족 | P0 범위를 데이터·파이프라인·평가로 한정하고, 나머지는 목을 유지해 화면을 살려 둡니다 |
| E2E 평가 재도입 지연 | 검색 지표만으로 먼저 게이트를 세우고 답변 품질은 이후에 추가합니다 |
| 소량 테스트가 전체를 재현하지 못함 | A1·A2로 우선 확인하고, 재현되지 않으면 적재 시점 파라미터는 전체 재적재로만 판단하도록 범위를 축소합니다 |
| 저장소에 정의 없는 테이블(`feedback`·`suggested_questions`) | `src/schema.py`에 정의를 복원해 재현 가능하게 만듭니다(P0 착수 전 정리) |
| 관리자 조작이 운영 데이터를 훼손 | 사유 필수 + 활동 로그 + 되돌리기 어려운 3종 재인증. 원문 직접 수정은 차단합니다 |

## 9. 완료 기준

- 목(MSW)을 끄고 실제 백엔드로 챗봇과 관리자 주요 화면이 동작합니다.
- 신규 URL을 관리자 화면에서 입력해 미리보기 → 적재 → 재색인 → 검색 반영까지 이어집니다.
- 파라미터를 변경해 전후 검색 품질을 화면에서 비교하고, 게이트를 통과해야 운영에 반영됩니다.
- 모든 위험 작업이 사유와 함께 활동 로그에 기록됩니다.
- P1·P2가 폐기한 설정(업무 필터·리랭커)을 초안으로 입력하면 게이트가 반려합니다.
